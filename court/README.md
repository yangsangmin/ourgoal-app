# 법정(court) — 한 장 설명서

근거: 헌법 제7조 제10항 [판정 분리], 제8조 제3항 [보고의 정본은 법정 판정서다]. 배경은 `docs/specs/REQ-TASK-ES-200-VERDICT-SEPARATION.md`.

## 1. 법정이 하는 일

**작업자(사람이든 AI 든)는 "됐다"고 주장만 쓴다. "됐다"고 판정하는 것은 법정이다.**

예전에는 일한 쪽이 시험 문제도 내고, 채점도 하고, 성적표도 썼다. 그래서 아무것도 안 재도 "100% 통과"가 나왔다.
법정은 작업자가 고칠 수 없는 곳(GitHub)에서, 고치기 전 앱과 고친 뒤 앱을 **나란히 실제로 띄워 놓고** 다음을 직접 본다.

| 법정이 보는 것 | 어떻게 |
| :-- | :-- |
| 되던 것이 고장 났는가 | 주장과 상관없이 항상 본다: 부품(js 파일)이 로드되는지, 기준 커밋의 시험지로 채점했을 때 깨진 검사가 없는지, 앱이 뜨는지, 창 열고 닫기·탭 전환 같은 표준 점검 |
| 주장이 사실인가 | 작업자가 낸 시나리오를 법정이 **진짜 마우스 입력으로** 다시 실행한다. "고쳤다"는 주장은 고치기 전에는 실패하고 고친 뒤에는 통과해야 인정된다 |
| 채점 기준을 건드렸는가 | 금고(5절) 파일을 제품 코드와 같이 고쳤으면 돌려보낸다 |

화면 캡처도 법정이 직접 찍는다. 작업자가 낸 캡처·"N/N 통과" 출력은 증거가 아니다.

### 법정이 보증하는 범위 (여기까지만이다)

- **법정이 재는 것은 표준 점검과, 작업자가 시나리오로 청구한 항목뿐이다.** 모든 버튼을 빠짐없이 눌러 보지 않는다. 청구하지 않은 화면·동작은 아무도 재지 않은 것이며, 무엇을 쟀는지는 판정서의 "법정이 실제로 한 일"과 "주장과 무관하게 법정이 직접 본 것"에 그대로 나온다.
- **주장 하나에 대해 법정이 보증하는 것은 "이 시험의 행동이 기준 커밋에서는 안 되고 작업 커밋에서는 된다"까지다.** 그 시험이 지시 문장과 같은 것을 재는지는 기계가 알 수 없다. 그래서 판정서는 주장 문장 바로 아래에 "법정이 실제로 한 일"을 한국어 문장으로 찍는다. 둘이 같은 것을 말하는지는 읽는 분이 그 두 줄을 대조해 판단한다.
- **지시 항목 목록(보고의 분모)은 작업자가 적어 낸 것이다.** 법정은 그 목록이 상민님 지시 원문과 같은지(빠진 지시가 없는지) 알지 못한다. 그래서 판정서는 "상민님 지시 N건"이 아니라 "작업자가 적어 낸 지시 항목 N건"이라고 말한다.
- 법정의 화면은 PC 의 자동 브라우저다. 접속 주소·기기·언어·시간대에 따라 다르게 동작하는 코드가 새로 들어왔으면, 법정 화면에서 된 것이 실제 사용자 환경에서도 되는지는 보증하지 못한다 — 그런 변경은 판정서에 따로 적히고 통과가 아니라 최소 "확인 부족"이 된다.

## 2. 판정 네 가지

판정서(`REPORT.md`) **머리의 굵은 네 줄**만 보면 된다: ① 판정 ② 상민님이 하실 일 ③ 작업자가 적어 낸 지시 항목 기준 분포 ④ 어떤 커밋을 어디서 심사했는가.
제목과 효력 안내 줄이 그 위에 오므로 **파일의 1~4행이 아니다.** 굵은 글씨의 "판정:" 줄부터 네 줄이다. 손으로 잘라 붙이지 말고 `node court/chat.js <PR번호>` 를 쓴다(6절).

| 판정 | 뜻 | 병합 | 종료코드 |
| :-- | :-- | :-- | :-- |
| **통과** | 적어 낸 지시 항목에 걸린 시험이 전부 "고치기 전엔 안 되고 고친 뒤엔 된다"이고 고장 난 것이 없다. 시험이 지시와 같은 것을 재는지는 법정이 모른다 — 둘째 줄의 "주장 ← 법정이 해 본 것"을 보고 판단한다 | 가능 | 0 |
| **확인 부족** | 막을 이유는 없지만, 확인 못 한 채 나가는 것이 있다(목록이 둘째 줄에 나온다). 주장이 안 걸린 제품 파일 변경이 있을 때, 금고만 바꾼 PR 도 여기에 해당한다 | 가능(알고 결정) | 3 |
| **돌려보냄** | 되던 기능이 고장 났거나, 주장이 사실이 아니거나, 채점 기준을 같이 고쳤거나, 잴 수 있는데 재지 않았거나, 안 되는 주장을 철회·종류 변경·이사로 바꿨다. 작업자가 고쳐서 다시 심사받는다 | 불가 | 1 |
| **심사 못 함** | 법정 도구가 고장 나서 못 봤다(법정이 판정을 내기 전에 시간 초과·강제 종료로 끝난 경우도 여기다 — 그때도 "실행 중 종료" 판정서가 남는다). **통과가 아니다** | 불가 | 2 |

"확인 못 함"은 잘못이 아니다. 못 잰 것을 쟀다고 적는 것, 잴 수 있는 것을 재지 않고 넘기는 것이 잘못이다.

### 고장이 아닌 것은 고장이라고 하지 않는다

법정의 사정으로 못 본 것을 "되던 기능이 고장 남"으로 돌려보내지 않는다. 아래는 돌려보냄이 아니라 **확인 부족**(못 본 것이 있다고 알림)으로 나온다.

| 판정서에 나오는 말 | 뜻 |
| :-- | :-- |
| **표준 점검 갱신 필요** | 표준 점검이 누르려던 버튼이 화면에 여러 개가 되어 법정이 하나를 고르지 못했다. 기능이 고장 났다는 뜻이 아니다. 그 점검이 보던 동작은 이번에 확인하지 못한 채 나간다. 표준 점검을 새 화면에 맞게 고치는 일은 금고 변경이라 별도 PR 이다. 누를 대상이 아예 안 보이면 그때는 고장이다 |
| **법정 환경 한계(외부 차단: 주소)** | 법정은 외부 통신을 끊고 심사한다. 이 변경이 새로 부르는 외부 파일(밖에서 받아 오는 라이브러리 등)이 막혀서 앱을 띄울 때 새 오류가 났다. 실제 서비스에서도 나는 오류인지는 법정이 확인하지 못했다. 법정에서 확인하려면 그 파일의 고정 사본을 법정의 대체 응답 목록(`court/config.json` 의 `stubs` 와 `court/vendor/`)에 먼저 넣는다 — 금고 변경이라 별도 PR 이다 |
| **확인 못 함(시간 부족)** | 법정이 주장을 돌려 보는 데 쓰는 시간은 한 번 심사에 25분까지다(`court/config.json` 의 `claimBudgetMs`). 넘기면 남은 화면 동작 주장은 돌리지 않고 "확인 못 함(시간 부족)"으로 센다. 판정서는 반드시 나온다. 주장이 많으면 여러 PR 로 나눠 내면 전부 돌려 볼 수 있다 |
| **결과가 흔들린다** | 앱을 띄울 때의 차이(새 오류·없어진 파일)나 표준 점검 결과가 기준 커밋과 작업 커밋에서 갈리면, 법정은 양쪽을 두 번씩 더 돌린다. 매번 같을 때만 고장으로 세고, 한 번이라도 다르게 나오면 고장으로 세지 않는다 |

반대로, 법정 도구 고장처럼 보여도 **이 변경이 만든 고장이면 돌려보냄**이다.

- 기준 커밋에서는 끝까지 돌던 시험지가 작업 커밋의 제품 코드 때문에 중간에 죽으면 "제품 코드가 기존 시험을 죽임"으로 돌려보낸다(심사 못 함이 아니다). 사유에 오류 문구가 나온다. 시험지가 아니라 제품 코드를 고친다.
- 돌려보낼 이유와 법정 도구 오류가 같이 있으면 판정은 돌려보냄이고, 첫 줄 끝에 "그 밖에 법정 도구 오류 N건으로 나머지 점검은 끝내지 못함"이 붙는다.
- 부품(js 파일)이 등록하던 전역을 다른 부품 파일로 옮긴 것은 고장이 아니다(앱 전체에서 그 전역이 여전히 등록되면 된다). 지운 부품 파일의 이름이 `index.html` 의 주석에만 남아 있는 것도 고장이 아니다.

둘째 줄의 "확인 못 한 채 나가는 것" 목록은 법정이 고른다: 필요한 확인 수준이 높은 것부터(진짜 폰 > 진짜 계정끼리 > PC 화면), 같은 수준에서는 고칠 게 없었음 > 코드만 확인 > 확인 못 함 순이다. 작업자가 적은 순서와 무관하다.

**판정의 효력은 GitHub 의 `court` 검사 기록에만 있다. 판정서 문서의 글자에는 효력이 없다**(어디서 출력했든 판정서가 이 문장을 싣는다).

## 3. 확인 수준 6단

"통과했는가"보다 먼저 "어떤 수준으로 확인했는가"를 본다. 수준은 작업자가 적는 값이 아니라 **법정이 실제로 한 일**에서 나온다.

| 수준 | 뜻 | 누가 할 수 있나 |
| :-- | :-- | :-- |
| 확인 못 함 | 아직 확인하지 못했다 | — |
| 글자만 봄 | 코드·설정에 그렇게 적혀 있는 것만 봤다 | 법정 |
| 부품만 돌려 봄 | 그 코드 조각을 따로 돌려 봤다 | 법정 |
| PC 화면에서 눌러 봄 | 실제 브라우저에서 눌러 보고 결과를 확인했다 | 법정 |
| 진짜 계정끼리 주고받아 봄 | 실서버에서 계정 2개로 주고받아 봤다 | 사람 손(`[손 필요]`) |
| 진짜 폰에서 해 봄 | 실제 폰에서 해 봤다 | 사람 손(`[손 필요]`) |

일의 종류마다 필요한 최소 수준이 있다(`grade-floors.json`). 예: 설정값은 "글자만 봄"으로 충분하지만, 화면 동작은 "PC 화면에서 눌러 봄", 남의 데이터 열람 차단은 "진짜 계정끼리", 폰 뒤로가기 버튼은 "진짜 폰"이어야 한다. 못 미치면 통과가 아니라 "확인 부족"으로 센다.

필요한 수준은 세 가지 중 가장 높은 것으로 정해진다: 작업자가 적은 분야(`domain`) · 주장이 걸린 파일과 검사하는 파일의 경로(`touches`·`check.file` — 예: `js/**`·맨 위의 `*.html` 은 PC 화면, `api/**`·`vercel.json` 은 진짜 서버, `android/**` 는 진짜 폰) · 주장 문장의 낱말. 분야를 낮게 적거나 파일을 빼고 적어도 낮아지지 않는다.

## 4. 작업자가 하는 일 — 주장 파일 쓰기

`reports/<작업번호>/claims.json` 에 **지시 항목(requirements)** 과 **주장(claims)** 을 적어 같은 PR 에 넣는다. 보고서의 분모는 주장 수가 아니라 지시 항목 수다. 지시 항목은 상민님 지시 원문을 한 항목도 빼지 않고 옮긴다.

**한 변경에 주장 파일은 하나다.** 이번 변경에 `reports/*/claims.json` 이 둘 이상 들어 있으면 돌려보낸다(법정은 첫 번째만 심사하고, 나머지에 든 주장은 심사받지 않은 채 묻히기 때문이다).

주장의 종류(`kind`):

| kind | 뜻 | 꼭 적는 것 |
| :-- | :-- | :-- |
| `behavior` | 화면 동작. 법정이 시나리오를 두 커밋에서 다시 돌린다 | `scenario`, `change`(`fix`·`new`), `fix` 면 `symptom` |
| `static` | 설정값·파일·문구. 최대 "글자만 봄" | `check` — **`check.file` 은 `touches` 안에 있어야 한다**(없으면 형식 오류) |
| `unverified` | 못 잰 것 | `unverified.reason`·`who`·`how`. 법정이 잴 수 있는 종류면 `cannotBecause` 도(아래) |
| `withdrawn` | 철회 | `withdrawnReason`. 지시 자체가 취소됐으면 상민님 말씀 원문을 적는다 |

최상위에 적을 수 있는 칸:

| 칸 | 뜻 |
| :-- | :-- |
| `requirementsSource` (선택) | 지시 원문이 적힌 문서의 저장소 안 경로. 없으면 판정서에 "지시 원문 문서 미기재" 경고가 실린다. 적었는데 작업 커밋에 그 파일이 없으면 형식 오류다 |
| `retire` (선택) | 기준 커밋의 시험지로 채점했을 때 깨지거나, 테스트 파일에서 지운 검사의 폐기 사유. **검사 제목별로** `{file, check(검사 제목 그대로), reason}` 을 적는다(5절) |
| `objection` (선택) | 법정 이의. `{finding(법정의 어느 판단이 틀렸는가), repro(그것을 보이는 재현 — 두 커밋·시험·기대와 실제, 20자 이상)}`. 판정서 "알아 두실 것"에 "법정 이의(작업자 주장)"로 실릴 뿐 판정을 바꾸지 않는다. **이의가 있어도 고쳐서 다시 심사받을 의무는 그대로다** |

`grade`·`verdict`·`outcome`·`passed`·`level` 은 적을 수 없다. 적으면 형식 오류다.

### 잴 수 있는 것은 "확인 못 함"으로 남길 수 없다

필요한 확인 수준이 "PC 화면에서 눌러 봄" 이하인 주장은 법정이 직접 잴 수 있는 종류다. 그런 주장을 `unverified` 로 내려면 `reason` 이 `tool-cannot-measure` 이고, 왜 못 재는지를 `unverified.cannotBecause` 에 아래 목록에서 골라 적어야 한다. 목록에 없거나 비어 있으면 법정은 "시험 미제출"로 보고 **돌려보낸다**(잴 수 있는데 재지 않음).

| `cannotBecause` | 뜻 |
| :-- | :-- |
| `needs-login` | 로그인한 뒤에만 보이는 화면(법정은 외부 통신을 막아 로그인할 수 없다) |
| `file-attach` | 파일·사진을 골라 붙이는 동작 |
| `native-dialog` | 브라우저나 운영체제가 띄우는 창(권한 요청·공유 창 등) |
| `camera-mic-share` | 카메라·마이크·화면 공유 |
| `push-notification` | 푸시 알림이 실제로 와야 확인되는 것 |
| `payment-window` | 결제 창 |
| `external-page` | 다른 사이트로 넘어가야 확인되는 것 |
| `long-duration` | 오래 기다려야 확인되는 것(법정의 시험 한 번은 3분까지) |
| `visual-quality` | 보기 좋은지·어색하지 않은지처럼 사람 눈으로 봐야 아는 것 |

목록의 사유가 있으면 "확인 못 함"으로 세되, 판정서 둘째 줄에 "법정 도구 한계로 못 잰 것 N건(사유)"로 따로 적힌다. 필요한 수준이 "진짜 계정끼리"·"진짜 폰"인 주장은 `needs-two-accounts`·`needs-live-server`·`needs-real-device` 로 내고 `[손 필요]` 안내를 붙인다.

### 안 되는 주장은 바꿔 적어도 풀리지 않는다

법정이 직접 돌려 보던 주장(`behavior`·`static`)을 지우거나, `withdrawn`·`unverified` 로 바꾸거나, 화면 동작 주장(`behavior`)을 글자 확인(`static`)으로 낮추거나, 다른 작업번호 폴더로 옮기면, 법정은 커밋 이력에 남은 옛 주장과 그 시험을 작업 커밋에 **그대로 다시 돌린다**. 여전히 안 되면 돌려보낸다. 철회 자체는 돌려보냄 사유가 아니지만, 철회한 주장이 걸린 지시 항목은 "확인 못 함(작업자가 철회함)"으로 남아 둘째 줄 목록에 나온다.
**그래서 처음부터 법정이 잴 수 없는 것은 화면 동작 주장으로 내지 않는다.** 로그인 뒤 화면·파일 첨부처럼 위 목록에 있는 것은 처음부터 `unverified` + `cannotBecause` 로 낸다. 한번 화면 동작 주장으로 낸 것은 그 시험이 통과하기 전에는 철회해도, 낮춰도 풀리지 않는다.
커밋 이력을 다시 써도 같다: GitHub 의 법정 댓글에는 앞선 심사에서 "안 됨"이던 지시 항목이 남아 있고, 법정이 그 지시를 다시 확인해 주기 전에는 검사가 실패로 남는다(6절).

```json
{
  "id": "modal-back",
  "title": "새 목표 창을 열고 뒤로가기를 누르면 창만 닫힌다",
  "steps": [
    { "do": "goto", "path": "/index.html" },
    { "do": "waitFor", "selector": "#homeAddGoal" },
```

시나리오는 정해진 낱말만 쓸 수 있다. 하는 일(`do`): `goto` `waitFor` `click` `type` `key` `back` `setViewport` `setOffline` `seedLocalStorage` `wait`. 확인(`expect`): `visible` `notVisible` `textContains` `count` `hasClass` `rect` `noHorizontalOverflow` 등. 임의 코드 실행은 없다 — 버튼을 실제로 누르지 않고 함수를 직접 불러 결과 화면을 연출할 수 없다. 사용자 행동이 없거나, 행동 뒤에 화면을 확인하지 않는 시나리오는 "시험 미제출"로 친다.

**법정이 앱을 여는 주소(호스트 이름과 포트)는 실행마다 바뀐다.** 시나리오의 `goto` 에는 경로만 적는다(`/index.html`). 특정 주소에 기대는 시나리오나 제품 코드는 법정에서 같은 결과를 내지 못한다. 선택자는 클래스 조합(`button.btn-primary` 등)보다 고유 id 나 하나뿐인 속성 값을 쓴다 — 같은 클래스의 버튼이 하나 더 생기면 법정은 어느 것을 눌러야 할지 고를 수 없다(표준 점검도 그렇게 쓴다).

## 5. 금고 — 채점 기준은 같이 못 고친다

`vault.json` 이 목록이다(헌법 [별표 3]과 같은 내용이며 `node court/appendix.js --check` 가 둘을 대조한다). 바뀐 파일은 넷 중 하나로 분류된다.

| 분류 | 무엇 | 규칙 |
| :-- | :-- | :-- |
| **동결(frozen)** | 채점 기준 그 자체: `court/` 전체, 헌법 정본과 `AGENTS.md`·`GEMINI.md`·`CLAUDE.md`, `.github/`, `.githooks/`, `package.json` 의 `scripts` 칸, `vercel.json` 의 동결 설정 칸 등 | 제품 코드와 **한 PR 에서 함께 바뀌면 돌려보낸다.** 금고만 바꾸는 PR 은 "확인 부족 — 상민님 결심 필요"로 표시되고, 승인 문구는 "금고 변경 승인"·"헌법 개정 승인"이다("1"·"진행"으로는 승인되지 않는다) |
| **테스트 파일(baseTests)** | `scripts/smoke-test.js`·`scripts/verify-integrity-gate.js`·`scripts/verify-all-clicks.js`·`scripts/test-*.js` | **고칠 수 있다.** 다만 작업자가 고친 시험지는 판정에 쓰이지 않는다 — 아래 |
| **문서·기록(neutral)** | 문서, 주장 파일, 작업 기록처럼 앱에 실려 나가지 않는 것(`vault.json` 의 `neutral` 목록) | 제품도 채점 기준도 아니다 |
| **제품** | **위 셋이 아닌 모든 변경.** 목록에 이름이 없어도 제품이다(맨 위의 `*.html`, `icons/`, `vercel.json`·`package.json` 의 동결 칸 밖 설정 포함) | 주장 파일이 있어야 하고, 주장이 안 걸린 제품 파일이 있으면 최소 "확인 부족"이다 |

### 테스트 파일은 고칠 수 있다 — 법정은 기준 커밋의 시험지로 채점한다

- 법정은 **기준 커밋(고치기 전)의 시험지**를 가져와 **작업 커밋의 제품**을 채점한다. 작업자가 테스트 파일을 어떻게 고쳤든 그 판은 판정에 쓰이지 않는다. 있던 기준을 고쳐서 통과시키는 길은 그래서 막힌다.
- 그 채점에서 **깨진 검사**, 그리고 테스트 파일에서 **지우거나 고친 검사**는 주장 파일의 `retire` 에 **검사 제목별로** 사유를 적는다: `{file, check(검사 제목 그대로), reason}`. 파일 이름만 맞는 사유 한 줄로 그 파일의 다른 검사까지 덮을 수 없다.
- 사유 없이 깨진 검사 = 돌려보냄("있던 검사가 깨졌는데 말이 없음").
- 글자가 있는지만 보던 검사의 폐기는 판정서에 알림으로 남는다. **제품 함수를 실제로 돌리던 검사의 폐기는 상민님 결심 사항**이다(어느 쪽인지 애매하면 법정은 실행형으로 본다 — 도우미 함수를 거쳐 제품을 돌리는 검사도, 같은 제목의 검사가 여러 개일 때 그중 하나라도 제품을 돌리면 실행형이다).
- **검사를 더하는 것은 자유다.** 검사를 하나 더하면서 다른 검사 제목의 번호 표기(`[검증 3/3]` → `[검증 3/4]`)만 바뀐 것은 폐기가 아니다. 그 검사가 작업 커밋에서도 통과하면 판정서에 "제목만 바뀜"으로 표시만 되고, 사유(`retire`)도 결심도 필요 없다.
- 제품은 그대로 두고 시험지만 약하게 만드는 변경도 상민님 결심 사항이다.
- 테스트 파일을 통째로 지우면 돌려보낸다.
- 작업과 함께 새로 만든 검증 스크립트의 출력은 증거로 받지 않는다(자기가 낸 시험).

법정이 틀렸다고 생각되면 법정을 고치지 말고, 주장 파일의 `objection` 칸에 무엇이 틀렸는지와 재현을 적는다(4절). 법정을 고치는 일은 별도 PR 과 `[결심 필요]`로만 한다(제7조 제10항 3호).

## 6. 내 PC 에서 돌린 것은 판정이 아니다

| | 내 PC (예비 점검) | GitHub (판정) |
| :-- | :-- | :-- |
| 실행 | `npm run court` · `npm run court:quick` · 푸시 전 자동(`.githooks/pre-push`) | PR 을 올리면 `court` 검사가 자동 실행 |
| 어느 법정으로 | 내 작업 폴더의 `court/` (내가 고칠 수 있다) | **main 에 있는** `court/` (PR 이 고쳐 와도 쓰이지 않는다) |
| 효력 | 없음. 판정서 맨 위에 "작업자 PC 에서 돌린 예비 점검입니다. 판정 효력이 없습니다"가 찍힌다. 옮겨 적을 수 있는 것은 **막힌 것뿐**이다. "막을 이유 없음"은 판정이 아니며 보고에 옮겨 적을 수 없다 | 있음. 브랜치 보호의 필수 검사이며, 결과가 PR 에 고정 댓글로 게시된다 |
| 쓰임 | 올리기 전에 돌려보낼 것이 뻔한 것을 미리 거른다 | 상민님께 가는 보고의 첫 블록 |
| 판정번호 | 같은 조건으로 다시 돌리면 같은 번호가 나온다. 다만 GitHub 판정의 번호와는 **같은 커밋이어도 다르다** | 실행 장소·빠른 점검 여부·GitHub 실행 번호가 번호에 들어간다. 내 PC 에서 미리 돌려 본 번호로는 GitHub 판정의 번호를 알 수 없다 |

### 푸시 전 예비 점검(`.githooks/pre-push`)이 하는 일

권고다. 뻔히 돌려보내질 것만 막고, 나머지는 알려만 준다. 화면 점검은 하지 않는다(빠른 점검).

| 빠른 점검 결과 | 훅이 하는 일 |
| :-- | :-- |
| 막을 이유 없음 | 그대로 올린다 |
| 돌려보낼 이유가 "주장 없음" 하나뿐 | **경고만 하고 올린다**(중간 저장·초안 PR 용 푸시). 주장 파일은 GitHub 의 법정이 요구한다 — 없으면 거기서 돌려보낸다 |
| 그 밖의 돌려보냄: 채점 기준을 같이 고침 · 되던 부품이 고장 남 · 있던 검사가 깨짐 · 제품 코드가 기존 시험을 죽임 등 | 막는다. 돌려보낸 이유를 화면에 보여 준다 |
| 심사 못 함 | 막는다(통과가 아니다). 왜 심사하지 못했는지 첫 줄에 나온다 |
| 법정이 도중에 죽음(종료코드가 0·1·2·3 이 아님, 또는 1 인데 돌려보냄 판정서가 없음) | "예비 점검을 끝내지 못했습니다(종료코드 N) — 판정은 GitHub 법정이 합니다"를 찍고 올린다. 점검하지 못한 것을 "막을 이유 없음"이라고 찍지 않는다 |
| 올리는 커밋이 이미 `origin/main` 에 들어 있음 | 볼 변경이 없으므로 법정을 돌리지 않고 올린다 |

훅은 법정에 임시 폴더를 주어 판정서를 쓰게 하고, 끝나면 지운다. 전체 판정서를 보려면 `npm run court:quick -- --head <커밋>` 을 직접 돌린다.

상민님께 보고할 때 첫 블록은 `node court/chat.js <PR번호>` 의 출력을 그대로 붙인다. 이 도구는 아무것도 계산하지 않고 GitHub 에 찍힌 판정(발급 주체가 GitHub Actions 인 `court` 검사 + 법정 계정이 단 댓글)만 읽어 온다. 심사를 청구했으면 `court` 검사가 끝날 때까지 기다린 뒤 보고한다.

| `chat.js` 출력 | 뜻 | 종료코드 |
| :-- | :-- | :-- |
| 굵은 네 줄 + `GitHub court 검사 결론: …` | 법정 판정을 옮겼다(통과든 돌려보냄이든) | 0 |
| `법정 심사 전 — 아래는 전부 작업자 주장입니다 (PR #N · 커밋 abc1234 · court 검사 진행 중 · 조회 …KST)` | 아직 판정이 없다. 무엇을 언제 조회했는지가 같이 찍힌다 | 3 |
| `법정 판정서 댓글을 찾지 못했습니다 — 굵은 네 줄을 옮길 수 없습니다 …` + `GitHub court 검사 결론: …` | 검사는 끝났는데 옮길 댓글이 없다: 법정 댓글이 아직 없거나, 다른 커밋의 것이거나, 검사 결론과 어긋나거나, **법정이 아닌 계정이 고친 댓글**이다. 검사 결론만 사실로 옮긴다 | 3 |
| `GitHub 에 없는 PR 입니다: #N — 법정에 심사를 청구한 적이 없습니다 …` | 그런 PR·커밋이 GitHub 에 없다("심사 전"과 다른 말이다) | 4 |
| `법정 판정을 조회하지 못했습니다(심사 전으로 취급) …` | GitHub 조회 실패 | 5 |

GitHub 쪽 구성: `.github/workflows/court.yml`(심사 — 읽기 권한만, PR 코드는 법정의 격리 실행 안에서만 돈다, 포크 PR 은 심사하지 않고 실패로 남긴다, 시간 제한 45분) · `court-publish.yml`(게시 — PR 코드를 받지도 실행하지도 않는다).
GitHub 러너 사정(글꼴 꾸러미 서버 장애 등)으로 심사를 시작하지 못하면 법정 댓글 첫 줄에 그 사유가 나온다. 그때는 `court` 검사를 다시 실행하면 된다(글꼴 설치는 세 번까지 스스로 다시 해 본다).

### 이 PR 이 몇 번 돌려보내졌는가 — 법정이 센다

- 법정 댓글의 넷째 줄 끝에 **"이 PR 돌려보냄 누적 N회"** 가 찍힌다. 같은 커밋을 다시 돌린 것은 세지 않는다. 작업자가 회차를 세어 적지 않는다.
- **3회부터** 돌려보냄의 둘째 줄은 "[결심 필요] 대상 — 이 PR 이 세 번 돌려보내졌습니다. 작업자는 멈추고 상민님께 보고해야 합니다"로 바뀐다(제12조 제1항 4호).
- 앞선 심사에서 "안 됨"이던 지시 항목은 법정 댓글에 남는다. 새 판정에서 법정이 다시 확인해 주지 않았는데 다른 칸으로 바뀌었거나 지시 목록에서 사라졌으면, 첫 줄이 **"돌려보냄 — 앞선 심사에서 안 됨이던 지시 N건이 확인 없이 바뀜"** 으로 게시되고 `court` 검사는 실패로 남는다. 풀리는 길은 하나다: 법정이 그 지시를 다시 확인하는 것(화면 동작 주장이 안 됐던 지시는 "화면에서 눌러 확인", 글자 확인 주장만 안 됐던 지시는 글자 확인으로 충분한 종류일 때 그것으로도).
- 이 기록은 법정 계정(`github-actions[bot]`)이 쓴 댓글에서만 읽는다. 커밋 이력을 다시 써도 남는다.
- **그 댓글을 마지막으로 고친 계정도 본다.** 법정 계정이 아닌 계정이 고쳤으면 법정은 그 PR 의 앞선 기록을 믿지 않는다: 누적 횟수를 3회 이상으로 올리고, 둘째 줄을 **"[결심 필요] 대상 — 법정 기록이 사람 계정(계정 이름)에 의해 고쳐졌습니다"** 로 게시하며, `court` 검사는 실패로 남는다. 이 표시는 그 PR 에서 지워지지 않는다(검사를 다시 돌려도 같다). 그 PR 에서는 통과가 나오지 않으므로, 상민님 결심 뒤 새 PR 로 다시 심사받는다. `node court/chat.js` 도 그런 댓글의 굵은 네 줄은 옮기지 않는다.
- 한계: 법정 댓글이 통째로 없어진 경우는 이 방법으로 알아내지 못한다(그때는 누적 횟수와 "안 됨" 기록이 0부터 다시 세어진다).
- **돌려보내진 작업을 새 PR 로 다시 낼 때는 PR 본문(블록 1)에 앞선 PR 번호를 적는다.** 누적 횟수와 "안 됨" 기록은 PR 단위라 새 PR 에서는 0부터 다시 세어지기 때문이다(제12조 제1항 4호).

## 7. 법정을 처음 들여오는 PR 은 법정 심사를 받지 못한다

GitHub 의 심사는 "main 에 이미 있는 워크플로와 법정"으로 돈다(그래야 PR 이 잣대를 같이 고쳐도 소용없다). 그런데 법정을 **처음** 들여오는 PR(#TASK-ES-200) 시점에는 main 에 법정도 워크플로도 아직 없다. 그래서 그 PR 에서는 `court` 검사가 아예 돌지 않는다.

그 한 번은 다음으로 갈음한다: 법정 자가시험(`npm run test:court` — 가짜를 주입해 전부 걸러내는지 확인) 전수 통과 + 독립 검수 + 상민님 결심. 이것은 그 PR 1건뿐인 예외이며 선례가 되지 않는다(제7조 제10항 8호). 같은 이유로 브랜치 보호의 필수 검사에 `court` 를 넣는 일(`docs/rules/branch-protection.json`)은 그 PR 이 병합된 **뒤에** 적용한다 — 먼저 넣으면 돌지 않는 검사를 기다리느라 그 PR 이 영영 병합되지 않는다.

`court` 검사는 심사를 시작하기 전에 main 의 법정 파일(자가시험 포함)이 다 있는지 먼저 본다. 없으면 무엇이 없는지를 적고 "심사 못 함"으로 끝난다(통과가 아니다). 그 사유는 PR 의 법정 댓글 첫 줄에도 나온다.

`docs/rules/branch-protection.tier2.json` 은 2단(AI용 GitHub 계정 분리)이 끝난 뒤에 쓰는 사본이다. 그때부터 `.github/CODEOWNERS` 가 효력을 가져, 금고(동결 목록)를 바꾸는 PR 은 상민님 계정의 승인 없이는 병합되지 않는다. 테스트 파일(`scripts/smoke-test.js` 등)은 CODEOWNERS 에 넣지 않았다 — 테스트 파일은 작업자가 고칠 수 있고, 법정이 기준 커밋의 시험지로 채점해서 지킨다(5절).

## 8. 명령 모음

| 명령 | 하는 일 |
| :-- | :-- |
| `npm run court -- --head <커밋>` | 예비 점검 전체(화면 점검 포함). Chrome 과 Node 22 이상이 필요하다 |

| `node court/selftest/run.js --unit-only` | 자가시험 가운데 브라우저가 필요 없는 단위 시험과 별표 대조만(몇 초). GitHub 의 법정이 심사 전에 이것부터 돌린다 |

| `node court/appendix.js --check <헌법 파일>` | 헌법의 별표와 법정 설정 파일이 같은지 대조 |
