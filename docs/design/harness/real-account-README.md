# 실계정 2개 확인 하네스 — [손 필요] 안내 (TASK-ES-355 · 노션 CORE-02, GOALS-24 흡수)

이 문서는 상민님이 **한 번만** 해 주시면 되는 일(테스트 계정 2개 만들기·환경 변수 넣기)과, 그 뒤 세션이 돌리는 명령·결과 읽는 법·계정 지우는 법을 적는다.
시나리오 목록은 [`real-account-scenarios.md`](real-account-scenarios.md), 도구는 [`real-account-check.js`](real-account-check.js).

> 이 하네스의 결과는 **작업자 쪽 예비 증거**다. 판정은 법정(`node court/chat.js <PR>`)만 낸다.
> 비밀번호는 채팅·PR·파일 어디에도 쓰지 않는다. 이 PC 의 Windows 사용자 환경 변수에만 둔다.

## 왜 사람 손이 필요한가

- 세션은 로그인 화면(Supabase 대시보드 로그인·OTP)을 통과할 수 없다. 테스트 계정을 만드는 곳이 그 안에 있다.
- 앱의 이메일 **회원가입 탭은 숨겨져 있다**(`index.html` `data-authtab="signup"` 버튼 `display:none`). 그래서 앱 화면으로는 새 이메일 계정을 만들 수 없고, **Supabase 대시보드의 Add user** 로 만든다.
- 하네스가 쓰는 로그인 경로는 **이메일 로그인**(`#loginUser`·`#loginPass`·`#loginSubmit` → `sb.auth.signInWithPassword`)이다. 이 경로는 Supabase 로그인 세션이 생긴다. 구글 직접 로그인·빠른 복구·테스터 B·게스트는 세션이 없어 DM·피드 댓글 확인에 쓸 수 없다(노션 COMM-11).

## 1. 테스트 계정 2개 만들기 (클릭 약 14번, 5분)

1. 크롬에서 `https://supabase.com/dashboard/project/dvqosviqbciohcywkzbq` 를 연다(상민님 계정으로 로그인되어 있어야 한다).
2. 왼쪽 메뉴 **Authentication** → **Users** 를 누른다.
3. 오른쪽 위 **Add user** → **Create new user** 를 누른다.
4. **Email** 칸: `ogtest-a@` 로 시작하는 주소를 쓴다(예: 받지 않아도 되는 상민님 도메인·별칭). **주소에 `ogtest` 글자가 반드시 들어가야 한다** — 하네스는 `ogtest` 가 없는 주소로는 로그인하지 않는다(실사용 계정을 잘못 넣는 사고 방지).
5. **Password** 칸: 새 비밀번호(다른 곳에서 안 쓰는 것). 메모장이 아니라 바로 아래 3번 환경 변수에 넣을 것이므로 잠깐만 기억한다.
6. **Auto Confirm User** 를 체크한다(확인 메일 없이 바로 로그인되게).
7. **Create user** 를 누른다. 목록에 A 가 생긴다.
8. 3~7 을 한 번 더: 주소는 `ogtest-b@...`. 목록에 B 가 생긴다.
9. (선택, 3계정 시나리오용) 한 번 더: `ogtest-c@...`. 없으면 C 가 필요한 시나리오는 `못 함(계정 C 없음)` 으로 남는다.

> 새 개인정보 수집은 없다. 테스트 계정은 상민님이 만든 가짜 사람이고, 이메일·비밀번호 외에 아무것도 넣지 않는다.

## 2. 닉네임은 정하지 않아도 된다

대시보드로 만든 계정은 앱에 처음 로그인할 때 `users` 행이 생기고, 닉네임은 주소의 `@` 앞부분(예: `ogtest-a`)으로 자동으로 정해진다(`index.html` `ensureUserRow` — 겹치면 `#1234` 같은 태그가 붙는다). 하네스는 로그인한 뒤 화면의 실제 닉네임(`state.profile.displayName`)을 읽어 그 글자로 상대를 검색하고, **상대 테스트 계정의 uid 와 같은 결과만** 누른다. 그래서 상민님이 앱에 미리 로그인할 필요가 없다.

## 3. 이 PC 에 환경 변수 넣기 (클릭 약 13번 + 값 5개 입력, 3분)

값은 **이 창에만** 입력한다. 채팅·노션·PR 에 쓰지 않는다.

1. 키보드 **윈도우 키** → `환경 변수` 입력 → **계정의 환경 변수 편집** 을 누른다.
2. 위쪽 **사용자 변수** 상자의 **새로 만들기** 를 눌러 아래를 하나씩 넣는다(변수 이름 / 값):

| 변수 이름 | 값 |
| :-- | :-- |
| `OG_APP_URL` | 확인할 앱 주소. 예: `https://ourgoal-app.vercel.app` (끝의 `/` 없이) |
| `OG_TEST_A_EMAIL` | 1-4 에서 만든 A 주소 |
| `OG_TEST_A_PASSWORD` | A 비밀번호 |
| `OG_TEST_B_EMAIL` | B 주소 |
| `OG_TEST_B_PASSWORD` | B 비밀번호 |
| `OG_TEST_C_EMAIL`·`OG_TEST_C_PASSWORD` (선택) | C 주소·비밀번호 |

3. **확인** → **확인** 으로 닫는다.
4. 이미 열려 있던 터미널·Claude Code 는 새 값을 모른다. **Claude Code 를 한 번 닫았다 다시 연다.**
5. 세션에 "실계정 하네스 돌려" 라고만 말씀하시면 된다. 값은 말씀하지 않는다.

## 4. 실행 명령 (세션이 한다)

```
node docs/design/harness/real-account-check.js --out <결과.json>
```

- 환경 변수가 하나라도 없으면 **아무 데도 접속하지 않고** `계정 없음 — 재생 안 함` 을 출력하고 끝난다(종료 코드 2). 시나리오는 모두 `못 함` 이다. 가짜 통과는 없다.
- 주소에 `ogtest` 가 없거나 A·B 가 같은 주소면 접속하지 않고 끝난다(종료 코드 3).
- 옵션: `--only RA-COMM-03,RA-COMM-04A` (일부만), `--include-withdraw` (탈퇴 신청→다른 기기 복구 시나리오까지 — 기본은 안 함), `--headful` (브라우저 창을 띄워 눈으로 보기).
- 걸리는 시간: 약 6~8분(원격 로그아웃 시나리오는 로그인 60초 보호 시간 때문에 65초를 기다린다).
- 배선만 점검할 때: `node docs/design/harness/real-account-check.js --mock <앱 폴더> --out <결과.json>` — 로컬 정적 서버 + 가짜 Supabase(두 브라우저가 같은 가짜 서버를 공유)로 돈다. 결과 파일 `mode` 가 `mock` 이고, 실계정 확인이 **아니다**.

## 5. 결과 읽는 법

결과 JSON 의 맨 위:

- `mode`: `live`(실계정) / `mock`(가짜 서버, 배선 점검) / `none`(계정 없음, 재생 안 함)
- `summary`: `{ "통과": n, "실패": n, "못 함": n }`
- `runTag`: 이번 실행이 만든 글자 표식(예: `ogtest-202610041530-ab12`). 이 표식이 붙은 데이터만 만들고 지운다.
- `cleanup`: 끝에 지운 것 목록(표·건수·성공 여부). 지우지 못한 것이 있으면 `leftover` 에 남고 출력 끝에 경고가 나온다.

시나리오마다:

- `status`: `통과` / `실패` / `못 함`
- `failedStep`: 실패하거나 못 한 단계 이름과 그때 본 값
- `evidence`: 확인에 쓴 값(화면에서 찾은 글자 수·건수·응답 코드). 비밀값·다른 사람 데이터는 넣지 않는다.
- `manual`: 자동 재생하지 않는 시나리오의 사람 절차(시나리오 표의 같은 행)

`통과` 는 "이 하네스가 이 단계를 실제로 확인했다"는 작업자 주장이다. 법정 판정이 아니다.

### 2026-10-04 mock 실행 결과 (배선 점검, 실계정 아님)

`out-real-account-mock-2026-10-04.json` — 재생 9개 중 통과 7·실패 2, 나머지 19개는 `못 함`(수동 15·mock 범위 밖 4). 실패 2건은 가짜 서버로도 드러나는 **클라이언트 쪽 동작**이라 실계정 재생에서 다시 봐야 한다:

- `RA-CORE-SWITCH`: 같은 브라우저에서 A 로그아웃 → B 로그인하면 B 기록 탭에 A 가 남긴 표식 기록이 1건 보였다(가짜 서버에는 그 기록이 같은 id 로 B 소유로 덮어써졌다 — 실서버에서는 RLS 가 막는지 확인 필요).
- `RA-COMM-04B`: B 브라우저를 닫은 채 A 가 보낸 DM 이 곧바로 "도착" 으로 표시됐고, B 가 대화를 연 뒤에도 "읽음" 으로 바뀌지 않았다(노션 COMM-04 의 "보낸 기기가 스스로 도착 기록" 지적과 같은 모양).

## 6. 하네스가 하지 않는 것

- 운영 사용자 데이터 읽기·쓰기. 하네스는 테스트 계정으로 로그인한 화면과, 테스트 계정이 만든 행(작성자 = A 또는 B)만 센다. 공개 키(anon) 확인도 `sender_id = A` 로 걸러 **건수만** 센다.
- 구글 OAuth 화면 통과(CAL-02), 31일 시각 이동·파기 SQL(ES-351 purge), 진짜 폰 확인. 이것들은 표에 `수동` 으로 적혀 있다.
- 결제·발행·외부 전송.

## 7. 테스트 계정 지우기 (끝났을 때, 클릭 약 6번)

1. Supabase 대시보드 → **Authentication** → **Users**.
2. `ogtest-a@...` 행 오른쪽 **⋯** → **Delete user** → 확인.
3. `ogtest-b@...`(와 `ogtest-c@...`)도 같은 방식.
4. 계정을 지워도 그 계정이 쓴 행이 공개 표(`users`·`team_pings` 등)에 남을 수 있다. 세션에 "테스트 계정 행 남았는지 봐" 라고 하시면, 지우기 **전에** 하네스 끝의 정리(`cleanup`)로 지운 목록과 남은 것을 보고한다. 계정 단위 영구 파기 절차는 `docs/sql/2026-10-04-account-purge-README.md`(TASK-ES-351)를 따른다 — 되돌릴 수 없으므로 그때 `[결심 필요]` 로 여쭌다.
5. **윈도우 환경 변수** 창에서 `OG_TEST_*` 변수를 골라 **삭제**.
