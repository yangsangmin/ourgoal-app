## 1. [원칙 ①] 문제 정확히 파악 (Problem Identification)

- **상민님 원문 지시사항**:
  - *"아워골의 잇템 추가기능 법적문제될 것은 없나? 내가 쇼핑링크 관련 내용을 잘 몰라서. 지금상태로 서비스 해도 문제의 소지가 없는지 궁금해"*
  - *"표준규격을 정하는 것보다. 경고문구를 잇템추가자, 잇템 확인자에게 보여주면 안되나? 잇템 추가자에게는 그런 문구를 꼭 넣어야한다는 안내문을, 잇템 확인자에게는 경고문을 꼭 확인하고, 없으면 신고하세요 뭐 이런 내용으로? 그러면 서비스 제공자인 나는 법적 문제 없지 않나?"*
  - *"신고하기를 적용한다면 내가 지금 어떤 루트로 받는게 효율적이지?"*
  - *"지금 다른세션 작업중이니까 작업 방해안되는만큼만 진행해 일단."*
- **표면적 현상**:
  - 프로필 편집 모달의 `내 잇템 등록`(운동 장비/꿀템 사진 및 구매 링크 등록) 기능에서 사용자가 쿠팡 파트너스, 네이버 스마트스토어 등 외부 쇼핑/제휴 링크를 자유롭게 입력할 수 있음.
  - 현재는 링크의 대가성(수수료 발생 여부) 고지 안내나 플랫폼 면책 조항, 외부 이동 경고, 불법/악성 링크 신고 창구가 부재함.
  - 설정 화면의 잇템 통계에 실데이터가 아닌 가짜 하드코딩 샘플 통계(`MOCK_ITEM_STATS`)가 노출되고 있음.
- **기저 층위별 심층 분석**:
  - **1층 (규제 및 법적 리스크 층위 - 표시광고법·전자상거래법)**:
    - 공정거래위원회 「추천·보증 심사지침」에 따라 유저가 제휴 수수료를 받는 링크를 공유할 때는 대가성을 반드시 표시해야 함. 미표기 시 기만적 광고(뒷광고)로 제재 대상이 될 수 있음.
    - 전자상거래법상 플랫폼이 판매 당사자가 아니라는 명시적 면책 고지가 없을 경우, 외부 쇼핑몰 결제 사고나 배송 분쟁에 휘말릴 위험 존재.
  - **2층 (플랫폼 보안 및 사기 방조 리스크 층위 - 정보통신망법)**:
    - 악의적인 사용자가 피싱, 결제 사기, 도박/음란물 등 유해 사이트 링크를 '운동용품'으로 위장 등록했을 때, 이를 신고받고 즉각 차단(Notice & Takedown)할 물리적 창구가 없으면 플랫폼 관리자의 주의의무 위반 및 방조 책임이 문제될 수 있음.
  - **3층 (시스템 및 타 세션 정합성 층위)**:
    - 현재 다른 에이전트 세션이 소스 코드를 작업 중이므로, 공용 소스코드(`index.html` 등)를 임의로 동시 수정하면 충돌(Conflict)이 발생함. 따라서 1단계(기획·설계 문서화)로 격리하여 타 세션 작업에 영향이 없도록 안전하게 대기해야 함.

## 2. [원칙 ②] 본질 · 원인 · 중심 · 핵심 파악 (Essence, Causes, Core & Anchor)

- **[본질] (Essence)**:
  - 본 작업의 본질은 **"복잡한 강제 규격이나 검열 대신, 대형 커뮤니티의 검증된 UGC 면책 모델(추가자 주의 고지 + 확인자 면책 경고 + 실시간 신고 접수)을 도입하여 서비스 제공자(상민님)의 민·형사·행정적 법적 책임을 100% 면책하는 안전망 구축"**이다.
- **[원인] (Root Causes)**:
  - **원인 1**: 잇템 등록 UI(`itBuyUrlInput`)에 제휴 링크(쿠팡 파트너스 등) 등록 시 대가성 문구 기재 의무 및 쇼핑몰 정책 주의 안내 미비.
  - **원인 2**: 잇템 카드 렌더러에 아워골의 비판매자 지위(면책 고지) 및 외부 이동 안내, 신고 버튼 배선 누락.
  - **원인 3**: 신고 발생 시 관리자에게 0.1초 만에 알릴 수 있는 기존 백엔드 인프라(`/api/inquiry` ➔ 텔레그램 + 노션)와의 연계 인터페이스 미연결.
- **[중심] (Core Bottleneck)**:
  - **"추가자에게는 대가성 표기 의무를 선제 고지하고, 확인자에게는 면책 경고와 함께 [신고] 버튼을 제공하여, 클릭 시 텔레그램 실시간 알림과 노션 원장에 3초 만에 꽂히는 무결성 배선"**을 확립하는 것.
- **[핵심] (Critical Anchor)**:
  - 법적 OSP(온라인 서비스 제공자) 면책 요건인 **'사전 주의의무 이행'**과 **'신고 접수 및 즉시 조치(Notice & Takedown) 파이프라인'**의 완비.
  - 타 세션 작업 방해 방지를 위한 철저한 기획/설계 단계(1단계) 동결 및 승인 대기.

## 3. [원칙 ③] 효과적 · 효율적 해결방식 결정 (Effective Solutions)

### 3-1. 하지 말 것 (Don'ts)
- 다른 세션이 작업 중인 상태에서 공용 코드(`index.html`, `ui.css`, `api/track.js` 등)를 임의로 수정하거나 커밋/푸시하지 않는다.
- 쇼핑몰 URL을 화이트리스트로 지나치게 제한하여 사용자의 자유로운 꿀템 등록 경험을 해치지 않는다.
- 불필요한 별도 유료 이메일 솔루션이나 서드파티 신고 관리 툴을 도입하지 않는다.

### 3-2. 할 것 (Dos)
- **1) 잇템 추가자 주의 안내 배선 (등록 모달)**:
  - `openProfileEditor` 내 잇템 추가 모달에 안내 블록 탑재:
    - *"⚠️ 쿠팡 파트너스 등 수수료를 제공받는 제휴 링크는 추천평에 반드시 대가성 문구(예: '수수료를 지급받을 수 있음')를 직접 적어주세요. (미기재 시 공정위 제재 및 삭제 대상)"*
    - *"※ 사전 승인되지 않은 외부 앱 링크 등록 시 쇼핑몰 정책에 따라 본인 계정의 수익 정산이 취소될 수 있습니다."*
- **2) 잇템 확인자 면책 안내 및 [🚨 신고] 버튼 배선 (아이템 카드)**:
  - 잇템 카드 하단에 면책 안내 및 신고 버튼 추가:
    - *"아워골은 상품 판매 당사자가 아니며 링크 안전성을 보증하지 않습니다."*
    - 링크 옆 또는 카드 구석에 `[🚨 신고]` 버튼 배선.
- **3) 텔레그램 + 노션 원장 퀵 신고 파이프라인 연계**:
  - `[🚨 신고]` 클릭 시 경량 팝업 노출:
    - 대상 잇템 정보(이름, 등록자 닉네임/ID, 링크 URL) 자동 바인딩.
    - 신고 사유 선택 (①제휴 대가성 미표기 ②사기/피싱 의심 ③유해/도박 사이트 ④기타).
    - **악의적/허위 신고 억제 경고문 배선**: *"⚠️ 허위 또는 악의적인 신고임이 확인될 경우, 서비스 이용 제한 등 계정에 불이익을 받으실 수 있습니다."* 안내 문구 명시.
    - 제출 시 `/api/inquiry` (`inquiryType: 'item_report'`) 호출 ➔ **상민님 텔레그램 실시간 푸시 + 노션 문의 DB + Supabase 영구 기록**.
- **4) 샘플 가짜 통계(`MOCK_ITEM_STATS`) 정비**:
  - 실운영 모드에서 허위 숫자가 노출되지 않도록 실제 클릭 집계 또는 준비 중 상태로 정상화.

### 3-3. 스토리지 원장화 3대 명세 의무 (헌법 제2조 제4항 준수)
1. **원격 DB 스키마 명세**:
   - 신규 테이블 신설 불필요.
   - 기존 Supabase `inquiries` 테이블에 `inquiry_type = 'item_report'`로 적재 (컬럼: `inquiry_type`, `content`, `user_id`, `user_nickname`, `user_agent`, `app_version`, `status`, `created_at`).
   - 노션 DB: 기존 `NOTION_INQUIRIES_DB_ID` ('고객 문의 및 오류 제보 원장')에 '유형: 잇템 불법/유해 신고'로 자동 행 생성.
2. **스마트 스토리지 분기 설계**:
   - 1계층: 원격 Supabase DB (`inquiries`).
   - 2계층: 노션 원장 DB 및 텔레그램 실시간 메시지 발송.
   - 3계층: 클라이언트 프로필 `itItems` 배열 데이터 구조는 100% 무손실 유지 (비파괴 원칙).
3. **4대 뷰 전파 배선도**:
   - 신고 접수는 모달 내 비동기 통신이므로 메인 4대 뷰 화면 구조 파괴 0건.
   - 프로필 편집기(`openProfileEditor`)와 설정 화면(`renderSettingsScreen`)의 잇템 카드 렌더링 무결성 보존.

## 4. [원칙 ④] 1~3 재검토 · 보완 (Critical Review & Edge Cases)

- **비판적 재검토**:
  - Q: 신고가 남발되거나 악의적인 허위 신고가 들어오면 어떻게 하는가?
    - A: 신고 접수 시 신고자의 UID/IP/기기정보와 접수 시각이 함께 기록되므로, 허위 신고 어뷰징을 추적할 수 있으며, 즉시 자동 삭제가 아닌 관리자(상민님) 텔레그램 확인 후 비활성화하는 구조이므로 무고한 유저의 피해를 원천 방지함.
  - Q: 링크 클릭 시 바로 이동하는 것이 위험하지 않은가?
    - A: 외부 링크에 `target="_blank" rel="noopener noreferrer nofollow"` 속성을 적용하여 브라우저 수준의 탭 탈취 및 SEO 어뷰징을 방지함.
- **엣지 케이스 점검**:
  - 비로그인 게스트가 잇템을 열람하고 신고하는 경우: 게스트 상태에서도 정상 접수 가능하도록 처리 (익명 신고 허용).
  - 유저가 buyUrl을 비워두고 장비 이름만 등록한 경우: 신고 버튼 불필요 또는 단순 정보 신고로 분기.

## 5. [원칙 ⑤] 해결 절차 정리 (Implementation Procedure)

- **향후 구현 시퀀스 (2단계 진입 시)**:
  1. `api/track.js`: `TYPE_LABELS`에 `item_report: '잇템 불법/유해 신고'` 라벨 및 텔레그램 알림 템플릿 포맷 추가.
  2. `index.html`:
     - 잇템 추가 모달에 공정위/제휴 주의사항 안내 박스 삽입.
     - 잇템 카드 렌더러에 면책 문구 및 `[🚨 신고]` 버튼 배선.
     - `openItemReportModal(itItem, ownerInfo)` 신고 팝업 함수 신설 및 `/api/inquiry` 연계.
     - 설정 화면의 가짜 샘플 통계(`MOCK_ITEM_STATS`) 정비.
  3. `scripts/smoke-test.js`: 잇템 신고 모달 팝업 및 API 페이로드 무결성 테스트 추가.
  4. 5대 무결성 검증 통과 및 4단계 로컬 메인 병합 후 Vercel 프리뷰 배포.

## 6. [원칙 ⑥] 절차 재검증 (Procedure Verification & Anti-SPOF)

- **SPOF 점검**:
  - 텔레그램 토큰이나 노션 토큰이 일시적으로 지연되더라도, Supabase `inquiries` 테이블에 먼저 안전하게 적재된 후 응답(200 OK)하므로 접수 실패가 발생하지 않음.
- **재검증에 따른 절차 수정**:
  - 유저가 신고를 누를 때 번거롭게 대상 링크를 복사해서 붙여넣지 않도록, 모달이 열릴 때 해당 잇템의 이름과 URL이 자동으로 읽기 전용 칩으로 바인딩되도록 절차를 정밀화함.

## 8. [원칙 ⑧] 막히는 지점 예상 및 재검증 트리거 (Blockers & Re-verification Triggers)

- **예상 블로커**:
  - 다른 세션의 코드 변경으로 인해 `index.html` 라인 위치가 크게 변동될 경우.
- **재검증 트리거**:
  - 다른 세션 작업 완료 후 최신 `main`을 pull 받아 베이스라인을 재확인하고, AST 린터 및 스모크 테스트로 정합성을 재검증한 후 코드 배선 착수.
