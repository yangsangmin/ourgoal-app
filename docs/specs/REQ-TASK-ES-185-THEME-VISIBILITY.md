## 1. [원칙 ①] 문제 정확히 파악 (Problem Identification)
- **상민님 지시 원문**: "테마별 시인성이 전혀 안좋아졌잖아 화이트테마는 왜 눌러도 검은색이냐? 성소만 그대로 두고 나머지 다 시인성 좋게 테마이름에 맞게 고치라고"
- **현재 발생하는 문제 및 한계 (표면적 현상)**:
  - 사용자가 설정에서 '화이트(White)' 테마 카드를 클릭해도 화면 배경이 전혀 밝아지지 않고 검은색 다크 모드로 유지됨.
  - 테마별(블랙, 도심) 카드 보더, 서피스, 텍스트의 대비가 미흡하여 각 테마의 정체성이 살지 않고 시인성이 저하됨.
- **표면 아래 기저 층위 분석**:
  - **1층 (미작동/단절 결함)**: `index.html` 내 `if(th === 'white') th = 'focus-sanctuary'` 및 `if(_initTh === 'white') _initTh = 'focus-sanctuary'` 코드가 존재하여, 화이트 테마 선택 시 무조건 성소 다크 테마로 덮어써짐.
  - **2층 (구조/프로세스 부재)**: `ui.css` 내 `[data-theme="white"]`에 `color-scheme: light;`만 존재하고 실제 라이트용 CSS 색상 변수(`--bg`, `--card`, `--ink`, `--rule` 등)가 정의되지 않아 기본 다크 토큰(`#0B0F17`, `#F8FAFC`)이 그대로 유지됨.
  - **3층 (시스템/유저 체감 괴리)**: 사용자는 화이트 테마를 기대하고 눌렀으나 화면이 여전히 검은색으로 보여 기능이 고장 났다고 인지하며 심각한 불신감을 느낌.
- **사용자 상황 및 페르소나**: 밝은 낮 야외나 조명이 밝은 실내에서 아워골을 사용할 때 눈의 피로를 줄이고자 화이트 테마를 선택하는 사용자.

## 2. [원칙 ②] 본질 · 원인 · 중심 · 핵심 파악 (Essence, Causes, Core & Anchor)
- **본질 축 (Essence Axis)**: `FIX/UX` (결함 수정 및 사용자 경험 개선)
- **[본질] (Essence)**: 사용자가 선택한 테마가 지체 없이 실제 UI 컴포넌트(배경, 폰트, 보더, 서피스)에 정확한 색채 규격으로 렌더링되고, 어떤 조명 환경에서도 시각적 피로 없이 최상의 가독성과 대비를 누리게 하는 엔지니어링 무결성 확보.
- **[원인] (Root Causes - 기저 원인 3가지)**:
  1. **원인 1**: `index.html` 초기화 및 설정 적용 함수에서 화이트 테마를 성소로 강제 치환하는 하드코딩된 위헌 코드.
  2. **원인 2**: `ui.css` 내 `[data-theme="white"]`에 라이트 모드 전용 토큰이 누락되어 `:root`의 다크 변수를 상속받는 결함.
  3. **원인 3**: 블랙(OLED 순수 블랙 부재) 및 도심(슬레이트/네온 대비 부재) 테마의 대비 튜닝 미흡.
- **[중심] (Core Bottleneck & Anchor)**: 성소(`focus-sanctuary`) 테마는 1바이트도 수정하지 않고 100% 현행 보존하면서, 화이트 테마의 강제 치환 제거 및 풀 라이트 토큰 세트 주입, 블랙·도심 테마의 시인성을 테마 이름에 맞게 극대화하는 것.
- **[핵심] (Critical Safety & Termination)**: 테마 변경 즉시 `localStorage` 캐시와 `state.profile.settings.theme` 원장에 영속화되어 새로고침 후에도 선택한 테마가 깜빡임(FOUC) 없이 유지되는 종단간 영속성.
- **체감 가설 (User Experience Hypothesis)**:
  > *"사용자가 설정에서 화이트 테마를 누르는 즉시 눈이 편안하고 화사한 순백색 인터페이스가 표출되고, 블랙 테마에서는 칠흑 같은 딥 블랙 속에 선명한 텍스트를 경험하며, 도심 테마에서는 세련된 야경 시티 감성의 선명한 대비를 체감할 것이다."*
- **기존 전체 기능 영향도 분석**:
  - 계정/로그인(세션, 게스트, 소셜)에 미치는 영향: 영향 없음 (세션 100% 보존).
  - 홈 화면 및 스트릭에 미치는 영향: 홈 탭 배경 및 카드가 선택 테마 색상으로 즉시 리렌더링됨.
  - 기록/통계/캘린더 탭에 미치는 영향: 전 탭의 카드 및 보더가 선택 테마에 맞춰 고시인성으로 일괄 표출됨.

## 3. [원칙 ③] 효과적 · 효율적 해결방식 결정 (Effective Solutions)
- **하지 말아야 할 것 (Avoid)**: 성소(`focus-sanctuary`) 테마의 CSS 변수나 DOM 구조 수정 일절 금지, 화이트를 다른 테마로 우회 치환하는 임시 땜질 금지.
- **해야 할 것 (Action)**: `index.html` 내 강제 치환 코드 완전 삭제, `ui.css` 내 화이트/블랙/도심 토큰 정밀 배선, 4대 테마 시각 자가감사 스크린샷 검증.
- **왜 이 방식이어야만 하는가 (Why this approach)**: CSS 변수 기반 테마 시스템의 근본 원리에 맞춰 토큰을 완전하게 정의해야만 모든 컴포넌트가 일관되게 고시인성으로 렌더링되기 때문.

### 3-1. 스토리지 원장화 3대 명세 (헌법 제2조 제4항 준수)
- **1호 (원격 DB 스키마 명세)**: `users.settings.theme` JSON 필드에 테마 식별자(`focus-sanctuary`, `black`, `white`, `urban-city`) 영속화.
- **2호 (스마트 스토리지 분기 설계)**: 로컬 캐시 `ourgoal_current_theme`에 동기화하여 첫 HTML 파싱 시 즉각 반영.
- **3호 (4대 뷰 전파 배선도)**: 테마 변경 시 `document.documentElement.setAttribute('data-theme', themeId)`를 통해 홈(`renderHome`), 목표(`renderGoalsScreen`), 기록(`renderRecordsScreen`), 캘린더(`renderCalendarScreen`), 소통(`renderCommScreen`), 설정(`renderSettingsScreen`) 전 뷰에 CSS 변수 즉시 전파.

### 3-2. 전수 인터랙션(버튼/클릭/입력) 명세표 (Zero-Dead-Click)
| UI 요소 (ID / Name) | 위치/화면 | 사용자 액션 | 기대 동작 (비즈니스 로직) | 예외 처리 및 사용자 피드백 |
| :--- | :--- | :--- | :--- | :--- |
| `theme-card[data-themeid="white"]` | 설정 > 화면&홈구성 | 클릭/터치 | 화이트 라이트 테마 즉시 적용 및 저장 | 활성 카드 테두리 표시 및 성공 토스트 |
| `theme-card[data-themeid="black"]` | 설정 > 화면&홈구성 | 클릭/터치 | 블랙 OLED 테마 즉시 적용 및 저장 | 활성 카드 테두리 표시 및 성공 토스트 |

| `theme-card[data-themeid="focus-sanctuary"]` | 설정 > 화면&홈구성 | 클릭/터치 | 성소 에메랄드 테마 즉시 적용 및 저장 | 활성 카드 테두리 표시 및 성공 토스트 |

### 3-3. 유저 데이터 100% 무손실 보존 규격 (Zero-Data-Loss Schema)
- **아바타 보존**: 기존 아바타 이미지 및 레벨 100% 보존.
- **목표 데이터 보존**: 기존 목표 목록, 마일스톤, 진행률 100% 보존.
- **기록 데이터 보존**: 과거 체크인, AI 피드백, 스트릭 100% 보존.
- **화면 구성 세팅값 보존**: `state.profile.settings.theme`에 선택 테마 안전 영속화.

## 4. [원칙 ④] 1~3 재검토 및 보완 (Review & Edge Cases)
- **비판적 자기 검토 및 약점/한계 인정**: 과거 화이트 테마 선택 시 일부 텍스트가 흰색으로 하드코딩되어 가독성이 떨어지자 임시방편으로 성소로 강제 치환했던 설계적 과오를 솔직히 인정하고, 이를 완전히 걷어내어 정공법으로 라이트 토큰을 완비함.
- **기존 기능과의 충돌 가능성 검토**: 성소 테마 코드를 전혀 건드리지 않으므로 기존 성소 사용자 경험에 0.001%의 회귀도 없음.
- **엣지 케이스 (Edge Cases)**:
  - OS 다크 모드(`prefers-color-scheme: dark`) 상태에서도 유저의 화이트 선택이 최우선 적용되도록 CSS 셀렉터 우선순위 보장.
  - 인라인 스타일 `color: #fff`가 존재하는 서브 텍스트는 화이트 테마 하에서 `var(--ink)`로 자동 치환되도록 방어 CSS 배선.

## 5. [원칙 ⑤] 해결 절차 정리 (Procedure & State Propagation)
- **구체적 실행 시퀀스**:
  1. [1단계]: `index.html` 내 화이트 강제 치환 코드 제거 및 `applyTheme` 정비 (10분)
  2. [2단계]: `ui.css` 내 화이트, 블랙, 도심 전용 토큰 및 가독성 규칙 주입 (15분)
  3. [3단계]: 스모크 테스트 및 무결성 게이트 검증 (5분)
  4. [4단계]: Chrome CDP 기반 4대 테마 실기기 스크린샷 캡처 및 시각 자가감사 (10분)
- **화면 간 상호연동 전파 규격**:
  - 데이터 변경 지점: `applyTheme(themeId)` 호출
  - 즉시 갱신 연계 화면:
    1. 홈 화면 (`renderHome`): 전체 배경 및 카드 색채 즉시 전환
    2. 목표 화면 (`renderGoalsScreen`): 목표 및 로드맵 카드 색채 즉시 전환
    3. 기록 화면 (`renderRecordsScreen`): 히트맵 및 통계 카드 색채 즉시 전환
    4. 캘린더 화면 (`renderCalendarScreen`): 달력 그리드 및 일정 색채 즉시 전환

## 6. [원칙 ⑥] 절차 재검증 (Procedure Verification & Anti-SPOF)
- **단일 실패점 (SPOF) 점검**: 테마 변경 시 `localStorage` 쓰기 실패(쿠키/스토리지 차단 브라우저)가 발생하더라도 런타임 메모리 상태(`state.profile`)로 테마 전환이 정상 작동하도록 try-catch 안전망 유지.
- **가정의 타당성 검증**: 성소 테마가 건드려지지 않는다는 전제가 지켜지는지 Git diff로 확인.
- **재검증 결과 도출된 절차 수정/보완사항**: `meta[name="theme-color"]`도 테마별로 정확히 업데이트하여 모바일 브라우저 상단바 색상까지 완벽히 일치시키도록 배선.
