## 1. [원칙 ①] 문제 정확히 파악 (Problem Identification)
- **로드맵 원문**: "치명 버그 24시간 SLA 가동·버그 신고 버튼" — 완료 기준 "피드백 DB 가동, 신고→수정 리드타임 기록".
- **착수 실측(2026-09-21)**:
  1. 신고 창구는 있다. 설정·푸터의 「1:1 문의 / 오류 제보」 모달 → `POST /api/inquiry` → Supabase `inquiries` + 노션 「아워골 고객 문의 및 오류 제보 원장」 + 텔레그램 알림. 운영 경로에 빈 본문을 보내면 HTTP 400 과 한글 오류 문구가 돌아온다(경로 생존).
  2. 원장에는 제목·유형·상태·닉네임·내용·접수일시 등 9개 속성뿐이다. **심각도·재현성·접수 경로·수정 배포일시가 없어** 어떤 신고가 24시간 대상인지, 고치는 데 얼마나 걸렸는지 기록할 자리가 없다.
  3. 오픈채팅·카카오톡으로 오는 신고를 원장에 넣는 절차와 도구가 없다.
  4. 원장의 5행은 전부 미분류 상태로 90시간 이상 방치돼 있다(전부 시험 행이지만, 실제 신고였어도 같았을 것이다).
- **사용자 상황**: 지인 배포 초기 사용자는 가입·체크인이 한 번 막히면 다시 오지 않는다. 신고해 준 사람이 "고쳤어요" 답을 하루 안에 받으면 남는다.

## 2. [원칙 ②] 본질 · 원인 · 중심 · 핵심 파악 (Essence, Causes, Core & Anchor)
- **본질**: 신고를 받는 것이 아니라 **신고가 고쳐질 때까지 시계가 보이는 것**이다.
- **원인**: 문의 접수 배선(#TASK-ES-123)은 "접수·알림"까지만 설계됐고, 분류와 종결(수정 배포·답장)을 기록하는 칸이 설계에 없었다.
- **중심**: `[신고] → [원장 입력: 인앱 자동 / 채팅 수동] → [분류: 심각도] → [수정 배포 기록] → [리드타임·SLA 판정 자동 계산] → [답장]`. 끊긴 곳은 분류부터 끝까지다.
- **핵심**: 같은 원장을 운영 API 가 쓰고 있으므로, **기존 속성·옵션명을 건드리지 않고 추가만** 해서 운영 접수를 깨지 않는 것.

## 3. [원칙 ③] 효과적 · 효율적 해결방식 결정 (Effective Solutions)
- **FR-01 원장 확장(추가만)**: 심각도(상/중/하) · 재현성(항상/가끔/1회/미확인) · 접수 경로(인앱/오픈채팅/카카오톡/세션 점검/기타) · 수정 배포일시 · 수정 링크 · 신고자 답장 · 리드타임(시간)[수식] · SLA 판정[수식]. 유형 옵션에 `UX 불편`·`칭찬`·`잇템 불법/유해 신고` 추가.
- **FR-02 도구 `scripts/feedback-sla.js`**: `add`(채팅 신고 입력) · `triage`(분류) · `resolve`(수정 기록, 링크 필수) · `replied`(답장 체크) · `check`(미분류·남은 시간·위반·리드타임 요약, 위반 시 종료코드 1).
- **FR-03 런북 `docs/growth/feedback-sla-runbook.md`**: 심각도 기준, 24시간 절차, 12시간 분류·에스컬레이션 시점, 답장 문안.
- **채택하지 않은 것**: 새 피드백 DB 신설(원장이 둘이 된다), Usersnap 위젯(외부 의존 + 화면 캡처 제3자 전송 = 개인정보 수집 확대), 앱 UI 변경(창구는 이미 동작한다).

## 4. [원칙 ④] 1~3 재검토 · 보완 (Critical Review & Edge Cases)
- 노션 select 는 없는 옵션명을 보내면 조용히 새 옵션을 만든다 → 도구가 보내기 전에 스키마의 허용 목록과 대조한다.
- 수정 배포 기록이 0건일 때 리드타임을 0으로 내면 "즉시 해결"로 읽힌다 → `null`/`측정불가` 로 낸다.
- 채팅 신고는 입력이 늦다. 입력 시각을 접수일시로 쓰면 리드타임이 짧게 나온다 → `--received` 로 신고 시각을 받는다.
- 미분류 행은 SLA 대상인지 알 수 없다 → `check` 가 12시간 넘은 미분류를 따로 센다.
- 채팅 신고자의 실명·연락처를 넣으면 개인정보 수집이 넓어진다 → 닉네임만 받는다.

## 5. [원칙 ⑤] 해결 절차 정리 (Implementation Procedure)
1. 운영 `/api/inquiry` 경로 생존 확인(부작용 없는 빈 본문).
2. 원장 data_source 에 속성 추가 → 되읽어 기존 9개 불변·신규 8개 확인.
3. 도구 작성 → `node --check` → 실제 원장에 `check`.
4. 점검 행으로 add → triage(상) → resolve → 수식 되읽기.
5. 런북·REQ·PLAN·TICKETS·dev_log 기록.
6. `npm test` → 브랜치·PR(4블록).

## 6. [원칙 ⑥] 절차 재검증 (Procedure Verification & Anti-SPOF)
- 2번이 운영 접수를 깨는가: 추가만 하므로 API 가 보내는 속성명은 그대로다. 되읽기에서 "사라짐 없음"으로 확인한다.
- 4번이 실제 데이터를 오염시키는가: 점검 행은 제목에 "[SLA 가동 점검] 실제 신고 아님", 접수 경로 `세션 점검` 으로 구분한다.
- 도구가 단일 실패점인가: 도구 없이도 노션 화면에서 같은 칸을 손으로 채우면 수식이 같은 값을 계산한다.

## 7. [원칙 ⑦] 단계별 실행 기준 (Success Metrics & Criteria)
- 원장 속성 9 → 17, 사라진 속성 0.

## 8. [원칙 ⑧] 막히는 지점 예상 및 재검증 트리거 (Blockers & Re-verification Triggers)
- 노션 수식이 API 에서 거부되면 식을 단순화해 다시 넣고 되읽는다.
- 원장에 data_source 가 둘 이상 생기면 도구는 멈춘다(구조 변경 감지) → 1~3 재검토.
