## 1. [원칙 ①] 문제를 정확히 파악한다

함수·문을 세포로 옮길 때마다 생성기는 원래 자리에 「옮김」 표지 주석 한 줄을 남긴다. 구획의 문이 모두 옮겨지면 그 구획에는 구획 주석 · 표지 주석 · 빈 줄만 남는다. 지금 main(bb0b2ea6)의 IIFE 는 2,289줄이고 그 가운데 최상위 주석이 502줄 · 빈 줄이 224줄이다(구획 주석 160 · 자리 표지 7 · 「옮김」 표지 250 · 생성기 머리 표지 22 · 그 밖 63). 구획 113개 가운데 문이 하나도 없는 구획이 40개다. 이 줄들은 공식 지표 `inlineScriptLines` 에 그대로 세어지고, 닫힌 목록에서 이것을 지울 수 있는 줄 종류는 X8 뿐이다. 그 모드가 아직 없다.

## 2. [원칙 ②] 본질·원인·중심·핵심

- **본질**: 실행되지 않는 글자(주석·빈 줄)만, 그것도 문이 하나도 없는 구획에서만 지운다. 실행 글자는 0 변화.
- **원인**: 옮기기 생성기가 남기는 표지는 그 구획에 문이 남아 있는 동안 묶음 경계와 읽는 사람을 위한 것이다. 문이 0 이 되면 쓸모가 없는데 지울 도구가 없었다.
- **중심**: `sweepOnce` — 구획을 줄로 가르고(구획 주석에서 다음 구획 주석 앞까지), 문이 0 인 구획의 주석 줄·빈 줄을 줄 단위로 지우고, 다시 파싱해 토큰열이 그대로인지 스스로 본다.
- **핵심**: 지우면 안 되는 주석을 가르는 일이다. ① 도구가 찾는 표지는 생성기가 안다(구획 주석 · 자리 표지 · 1차 이음매 — 5.7 의 표). ② 시험이 글자로 붙잡는 주석은 생성기가 모른다 — `keep` 칸과 「모의 적용 사본에서 시험 전부」 절차로 막는다.

## 3. [원칙 ③] 해결 방식 — 사양

설정 꼴 · 지우는 줄 · 건드리지 않는 것 · 정지 조건 · 사후 대조의 전문은 설계 `CELL-REGISTRY-DESIGN.md` 5.7 에 있다(PR 본문에도 공개). 결정한 것과 그 까닭:

| 결정 | 까닭 |
|---|---|
| 대상은 `"groups": "all"`(적용 시점에 문이 0 인 구획 전부) 또는 제목 배열 | 구역 이전이 곧 문 약 170개를 더 옮긴다. 대상 목록을 설정에 박으면 그때 낡는다. 제목을 적는 꼴도 생성기가 「문이 0」을 검사해 아니면 멈춘다. 줄 번호는 받지 않는다 |
| **구획 주석은 지우지 않는다** | 닫힌 목록 X8 의 정지 조건이 「함수 이전 생성기가 기대는 자리 표지·구획 주석·1차 이음매 주석」을 든다. 지도 도구(`inline-script-map.js`)도 묶음을 구획 주석으로 가른다 — 남기면 지도의 묶음 수·제목·순서가 그대로다(단위 시험 R2). 빈 구획의 구획 주석을 지우는 일은 finalize(X9)의 몫으로 둔다 |
| 자리 표지·1차 이음매가 든 구획은 **통째로 제외** | 생성기(머리 이음매 자리)와 검사기(`slotLines`)가 자리 표지 아래 줄을 「다음 자리 표지나 빈 줄까지」로 센다. 그 구획의 빈 줄 하나가 경계다 |
| `keep` — 그 글자를 담은 주석은 남긴다. 맞는 주석이 없으면 멈춘다 | 시험이 붙잡는 주석은 생성기가 알 수 없다. 쓰는 PR 이 실측으로 찾아 적는다. 오타로 지켜지지 않는 일을 정지로 막는다 |
| 줄 단위로만 지운다(지키는 주석과 줄을 나눠 쓰는 주석은 함께 남긴다) | 줄 안의 글자를 지우면 X8 「주석 줄·빈 줄」 밖이다 |
| 단계 배열 + `{ "unwire": … }` 단계 | unstate 와 같은 꼴. 가져오기 줄을 지워 문이 0 이 된 구획을 같은 PR 에서 쓸 수 있다(법정은 PR 하나에 생성기를 한 번만 돌린다) |
| 끼워 넣는 자리는 unwire 머리 앞 | 기존 줄을 한 줄도 건드리지 않는다. 함수 선언은 끌어올려지므로 뒤에 있는 `parseUnwireDoc` · `unwireOnce` 를 부를 수 있다 |
| 검사기는 바꾸지 않는다 | sweep 은 세포 파일을 만들지 않는다. unwire · unstate 와 같이 사후 대조를 생성기 안에 두었다 |

## 4. [원칙 ④] 재검토 (반례·부작용)

- **실행 글자가 바뀌지 않는가** → 생성기가 쓰기 전에 다시 파싱해 주석을 뺀 토큰열이 이전과 같은지 본다(다르면 쓰지 않는다). 단위 시험은 생성기와 따로 다시 파싱해 같은 것을 본다(감사 A — 성공한 꾸러미 11건과 실제 index.html 2건): 토큰열 동일 · 사라진 줄은 실행 글자가 없는 줄뿐 · 남은 줄의 글자와 순서 그대로 · 줄 끝(CRLF) 그대로.

- **기존 경로가 달라지지 않는가** → 생성기 diff 는 한 자리에 끼워 넣은 187줄뿐이다(D0). 병합된 unwire(#920) · unstate(#927) · 옮기기(#930) PR 의 기준 트리에서 같은 설정으로 다시 만든 결과가 병합된 것과 바이트 동일(G648 · G649 · G659). 앞선 단위 시험 전부 재실행(B).

- **반론 3 「시험이 붙잡는 주석을 생성기가 못 막는다」** → 맞다. 생성기는 시험을 읽지 않는다(읽어도 시험이 세포 합본에서 찾는 이름과 index.html 에서만 찾는 글자를 가를 수 없다). 그래서 사양에 「쓰는 PR 이 모의 적용 사본에서 시험 전부를 돌린다」를 적고, `keep` 과 메타 `vanishedWords` 를 두었다. 한계로 적는다.
- **재검증**: 모의 적용의 시험 비교는 저장소 밖 사본이 아니라 git 작업 폴더 둘(기준·모의)에서 했다. 단위 시험의 실제 사본 항목(R1~R4)은 기준 커밋을 고정해(PIN) main 이 움직여도 같은 입력으로 돈다.
