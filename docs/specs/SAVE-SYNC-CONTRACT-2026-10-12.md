## 0. 서 있는 사실과 그 한계
1. 로그인 사용자가 앱을 다시 열 때 서버 읽기가 성공하고 서버 기록이 1건 이상이면 `js/core/profile-load.js` 177행이 기기 백업을 서버 것으로 통째로 덮어쓴다. 그래서 저장이 성공했어도 사진 · AI 피드백 · 에너지 · 집중이 사라지고(화면 확인), 올리지 못한 기록 · 목표도 사라진다(화면 확인 — 기록 / 함수 재현 — 목표).
2. ★ 잃는 자리는 이 한 줄만이 아니다: 서버가 답하지 않으면 기기에도 쓰이지 않는다 / 기기 쓰기 실패가 조용하다 / 수동 동기화 단추가 기기에만 있는 것을 버린다(코드로 읽음) / 지움 요청이 실패하면 지운 것이 되살아날 수 있다(코드로 읽음) / 서버 라이브러리를 못 받은 상태에서는 게스트의 저장도 새로 고침 뒤 없다(화면 확인).
3. 실패는 사용자에게 보이지 않는다(500 · 통신 거절은 성공 알림이 글자까지 같다). 라이브러리는 예외 없이 `{error}` 를 돌려주고 응답 없음에는 시간 제한이 없다.
4. ★ 서버 쪽: 앱은 수정 시각 · 버전 칸을 보내지도 읽지도 않는다. 운영 표에 그런 칸이 있는지, 표의 기본 키 · 접근 규칙 · 지운 행이 주인에게 보이는지는 **미확인**이다(세 표의 기본 정의와 접근 규칙이 저장소에 없고 운영을 조회하지 않았다). 저장소가 아는 서버 프로젝트는 하나이고 시험용 서버는 저장소 기준으로 없다.
5. 지움은 표식(`deleted_at`)을 붙이는 수정 요청 한 번이고 결과를 보지 않는다. 행을 지우는 코드는 앱에 0건이다(서버 쪽에서 지워지는 길 — 탈퇴 · 파기 — 은 따로 있다).
6. 저장 한 번이 사용자 1행 · 목표 전부 · 기록 전부를 보낸다. 한 번 누르면 9초에 5번, 켜기만 해도 3번, 기록 탭을 그리기만 해도 나간다.
7. 기록 창 · 기록 도우미 · 목표 만들기는 저장 중 단추를 잠그지 않는다(세 번 누르면 같은 id 3건 / 목표 3개 — 화면 확인).
8. ★ 홈 기록에는 목표 연결(`goalId`)이 없고 분류만 옮긴다. 「목표와 이어진 기록」 여정이 이미 구현됐다고 보지 않는다 — 이 계약의 범위 밖이지만 따로 올린다(9절).

## 1. 순서
- ★ **P0 (좁힘 — 부수지 않는 것만)**: 177행에서 덮어쓰기 **전에**
  - (i) 서버가 주지 않는 칸(사진 · 피드백 · 에너지 · 집중 · 노션 구조 · 테마 부가정보)을 같은 계정 · 같은 id 의 기기 값에서 되붙인다.
  - (ii) 기기에만 있고 서버 응답에 없는 기록 · 목표는 **지우지 않고 보관 열쇠로 옮긴다.** 올리지 않는다. 화면은 지금과 같다(지금도 안 보인다). 달라지는 것은 「영영 없어짐」이 「기기에 남아 있음」이 되는 것뿐이다.
  - (iii) 덮어쓰기 직전의 기기 백업 사본을 한 세대 남긴다(되돌리기용).
  - ◆ 보관과 사본 쓰기를 **되읽어 확인한 뒤에만** 원래 백업을 바꾼다. 용량 초과 · 일부만 쓰임 · 그 사이 앱 종료 때는 원본을 그대로 둔다.
  - ◆ 사본 한 세대를 다음 실행의 (이미 빠진 것이 있는) 백업으로 덮어 하나뿐인 사진을 잃지 않게 한다 — 아직 되찾지 못한 것이 든 사본과 보관 항목은 덮지 않는다.
  - ◆ 본문이 달라진 기록에는 옛 피드백 · 구조를 되붙이지 않는다(4절 규칙을 P0 부터 지킨다).
  - ◆ 되붙이기가 다시 열 때뿐 아니라 수동 동기화와 다음 저장에서도 지켜지는지 확인한다. 목표와 기록의 덮어쓰는 자리가 다르면 자리마다 적는다.
  - ◆ 숨겨서 보관하는 것은 되찾을 재료를 남기는 것이지 「쓸 수 있다」 「저장이 안전하다」가 아니다.
  - 서버에 무엇을 더 묻거나 더 올리지 않는다. 서버 표 · 화면 · 저장 순서는 그대로다. 「없으면 한 번도 안 올라간 것」 같은 판별은 P0 에 넣지 않는다.
- 그 다음 A → B → C → 종단간 회귀(회의 02 합의 그대로). P0 는 A 보다 먼저 병합할 수 있다 — 조건: 덮어쓰기 전후의 기기 자료를 브라우저 재현으로 견준 증거와 되돌리기 확인.
- ★ **실서버 읽기 조사가 B 보다 먼저다**(8절). B 의 규칙은 그 결과에 달려 있다.

## 2. (a) 상태 계약
`saveProfile` 은 예외를 던지지 않고 결과를 돌려준다(값을 더하기만 한다 — 옛 호출은 그대로 돈다. 이것은 호환을 위한 것이고, 경로별 알림 · 닫기 · 잠금은 7절에서 따로 고친다).

- 결과: 자료 종류(사용자 · 목표 · 기록)마다 `기기: 됨 / 안 됨` 과 `서버: 반영 확인 / 미확정 / 일시 장애 / 재인증 필요 / 거절(까닭) / 안 보냄`.
- ★ 실패를 가르는 기준: 응답 없음(제한 시간) · 통신 거절 · 5xx · **429** = 일시 장애 / 401 · `PGRST301` = 재인증 필요 / **403 은 권한 거절과 인증 문제를 가른다** / 그 밖의 4xx = 거절이며 **까닭을 붙인다**: 너무 큼(사용자가 고칠 수 있다) · 잘못된 자료(고쳐서 다시 보낼 수 있다) · 권한(사용자가 못 고친다).
- ★ 「미확정」: 요청을 보냈으나 반영을 확인하지 못한 상태(제한 시간으로 취소한 요청, 돌려받은 행이 확인 조건에 안 맞는 경우). 성공이 아니다.
- 「기기: 됨」은 쓴 뒤 되읽어 같을 때만이다. ★ 사진이 든 쓰기가 용량 때문에 실패하면 「본문만 보존」과 「아무것도 보존 못 함」을 가른다.
- 쓰는 순서: 기기 쓰기(자료 + 5절의 목록 항목)가 서버 호출 앞.
- ★ **입력을 비우고 단추를 푸는 때는 기기 쓰기 확인 직후다. 서버 답은 기다리지 않는다.** 「확인」은 자료와 다시 보낼 뜻(목록 항목)이 되살릴 수 있는 꼴로 남았다는 것이다. 「기록 중…」은 그 짧은 사이에만 보이고, 서버를 기다리는 동안은 상태 표시가 말한다.
- ★ 경험치 · 축하 창 · 색종이 · AI 피드백 요청은 기기 쓰기가 확인된 뒤에만 일어난다. 「저장하지 못함」이면 하나도 일어나지 않는다.
- ★ 제한 시간과 다시 보내는 간격은 박아 넣는 숫자가 아니라 **설정값과 상한**이다. 시험에서는 작은 값으로 취소 · 늦은 성공 · 재접속을 확인하고 실제 망에서 보정한다. 취소는 서버 되돌림이 아니다 — 미확정으로 남긴다. 일시 장애는 상한과 흩뜨림을 둔 간격으로, 거절 · 재인증 필요는 자동으로 되풀이하지 않는다. 진행 중에는 같은 보내기를 또 일으키지 않는다.

화면 상태는 여섯이고, ★ **사용자가 할 일로 묶으면 셋**이다(세기 — 색 · 단추 유무 — 는 셋으로, 글은 여섯으로).
| 묶음 | 상태(속성 값) | 뜻 |
|---|---|---|
| 할 일 없음 | 반영됨(confirmed) | 서버 반영을 확인했다 |
| 할 일 없음 | 올리는 중(sending) | 보내고 기다린다 |
| 할 일 없음 | 기기에 보관됨(local) | 기기에는 있고 서버 반영은 아직 확인 전이다(일시 장애 · 미확정) |
| 할 일 있음 | 다시 로그인 필요(reauth) | 로그인하면 올라간다 — 로그인 뒤 **자동으로** 보낸다 |
| 할 일 있음 | 저장하지 못함(failed) | 기기에도 없다 — 입력을 지우지 않는다 |
| 고칠 수 있음/없음 | 올리지 못함(rejected + 까닭) | 기기에는 있다. 까닭이 「너무 큼 · 잘못된 자료」면 고쳐서 다시, 「권한」이면 문의로 |

◆ 표에 더하는 약속:
- 「기기에 보관됨」의 까닭은 셋이다 — **보내는 차례를 기다림 · 반영 확인 전 · 보관(자동으로 올리지 않음)**. 기록 창은 방금 저장한 것만 말하므로 앞의 둘만 만나고, 기록 목록의 카드와 보관함은 셋째를 만난다. 셋째에 「곧 올라간다」는 말을 쓰지 않는다. 일시 장애와 미확정에 함께 참인 글은 「기기에 보관했어요. 올라간 것은 아직 확인되지 않았어요」 꼴이다(「연결되면 올라가요」는 미확정에 거짓일 수 있다).
- 까닭 「사진 빠짐」: 글은 보존됐고 사진은 못 한 경우. 「저장하지 못함」이 아닌 어느 상태에도 함께 붙을 수 있다. 사진을 다시 붙일 수 있게 미리보기를 지우지 않고, 보존된 부분만 확정한다(첨부 실패를 본문 성공 뒤에 숨기고 입력과 사진을 모두 비우지 않는다).
- 나머지 조합: 기기 쓰기는 실패했는데 서버 반영이 확인됨 → 「반영됨」(기기 사본이 없다는 것은 계수기에) / 기기 쓰기 실패 + 서버 미확정 → 「저장하지 못함」으로 다루고 입력을 남긴다 / 안 보냄(보관) → 「기기에 보관됨 · 보관」.
- 다시 보내기의 상한을 넘겨도 남는 항목에는 확인 · 문의로 가는 길이 있어야 한다.

## 3. (c) 기기에만 남아 있는 것 — ★ 판별은 확인된 뒤에만
- 초안 1 의 「서버에 그 id 가 아예 없으면 한 번도 안 올라간 것」은 **버린다.** 없음은 접근 규칙이 숨긴 것 · 조회 범위 · 쪽 나눔 누락 · 계정 변경 · 서버 쪽 삭제 · 동시 변경일 수도 있다.
- 규칙: 기기에만 있는 기록 · 목표는 **존재 미확정**으로 보관한다. 지우지 않고, 자동으로 올리지 않는다.
- ◆ **전환 전부터 기기에 남아 있던 것**은 자동으로 올리지 않는다(이 앱이 그 계정으로 만들었다는 증거가 기기에 없다). 옛 오프라인 대기줄의 항목도 「새 기록」이라고 단정하지 않고 보관으로 간다. 새 계약 아래에서 생긴 변경(새로 · 고침 · 지움 · 되살림)은 5 · 6절의 조건을 채울 때 보낸다.
- 보관한 것을 다시 올리는 길은 둘뿐이다: (가) 실서버 조사로 「지운 것 포함 조회가 주인에게 온전히 보인다」가 확인되고 그 조회로 존재하지 않음 · 지워지지 않음이 확인된 것 (나) 사용자가 보관함에서 직접 고른 것 — ◆ 고른다고 계정 · 주인 · 다른 기기에서 지웠는지의 검사가 면제되지 않는다. 「되살리기」와 「새 사본으로 올리기」를 가르고, 지운 것이 되살아날 수 있다는 것을 말하는 확인 한 번을 거친다.
- 읽기가 실패한 재실행에서는 기기 것을 **보여 주기만** 한다. ★ 지금 코드가 그때 기기 것을 통째로 다시 올리는 것(169~175행)은 B 에서 그친다.
- 게스트 → 가입 이관은 같은 변환(기록의 `meta` · 목표 연결 · 사진의 한계까지)을 쓰고 같은 규칙으로 시험한다.
- ★ 보관함(격리 칸): 계정마다 따로. 다른 계정에 본문을 보이지 않는다. 기한이 지났다고 자동으로 영구 삭제하지 않는다(지우는 규칙은 상민님 결심 — 탈퇴 · 파기 때의 처리 포함). 화면: 「다른 기기에서 지운 것의 사본」은 보이지 않는다 / 「올리지 못한 것」은 **비어 있지 않을 때만** 기록 탭의 보관함에 보이고, 할 수 있는 일은 내용 보기 · 복사 · (확인된 경우) 다시 올리기.

## 4. (i) 서버로 안 가는 칸
- 대상과 되붙이는 규칙은 1절 P0 (i). 서버가 준 칸을 기기의 옛 값으로 덮지 않는다.
- ★ 기록의 본문을 고친 뒤에는 옛 AI 피드백 · 구조를 그대로 되붙이지 않는다(본문이 달라졌으면 피드백은 「옛 본문에 대한 것」으로 표시하거나 떼어 둔다 — 어느 쪽인지는 B 설계에서). ◆ 지움은 휴지통으로 옮기기와 영구 삭제를 가른다: 휴지통에 있는 동안에는 사진 · 피드백을 되살릴 수 있게 그대로 두고, 영구 삭제 · 탈퇴 때의 파기는 승인된 정책과 보관함 사본의 처리에 맞춘다. 이번 안정화에 있던 기능을 없애는 일을 섞지 않는다.
- 한계: **같은 기기 안에서만** 보존이다. 이 조치만으로 「사진이 안전하다」고 쓰지 않는다. ★ 사용자에게 알린다 — 사진을 붙이는 순간 미리보기 아래 작은 글 한 줄과 설정에. 매번 알림으로 띄우지 않는다(문구는 시안).
- 미해결: 사진 · 피드백을 서버에 남길지, 일정 · 설정이 기기에만 있는 것. ★ 「피드에 공유」로 이미 서버에 간다는 것이 개인 기록의 새 올리기를 자동으로 허락하지는 않는다 — 상민님 결심.

## 5. (b) 미확정 변경 목록
- 계정마다 기기의 별도 열쇠. ★ 항목 = 변경 고유 id · **변경 세대(그 대상의 몇 번째 변경인가)** · 계정 · 자료 종류 · 종류(새로 / 고침 / 지움 / **되살림**) · 대상 id · 서버로 갈 칸의 내용(사진 같은 큰 것은 넣지 않는다 — 목록으로 사진까지 되살린다고 말하지 않는다) 또는 삭제 표식 · **보낼 때 알고 있던 서버 상태** · 만든 때 · 시도 횟수 · 마지막 실패의 종류.
- ★ 한 대상의 변경이 이어질 때(새로 → 고침 → 지움 → 되살림, 보내는 중에 또 고침): 항목은 대상마다 하나로 합치되 세대를 올린다. **확인된 세대까지만** 지운다 — 보내는 중이던 세대 3의 답이 와도 그 사이 세대 4가 생겼으면 항목은 남는다.
- 적는 순서와 중단: 자료 → 목록 → 되읽기. ★ 그 사이에 앱이 꺼진 경우(자료만 있음 / 목록만 있음)를 켤 때 부수지 않고 고친다 — 자료만 있고 목록이 없으면 3절의 보관 규칙, 목록만 있고 자료가 없으면 목록의 내용으로 본문을 되살리고 사진은 없다고 표시.
- 보내는 것은 목록에 있는 대상뿐이다. 「매번 전부 다시 보내기」를 그친다.
- ★ 뺄 때의 증거: 돌려받은 행에서 (1) id · 계정 · 자료 종류가 맞고 (2) 반영된 행 수가 맞고 (3) 보낸 칸들이 **자료형별로 고르게 한 뒤** 같다 — 시각은 같은 시점인지, 숫자와 글자, 빈값과 안 보냄, 묶음 값의 열쇠 순서, 서버가 채우는 기본값. 글자를 그대로 이어 붙인 지문으로 견주지 않는다. 서버가 빼거나 바꾸는 칸은 계약에 이름을 적는다. 안 맞으면 끝없이 다시 보내지 않고 미확정 또는 오류로 남긴다. 맞추려고 보낸 내용을 버리지 않는다.
- ★ 내용이 우연히 같은 옛 요청의 답을 새 변경의 확인으로 쓰지 않는다(변경 고유 id · 세대로 짝을 맞춘다). 지움은 그 행의 지움 상태와 그 지움 요청의 답으로, 되살림은 따로 확인한다. 응답 없음 · 읽기 거절은 성공이 아니다.
- 지움 · 되살림도 목록을 탄다. 다시 보내는 때: 켤 때 · 온라인 복귀 · 다음 저장 · 사용자의 「다시 올리기」 · 로그인 직후 · ◆ **켜 둔 채 서버가 돌아온 경우**(지금은 켜 둔 채 기다려도 다시 올라가지 않는다 — 화면 확인).
- ◆ 변경 세대는 같은 대상을 여러 탭이 만질 때도 겹치지 않게 올라가야 한다(계정별 열쇠 안에서).

## 6. (d) 충돌과 경계 — ★ 기기만으로 되는 보장과 서버가 도와야 되는 보장을 가른다
**기기만으로 되는 것**
- 한 기기 안에서: 한 번에 한 탭만 목록을 고치고 보낸다. ★ 브라우저 잠금이 없을 때의 시각 표식 잠금은 온전한 잠금이 아니다 — 경쟁과 죽은 탭이 남긴 잠금의 복구를 시험하되, ◆ 「시험했다」로 보장을 대신하지 않는다. 잠금이 없는 브라우저에서는 충돌에 안전한 다른 방식을 쓰거나 지원 범위를 좁혀 적는다.
- 계정: 지금 로그인한 계정의 항목만 보낸다. 로그아웃은 목록을 지우지 않고, 나가 있던 요청은 취소한다. 저장할 때와 보낼 때의 계정이 같은지 본다.
- 같은 id 가 한 묶음에 두 번 들지 않게 거른다. id 는 창을 열 때 한 번 만들고, ★ 창을 다시 쓰거나 다음 기록을 시작할 때 새 id 를 준다.
- ★ 경험치 · AI 피드백의 「기록 하나에 한 번」: 기기의 표식만으로는 여러 탭 · 여러 기기 · 껐다 켠 뒤까지 보장되지 않는다. 경험치는 따로 도는 서버 원장이 같은 기록에 두 번 주지 않는지 확인하고, 피드백을 붙이는 저장이 그 사이의 본문 · 사진 고침을 덮지 않게 한다. AI 가 늦거나 실패하거나 다시 만들어질 때의 규칙을 적는다.

**서버가 도와야 되는 것 — 지금은 보장하지 못한다**
- ★ 늦게 도착한 옛 요청이 서버의 더 새로운 내용을 덮는 것, 다른 기기에서 지운 직후 이 기기의 고침이 도착하는 것. 답을 무시하는 것만으로는 막지 못하고, 보내기 전에 조회해 봐도 조회와 쓰기 사이의 틈이 남는다.
- 막으려면 서버의 조건부 쓰기(수정 세대 칸, 또는 지움 상태를 건드리지 않는 갱신)가 있어야 한다. 그것은 운영 표를 고치는 일이다.
- ◆ 지금은 **미측정**이다. 실서버에서 재현되면 **출시 차단 후보**다(8절의 기준 「지운 것이 되살아난다」 「사라진다」에 닿는다). 해결하거나, 닿는 길을 좁히거나, 위험을 적은 별도 결정이 있기 전에는 「저장 안전 완료」로 표시하지 않는다.
- ◆ 지금 운영에도 같은 동작이 있다는 것은 「새로 생긴 회귀가 아니다」의 근거일 뿐 면제 근거가 아니다. 위험을 안고 가는 결정이 나더라도 「유실 방지 검증 통과」와는 따로 적는다.
- 실서버 조사 결과(표에 쓸 만한 칸이 이미 있는가, 묶음 저장이 지움 표식을 건드리는가)와 선택지를 상민님께 올린다.

## 7. (e) 화면이 읽는 것 · (f) 호출자
- 화면이 쓰는 것은 셋이다: **이 기록의 상태**(기록 창과 ★ 기록 목록의 카드가 모두 물을 수 있다) · **남은 것의 요약**(자료 종류별 개수 · 가장 오래된 것의 나이 · 재인증 필요 유무 · 올리지 못함 유무) · ★ **「저장 상태가 바뀜」 사건**(배경에서 다시 보내 상태가 바뀌면 화면이 줄을 고친다 — 앱에 이미 있는 사건 통로를 쓴다).
- ★ 상태 표시의 뼈대(기록 창 꼴과 상태 표시가 같이 쓰는 약속): 기록 창 안 저장 줄 아래에 요소 하나 `#captureSyncStatus`, 상태는 속성 하나 `data-sync-state`(confirmed · sending · local · reauth · rejected · failed), 까닭은 `data-sync-reason`, 단추는 많아야 하나 `#captureSyncAction`. **코드는 속성과 글만 바꾸고 색 · 크기를 직접 적지 않는다.** 읽어 주는 자리는 이미 있는 `#a11yLiveAnnouncer`.
- 기록 창은 기록만 센다. 목표 · 설정의 남은 것은 전역 자리가 말한다.
- ◆ 상태 표시가 사라지는 때는 시안이 정한다(「반영됨」은 잠깐 보이고 사라지고, 나머지는 풀릴 때까지 남는다는 방향).
- ◆ 늦게 온 상태 사건이 지금의 입력이나 알림을 바꾸지 않게, 사건마다 대상 id · 계정 · 세대를 보고 그린다(기록 둘을 빠르게 저장한 경우). AI 피드백의 실패는 기록 저장의 실패와 따로 말한다.
- ★ 「다시 올리기」는 목록 전체를 다시 보낸다 — 남은 것이 둘 이상이면 단추 글이 그렇게 말한다. 「다시 로그인 필요」는 로그인 뒤 자동으로 보내고 한 번 더 누르게 하지 않는다. 화면 글에 「서버」라는 낱말을 쓰지 않고 앱에 이미 있는 「기기에 보관」을 따른다.
- ★ 알림: 경험치와 축하는 기기 쓰기 확인 즉시. 알림의 앞 글만 상태를 따른다(반영됨이면 지금 글, 기기에 보관됨이면 다른 글). 축하 창이 화면을 덮는 동안의 상태 표시는 시안이 두 가지로 그려 정한다.
- 호출자(저장 경로 11개) 공통 규칙 넷: ① 결과를 받아 사실대로 알린다 — ★ 알림은 공용 도우미 하나가 「한 일 + 상태 꼬리」 꼴로 짓는다 ② 기기 쓰기 확인 전에는 창을 닫거나 입력을 비우지 않는다 ③ 저장 중에는 단추를 잠근다 ④ id 는 창을 열 때 한 번.
- ★ 시안의 범위는 기록 창과 공용 알림 꼴 하나다. 나머지 10경로의 화면은 시안 범위 밖이고 구현 지시의 표로 다룬다.

## 8. (g) 계수기 · (h) 범위 밖 · (j) 검증
- 계수기: 설정 묶음이 아닌 별도 열쇠. 시도 수(분모) · 경로 · 결과 종류 · 기간. 다시 보내기와 고유 변경 수를 가른다. 본문 · 사진 · 토큰 없음. 서버로 보내지 않는다. 기기 몇 대의 값을 전체 실패율로 쓰지 않는다.
- 범위 밖: 일반 동기화 엔진 · 실시간 구독 · 성능 최적화 · 일정/설정의 서버 보존 · 홈 기록의 목표 연결.
- ★ **실서버 조사(B 보다 먼저) — 읽기부터, 쓰기는 승인 뒤**:
  - 읽기(전용 시험 계정으로 자기 행만 — ◆ 이미 허락된 계정으로 하는 부수지 않는 조사라 새 승인을 따로 구하지 않는다. 비밀값을 출력하지 않고, 남의 본문 · 쓰기 · 파기 · 발송을 하지 않으며, 로그인이 일으키는 토큰 갱신 같은 딸린 효과는 적어 둔다): 칸의 유무와 값의 모양 / 지운 행이 주인에게 보이는가 / 쪽 나눔과 범위 / 수정 시각 · 버전 칸이 있는가.
  - ◆ 자기 행을 읽어 알 수 있는 것(값 · 칸의 유무)과 권한이 있어야 볼 수 있는 표 정의(기본 키 · 자료형 · 기본값 · 접근 규칙 전체 · 쓰기 허용)를 가른다. 못 본 정의는 미확인으로 남긴다. 조회 결과 0행은 「없다」의 증명이 아니다.
  - 쓰기(운영 안의 시험 계정 A · B, 자료 · 정리 범위 · 바깥 알림 억제를 먼저 적고 승인받은 뒤): 자기 행 쓰기와 상대 행 거절 / 지움 표식 붙이기 · 되살리기 / 「받은 행을 돌려 달라」가 규칙에 막히는가, 돌려주는 칸의 모양 / 0행 결과 / 돌려받기는 거절인데 쓰기는 된 경우 / 같은 id 재시도 · 한 묶음에 같은 id 둘 · 늦은 답 뒤 새 고침 · 다른 기기에서 지운 뒤 고침 / 묶음 저장이 지움 표식을 건드리는가.
- 검증표: 변경 종류(새로 · 고침 · 지움 · 되살림) × 조건(성공 · 500 · 401 · 403 · 429 · 통신 거절 · 응답 없음 · 오프라인 · 탭 강제 종료 · 새로 고침 · 계정 전환 · 두 탭 · 여러 번 누르기 · 사진 · 용량 초과) × 확인 방식(함수 · 브라우저 · 실서버 · 실기기). 단계마다 「확인한 범위」와 「못 잰 것」을 따로 적는다.
- ★ 로드맵 출시 체크리스트와의 이음: 이 계약이 닿는 항목 — 게스트→가입(QA01) · 세션과 종료 뒤 복귀(QA02) · 저장과 복귀(QA03~05) · 자정/시차(QA06) · 삭제/휴지통/복원(QA07) · 목표/템플릿의 주인과 연결(QA08) · 로그인/뒤로가기(QA12) · 남의 자료 접근 거절(QA13) · AI 지연과 429(QA14) · 탈퇴와 보관함 파기(QA16 · 17) · 백업 · 사진 복원 · 되돌리기(QA18) · 키보드/큰 글씨(QA19). 그 밖의 항목은 계약 범위 밖이지만 출시 체크리스트에 그대로 남는다.
- ★ **출시를 막는 기준**: 아래 가운데 하나라도 남아 있으면 막는다 — 기기 쓰기가 확인된 기록 · 목표 · 사진이 그 뒤 화면이나 기기에서 사라진다 / 기기 쓰기가 확인되지 않았는데 입력이 비워져 어디에도 남지 않는다 / 실패가 성공으로 보인다 / 다른 계정으로 쓰인다 / 지운 것이 되살아난다 / 경험치가 겹쳐 들어간다 / 저장이나 로그인이 안 되는 상태에 갇힌다 / 영영 미확정으로 남는다. 「브라우저 재현에서 안 보였다」만으로 통과시키지 않고, 필요한 실서버 · 실기기 증거와 못 잰 것을 함께 놓고 판정한다.

## 9. 상민님께 올릴 것(이 계약에서 나온 것)
1. 서버가 도와야 되는 보장(6절 뒤쪽)을 출시 전에 넣을지 — 실서버 읽기 조사 뒤에, 운영 표를 고치는 일이 필요한지와 함께.
2. 운영 안의 시험 계정으로 쓰기 시험을 할지(8절) — 범위를 적어서.
3. 사진 · 피드백의 서버 보존, 일정 · 설정의 서버 보존.
4. 보관함을 지우는 규칙.
5. 홈 기록에 목표 연결이 없다는 사실 — 「오늘 행동 → 기록 저장 → 목표 연결 확인」 여정이 지금 무엇으로 확인되는지부터 다시 본다(디자인 지시의 여정 회귀 확인에도 닿는다).
6. 새 화면 글(상태 여섯 · 사진 한계 안내 · 보관함) — 시안으로.
