## 1. [원칙 ①] 문제를 정확히 파악한다

- 로그인 사용자의 사진과 AI 피드백이 저장이 성공했는데도 새로 고침에서 사라진다. 저장이 실패해도 성공으로 보이고, 그 기록은 다시 열 때 사라진다. 운영 표에는 앱이 지움을 적는 칸이 없다. 고치는 일을 시작하려면 「무엇을 어떤 순서로, 무엇이 되면 끝인가」가 상민님이 병합한 글로 있어야 한다.

## 2. [원칙 ②] 본질 · 원인 · 중심 · 핵심

- **본질**: 사용자가 남긴 것을 잃지 않게 하고, 잃을 수 있는 상태를 사실대로 알린다.
- **원인**: 다시 열 때 기기 백업을 서버 것으로 통째로 덮는다 · 저장 함수가 실패를 알리지 않는다 · 기기 쓰기가 서버 호출 뒤에 있다 · 코드가 전제한 운영 표의 칸 일부가 운영에 없다.
- **중심**: 계약 문서. 코드보다 먼저 세 세션이 돌려 본 약속이고, 이 지시는 그 약속을 가리킨다. 계약 뒤에 나온 사실은 계약을 고치지 않고 따로 적었다.
- **핵심**: 「했다」와 「확인했다」를 가른다. 화면 확인 · 함수 재현 · 코드 읽기 · 실서버의 확인 · 추론 · 모름을 섞지 않는다. 숨긴 보관을 「저장 안전 완료」로 쓰지 않는다.

## 3. [원칙 ③] 해결 방식

- 글틀(`reports/TASK-ES-694/text/*.md`)에 숫자를 표지로 두고, `tools/measure.cjs` 가 코드와 근거에서 읽은 값을 `tools/render-directive.cjs` 가 채워 지시함에 넣는다. 도구는 넣기 전에 지시가 기대는 사실 27가지가 맞는지 보고 틀리면 멈춘다.
- 계약과 조사 문서는 볼트가 정본이다. 지시가 근거를 저장소 안에서 가리킬 수 있게 사본을 넣었다(머리에 사본 · 정본의 자리 · 병합 시점의 판).

## 4. [원칙 ④] 재검토

- **이 지시가 승인선을 넓히지 않는가** → 운영 표를 고치는 일(조건부 쓰기 · SQL 실행) · 사진과 피드백을 서버로 올리는 일(수집 확대일 수 있다) · 보관함을 지우는 규칙 · 기능 삭제는 지시에 없고 「결심 대기」 표에 올렸다. 운영 서버 쓰기 시험은 상민님의 승인 말씀을 원문 · 물은 글 · 범위 밖과 함께 옮기고 「승인은 그 말씀이다 — 이 지시의 병합이 아니다」 「운영에 SQL 을 실행하는 일은 승인에 없다」고 적었다. 승인의 범위는 볼트의 결심 기록 글자 그대로이고 이 작업자가 넓히거나 좁히지 않았다.
- **병합 전에 한 일을 숨기지 않았는가** → 운영 서버 읽기 조사를 병합 전에 했다는 것, 상민님께 따로 여쭙지 않았다는 것, 「자기 행만」을 넘긴 조회가 11건 있었다는 것을 지시 (나) · 근거 글 · PR 본문 머리에 적었다.
- **추론을 확인처럼 적지 않았는가** → 「지움이 서버에 반영될 수 없다」 「기록 저장마다 거절 1 + 재전송 1」 「사용자 저장이 5칸으로 줄어든다」는 [추론]으로, 「uuid 아닌 id 가 든 묶음이 통째로 거절되는가」는 [모름]으로 적었다. 「SQL 이 운영에 실행되지 않았다」가 아니라 「실행되지 않은 상태로 보인다(칸의 유무로)」로 적었다.
- **P0 가 부수지 않는가** → 계약이 P0 를 「서버에 더 묻거나 더 올리지 않는다 · 화면은 그대로」로 좁혔고 조건 여섯을 지시에 그대로 옮겼다. 운영 표의 사실은 이 묶음에 닿지 않는다.
