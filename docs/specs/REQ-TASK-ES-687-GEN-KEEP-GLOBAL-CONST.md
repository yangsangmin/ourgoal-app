## 1. [원칙 ①] 문제를 정확히 파악한다 — `keepInline` 꼴이 왜 동작을 보존하지 못했나

마지막 정리(#TASK-ES-685, PR #959)는 `keepInline` 으로 서버 연결 세 문(주소 · 공개 키 선언, `define('sb', … createClient(…))`)과 그 앞의 문을 인라인에 남기고 나머지 시동 문을 `js/app/boot.js` 로 옮겼다. 법정은 「통과」였고 빌더(이 작업자)의 측정은 전부 기준과 같았다 — 게스트 시나리오 30개, 부팅 사건 364건(구역 함수 호출 · 상태 정의 · 통로 노출), 가짜 연결 366건.

**다른 담당의 독립 확인(전 구간 대조 2회차)이 요청 밖에서 차이 하나를 쟀다**(`reports/TASK-ES-687/evidence-959/` — 그 결과 파일을 글자 그대로 옮겨 둠, 도구 `tools/auth-race.cjs`). 잰 법: 임시 브라우저의 저장소에 만료 전 가짜 세션을 넣고, **진짜** 연결 라이브러리(운영 화면이 CDN 에서 받는 판 2.117.3 · 저장소에 설치된 판 2.115.0)를 심어 부팅한다. 서버와는 통신하지 않는다.

| | 수신기를 건 스크립트 | 첫 수신기보다 초기화가 먼저 끝남 | `SIGNED_IN` 전달 때 걸려 있던 수신기 | 앱 수신기가 받은 `SIGNED_IN` | 끝의 대기 세션 |
|---|---|---|--:|--:|---|
| 직전 main(3회 · CDN 판 2회) | 인라인 | 아니오 | 3 | 2 | 있음 |
| #959 머리(3회 · CDN 판 2회) | `js/app/boot.js` | **예** | **1** | **0** | **null** |
| 세션 없는 대조군 — 직전 main | 인라인 | 아니오 | (알림 없음) | 0 | null |
| 세션 없는 대조군 — #959 머리 | `js/app/boot.js` | 예 | (알림 없음) | 0 | null |

- 세션이 없으면 두 쪽 모두 앱 수신기가 `INITIAL_SESSION`(null)만 받고 끝 상태가 같다(초기화가 끝나는 자리만 다르다) — 게스트로는 차이가 드러나지 않는다.
- 직전 main 의 사건 줄: 연결 만들기 → 수신기 1 → `runAppBoot` → 수신기 2 → `SIGNED_IN` 알림(수신기 3) → 앱 수신기 둘이 받음 → …
- #959 머리의 사건 줄: 연결 만들기 → `SIGNED_IN` 알림(수신기 1 — 라이브러리 자신의 것뿐) → 초기화 끝 → 수신기 1 → `runAppBoot` → 수신기 2 → 앱 수신기는 `INITIAL_SESSION` 만 받음(앱 코드는 그 사건을 처리하지 않는다).

**왜인가**: 인라인 IIFE 는 한 스크립트라 그 안의 문은 끊김 없이 돈다. 둘로 가르면 그 경계에서 브라우저가 **밀린 약속(마이크로태스크)을 먼저 다 돌린다**. 연결 만들기는 초기화와 인증 알림을 약속으로 미뤄 두는데, 그것이 인라인 쪽에 있고 수신기 걸기가 부팅 파일 쪽에 있으니 알림이 수신기보다 먼저 나간다. 문 차례는 글자로 같았다.

**왜 빌더의 측정이 못 봤나**: 시점 탐침은 외부 통신이 막혀 연결이 `null` 이거나, 알림을 미루지 않는 **동기** 가짜 연결이었다. 시나리오는 게스트(저장된 세션 없음)뿐이었다. 「문 차례」는 쟀지만 「스크립트 경계에서 무엇이 먼저 도는가」는 재지 않았다 — 측정의 구멍이다.

끝 결과(진짜 계정으로 프로필이 뜨는지)는 독립 확인도 재지 못했다(외부 통신 차단 · 실계정 미사용 — 측정불가). 확인된 것은 「인증 사건이 누구에게 전달되는가」가 달라진다는 사실까지다. 그것만으로 「동작 보존」 주장은 성립하지 않는다.

## 2. [원칙 ②] 본질·원인·중심·핵심

- **본질**: 「같은 차례」와 「같은 동기 구간」은 다르다. 덩어리 해체가 지켜야 하는 것은 뒤의 것까지다.
- **원인**: 커밋 훅이 막는 줄(키 글자가 든 선언)과 차례에 민감한 줄(연결 만들기)을 한 묶음으로 인라인에 남겼다.
- **중심**: 두 가지를 떼어 놓는다 — 훅이 막는 것은 **선언 두 줄**뿐이다. 연결 만들기 줄에는 키 글자가 없다(이름만 있다).
- **핵심**: 인라인에 남기는 것을 **차례에 무관한 문**(부수효과도 다른 이름 읽기도 없는 문자열 상수 선언)으로 한정한다. 그러면 연결 만들기와 수신기 걸기는 다시 한 스크립트(부팅 파일) 안에 있다. 대가는 그 두 이름이 전역 이름이 되는 것이다.

## 3. [원칙 ③] 해결 방식

설정 `keepGlobalConst: { statements: [앞머리…], readers: [앞머리…], reason }`(사양 전문은 설계 5.9).

- 남길 수 있는 것: 문자열 리터럴로 초기화하는 `var` 선언(이름 하나) 한 줄. 이름은 대문자 상수 꼴(6자 이상). 한 줄을 혼자 쓰고 연달아 있어야 한다.
- `readers`: 그 이름을 읽는 상태 선언(`define` · `defineVar`). 부팅 파일로 간다.
- 결과: index.html 에 `<script>` + 선언 줄(바이트 그대로) + `</script>`+부팅 태그. 부팅 파일에 나머지 문 전부(원래 차례). `relay` 의 중계도 원래 사양대로 부팅 파일로.
- 전역 이름 검사: index.html 이 부르는 로컬 스크립트 파일 전부와 index.html 의 블록 밖 글자에서 그 이름을 찾는다(코드 · 문자열 — 주석은 세지 않는다). 하나라도 있으면 멈춘다.
- 사후 대조: 남긴 최상위 스크립트를 다시 파싱해 **문자열 상수 선언만** 있는지(문 종류 · 토큰 종류) 본다 — 호출 · 대입 · 약속 · 수신기 등록 같은 순서 민감한 문이 인라인에 남지 않는다.
- 값 글자(문자열의 내용)는 표준 출력에도 메타에도 적지 않는다(이름 · 줄 번호 · 길이만).

## 4. [원칙 ④] 재검토 (반례·부작용)

- **새 전역 이름 둘** → `window.SUPABASE_URL` · `window.SUPABASE_ANON_KEY` 가 생긴다(최상위 `var` — 지울 수 없는 속성). 저장소에서 그 이름을 읽거나 「없음」을 전제하는 화면 코드 · 시험 · 가드는 0 이다(생성기의 전역 이름 검사: 스크립트 372개에서 걸림 0 — 단위 시험 X1 · 모의). 값은 지금도 index.html 에 적힌 공개 글자다. **공식 지표는 최상위 `var` 를 세지 않아 이 변화가 지표로는 보이지 않는다**(`windowAssignments` 75 → 75).
- **선언이 앞당겨진다** → 원래는 테마 적용 호출 뒤, 이제는 부팅 파일 전체보다 앞. 문자열 상수라 값도 부수효과도 같다. 앞의 문이 그 이름을 읽으면 멈춘다(정지 S27).
- **테마 적용 호출도 부팅 파일로 간다** → 차례는 같지만 외부 파일을 받은 뒤에 돈다. 시각이 요청 하나만큼 늦을 수 있다 — 로컬에서는 잴 수 없다(측정불가). #959 의 꼴은 이 호출을 인라인에 남겼었다.
- **엄격 모드** → 인라인에 남는 것은 선언뿐이라 `"use strict"` 유무로 달라질 글자가 없다. 부팅 파일은 지금과 같은 IIFE + `"use strict"` 껍데기다.
- **같은 구멍이 또 있는가** → 이 옵션이 인라인에 남기는 문은 「약속을 만들 수 없는 문」뿐이다(사후 대조가 토큰 종류로 확인). 그리고 단위 시험 E2 가 스크립트 사이마다 밀린 약속을 비우는 조건에서 세 꼴을 맞댄다: 원래 IIFE 와 `keepGlobalConst` 꼴은 수신기가 알림을 받고, `keepInline` 꼴은 받지 못한다.
- **옵션 없이는 그대로인가** → 꾸러미 6개(성공 4 · 정지 2)를 기준 생성기와 고친 생성기로 돌려 index.html · 부팅 파일 · 표준 출력 · 메타 · 오류 글자가 같다(G1). 앞선 89건도 통과(P).
