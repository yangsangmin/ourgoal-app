## 1. [원칙 ①] 문제를 정확히 파악한다

닫힌 목록의 마지막 줄 종류 X9 는 IIFE 껍데기를 지우고 부팅 파일로 넘기는 것이다. 그 모드가 아직 없다. 그리고 지금 덩어리는 그 전제에 한참 못 미친다 — 최상위 문 399개 가운데 전제에 맞는 꼴이 아닌 것이 240개다(생성기 finalize 를 지금 main 에 돌려 센 값). 그래서 이 PR 이 낼 것은 둘이다: ① 모드 자체(꾸러미로 증명) ② 거기까지 **무엇이 남았고 무엇으로 풀리는지**의 실측 — 특히 결심이 있어야 풀리는 것과 방법이 아직 없는 것.

## 2. [원칙 ②] 본질·원인·중심·핵심

- **본질**: 마지막에 남는 문(손잡이 · 가져오기 · 호출)을 고쳐 쓰지 않고 글자 그대로 바깥 파일로 옮긴다. 자리는 같고(앞 태그 줄 끝) 동기다. 실행 글자 0 변화.
- **원인**: IIFE 가 0 이 되려면 껍데기와 `<script>` 태그까지 지워야 하는데, 그것은 「줄 삭제 + 파일 생성 + 태그 삽입」이라 기존 모드로 할 수 없다.
- **중심**: `runFinalize` — 전제를 검사하고(아니면 종류별 수를 적고 정지), 부팅 파일을 만들고, 다시 파싱해 토큰열이 이전 IIFE 와 같은지 스스로 본다.
- **핵심**: ① 「같은 순서로 부른다」를 어떻게 글자로 옮기느냐 — `window.키트.f()` 로 고쳐 부르면 값을 잡는 시점과 `this` 가 달라진다. 그래서 IIFE 를 통째로 옮긴다. ② 전제까지의 거리를 재는 일 — 무엇이 무엇을 붙잡고 있는지(돈 근처 블록이 `sb` · `state` 를, 944줄 함수가 가져오기 47개를)를 이름 참조로 따라간다.

## 3. [원칙 ③] 해결 방식 — 사양

설정 꼴 · 전제 · 하는 일 · 정지 조건 · 사후 대조의 전문은 설계 5.8 에 있다(PR 본문에도 공개). 결정한 것과 그 까닭:

| 결정 | 까닭 |
|---|---|
| 부팅 파일 = IIFE 껍데기 + 남은 문을 글자 그대로(주석·빈 줄 제외) | 가져오기를 건너뛰고 `window.키트.f()` 로 부르면 ① 값을 잡는 시점이 「머리에서 한 번」에서 「부를 때」로 ② `this` 가 `undefined` 에서 키트로 바뀐다. 문을 고치지 않으면 토큰열 대조로 「실행 글자 0 변화」를 기계로 볼 수 있다 |
| 전제의 세 종류를 좁게: 가져오기는 이름 = 속성 · 최상위에서 불림, 호출은 인자 없음 | 「구역 함수 가져오기·호출문」(3.4)이 정확히 이 꼴이다(region 이 만드는 줄). 불리지 않는 가져오기 · 쓰이지 않는 손잡이는 재철거가 먼저다 — 부팅 파일에 죽은 줄을 싣지 않는다 |
| 손잡이는 `window.X` 와 `window.X.y` | unwire X1 이 받는 손잡이 꼴과 같다(`_xp = window.OurgoalAvatarParts.xp`) |
| 부팅 파일 경로를 `js/app/boot.js` 로 고정 · `defer` 같은 칸 없음 | 설계 3.4 가 경로와 「동기 태그」를 정했다. 설정으로 바꿀 수 있으면 닫힌 목록 밖 동작이 켜진다 |
| 태그는 `<script>` 바로 앞 줄(script 태그로 끝나는 줄)의 끝에 붙인다 — 아니면 정지 | 3.4 「앞 태그 줄 끝에」. 같은 자리라 로드 순서가 그대로다(모든 세포 태그 뒤, 뒤 인라인 블록 앞) |
| 껍데기 다섯 줄에 다른 글자가 있으면 정지 | 줄째 지우므로 그 줄의 다른 글자를 함께 지우지 않게 |
| 전제 미충족이면 종류별 수를 오류 글자에 적는다 | 「얼마나 남았나」를 생성기 한 번으로 볼 수 있다(6.4 의 240개가 이 값이다) |
| 끼워 넣는 자리는 sweep 블록 다음 | 기존 줄을 한 줄도 건드리지 않는다 |

- **반론 3 「남은 것 표가 계획기 가정 위에 서 있다」** → 맞다. 「구역 이전 예정」은 #TASK-ES-643 계획기를 지금 main 에 돌린 것이고, 실제 구역 이전 PR 이 다르게 잡으면 수가 달라진다 — 표와 보고에 그렇게 적었다. 다만 결심 필요 ①~⑤ 와 방법 미정 ㉠~㉢ 은 계획과 무관하게 생성기의 정지 조건(region 의 돈 근처·결심 대기 정지 · unstate 의 선언 둘·한 줄 정지)과 시험·가드의 실측에서 나온 것이다.
- **반론 4 「깨지는 시험 17개는 과장이다」** → 그렇다 — 상한이라고 적었다. 모의본은 IIFE 글자를 합본이 읽지 않는 파일로 뺐다. 실제로는 글자가 세포로 갈 때마다 그 PR 이 시험을 돌려 붙잡힌 줄을 빼 두므로, 마지막에 남는 것은 6.4 의 결심 필요 목록이다. 모듈 가드 실패의 세 사유 가운데 둘(800줄 초과 · 신고서)은 모의본의 한계라고 가려 적었다.
- **재검증**: 앞선 묶음의 diff 모양 검사 셋(661 D0 · 657 D1 · 643 D0)이 구조적으로 거짓이 된 것은 그 시험 파일을 고치지 않고 사실대로 적었다(L110). 출력을 재는 나머지는 통과했다.
