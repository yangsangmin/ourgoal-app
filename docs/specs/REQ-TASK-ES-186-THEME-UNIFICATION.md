## 1. [원칙 ①] 문제 정확히 파악 (Problem Identification)
- **상민님 지시 원문**:
  > "아월골의 성소테마와 블랙, 화이트, 도심테마는 지금 상태가 달라.  
  > 성소테마 기준으로 똑같이 보이고 작동하게 고쳐. 블랙, 화이트, 도심테마의 색깔만 다르게."
- **현재 발생하는 문제 및 한계 (표면적 현상)**:
  - 아워골 앱에서 기본 테마인 '성소(focus-sanctuary)'를 사용할 때는 최신 V3 조형(홈 14일 활동기록·오늘의 3초 체크인 Hero Card, 목표 탭 마운틴 트레일 등반 조형, 캘린더 월/타임라인/타이머 모드, 기록 히트맵/피드/통계/보관함/리캡 세그먼트, 소통 러닝메이트 레이더)이 정상 표출됨.
  - 그러나 사용자가 설정에서 '블랙', '화이트', '도심' 테마 중 하나를 선택하면 화면 레이아웃과 조형이 성소와 완전히 딴판으로 붕괴되어 레거시 구형 레이아웃(#calGrid, #goalChipRow, #bottomNavFab 돌출 플로팅 버튼 등)이 노출되고, V3 조형 슬롯이 통째로 숨겨지며 스크립트 렌더링이 조기 중단됨.
- **표면 아래 기저 층위 분석**:
  - **1층 (미작동/단절 결함)**: `js/sanctuary-v3-engine.js` 내 `isFocusSanctuary()`가 `data-theme === 'focus-sanctuary'`만 검사하여, 블랙·화이트·도심 테마 전환 시 V3 렌더러가 아무것도 그리지 않고 조기 `return`해 버림. 또한 `ui.css` 내 핵심 조형 룰셋(약 1,800줄)이 `[data-theme="focus-sanctuary"]`로만 하드코딩 스코핑되어 있어 타 테마에서는 숨김/비활성화됨.
  - **2층 (구조/프로세스 부재)**: 테마 전환을 단순 색상 변수(`--bg`, `--card`, `--brand`)의 교체로 설계하지 않고, 특정 테마('focus-sanctuary') 전용으로 조형 클래스를 분기시키는 바람에 테마마다 UI 구조와 기능이 파편화되는 구조적 결함이 잔존함.
  - **3층 (시스템/유저 체감 괴리)**: 유저는 "어두운 방에서 눈이 부시지 않은 블랙 테마"나 "주간에 산뜻한 화이트 테마"를 기대하고 색상 테마를 바꿨을 뿐인데, 갑자기 마운틴 트레일이 사라지고 구형 화면으로 튕겨져 나가는 심각한 UX 파괴와 박탈감을 경험함.
- **사용자 상황 및 페르소나**:
  - OLED 폰 배터리를 아끼기 위해 블랙 테마를 켠 유저, 대낮 야외에서 가독성을 위해 화이트 테마를 켠 유저, 네이비 시안 야경 감성을 좋아하는 도심 테마 유저 모두가 성소와 100% 동일한 V3 조형과 기능을 고유의 아름다운 색상으로 누리고자 함.

## 2. [원칙 ②] 본질 · 원인 · 중심 · 핵심 파악 (Essence, Causes, Core & Anchor)
- **본질 축 (Essence Axis)**: `FIX` / `UX` (회귀 결함 복구 및 4대 테마 전면 무결성 일치)
- **[본질] (Essence)**: 테마란 앱의 구조나 동작을 바꾸는 것이 아니라 '오직 색채(Color Palette)만을 갈아입히는 스킨'이어야 함. 성소의 우수한 레이아웃과 20대 화면 인터랙션을 모든 테마의 기본 공통 뼈대로 삼고, 테마별로는 오직 색상 토큰만 달라지도록 정합성을 완성하는 것이 본질임.
- **[원인] (Root Causes - 기저 원인 3가지)**:
  1. **원인 1**: `js/sanctuary-v3-engine.js`의 `isFocusSanctuary()` 분기문이 성소 외 테마의 V3 렌더링을 원천 차단함.
  2. **원인 2**: `ui.css` 5386~7136행의 방대한 상하 조형 룰셋이 `[data-theme="focus-sanctuary"]`로만 묶여 있어, 타 테마에서는 `#sanctuaryGoalsView`, `#sanctuaryCalendarView`, `#sanctuaryRecordsView`, `#sanctuaryCommView`가 `display: none`으로 은폐됨.
  3. **원인 3**: `ui.css` 내 블랙, 화이트, 도심 테마 고시인성 룰이 공통 조형 뼈대 없이 개별 인라인 태그(`html[data-theme="white"] body`, `card` 등)를 파편적으로 덮어쓰고 있었음.
- **[중심] (Core Bottleneck & Anchor)**: `js/sanctuary-v3-engine.js`의 실행 게이트를 전 테마 공통으로 개방하고, `ui.css`의 조형·간격·배치 룰셋 셀렉터를 4대 테마 공통(`focus-sanctuary`, `black`, `white`, `urban-city`)으로 완전 통합하는 것.
- **[핵심] (Critical Safety & Termination)**: 성소 테마의 시각적 완성도와 동작은 100% 현행 보존하면서, 블랙·화이트·도심 테마에서 성소와 1픽셀의 어긋남 없이 동일한 레이아웃이 렌더링되고, 테마별 고유 대비와 브랜드 컬러가 완벽히 적용되는 종단간 일치성 보장.
- **체감 가설 (User Experience Hypothesis)**:
  > *"사용자가 성소, 블랙, 화이트, 도심 테마 중 어느 것을 선택하더라도, 레이아웃의 흔들림이나 기능 누락 없이 완벽히 동일한 상단바, 마운틴 트레일, 캘린더 모드, 히트맵, 소통 레이더를 체감하며, 오직 테마 고유의 매력적인 색채(에메랄드/트루블랙/순백/슬레이트시안)만을 선명하게 경험할 것이다."*
- **기존 전체 기능 영향도 분석**:
  - 계정/로그인(세션, 게스트, 소셜) 영향: 없음.
  - 홈 화면 및 스트릭 영향: 성소와 동일한 14일 활동기록 히어로 및 3초 체크인 카드가 4대 테마 전부에 완벽 동기화.
  - 기록/통계/캘린더 탭 영향: 성소 V3의 3대 캘린더 모드(월/타임라인/타이머) 및 5대 기록 세그먼트가 4대 테마 전부에 무결하게 활성화.

## 3. [원칙 ③] 효과적 · 효율적 해결방식 결정 (Effective Solutions)
- **하지 말아야 할 것 (Avoid)**:
  - 성소 테마 기존 디자인이나 스타일 토큰을 1바이트라도 훼손하는 행위 금지.
  - 테마별로 별도의 렌더러 함수를 복제하여 만드는 중복 코드 양산 금지.
  - 테마 선택 시 화면 깜빡임이나 강제 리로드 유발 금지.
- **해야 할 것 (Action)**:
  - `js/sanctuary-v3-engine.js` 내 `isFocusSanctuary()`를 4대 유효 테마(`['focus-sanctuary', 'black', 'white', 'urban-city']`) 지원으로 확장하여 전 테마 공통 실행 보장.
  - `ui.css`에서 `[data-theme="focus-sanctuary"]`로 스코핑되어 있던 조형 룰셋을 4대 테마 공통 셀렉터로 통합 확장.
  - `ui.css`의 블랙, 화이트, 도심 전용 색상 룰셋을 정돈하여 V3 조형(마운틴 트레일, 서브탭, 알약 칩, 캘린더 타임라인, 레이더 카드 등)에 테마별 고유 색상 및 배경/보더가 선명하게 적용되도록 완비.
- **왜 이 방식이어야만 하는가 (Why this approach)**:
  - V3 조형 코드를 하나로 단일화(SSOT)하고 CSS 변수 및 테마 셀렉터로 색상만 분기해야 향후 신규 기능 추가 시에도 4개 테마가 영구적으로 동기화 상태를 유지할 수 있음.

### 3-1. 스토리지 원장화 3대 명세 (헌법 제2조 제4항 준수)
- **1호 (원격 DB 스키마 명세)**: 기존 `profiles.theme` 컬럼 그대로 사용 (`focus-sanctuary`, `black`, `white`, `urban-city` 4종). 신규 컬럼 불필요.
- **2호 (스마트 스토리지 분기 설계)**: 로컬스토리지 `ourgoal_current_theme` 및 `state.profile.settings.theme` 동시 영속화 유지.
- **3호 (4대 뷰 전파 배선도)**: 테마 변경 시 `applyTheme(tid)` 호출 후 활성 탭에 맞춰 `OurgoalSanctuaryV3.render(state.activeTab)` 즉각 호출 및 4대 뷰(`renderHome`, `renderRecordsScreen`, `renderStatsScreen`, `renderCalendar`) 동시 전파.

### 3-3. 유저 데이터 100% 무손실 보존 규격 (Zero-Data-Loss Schema)
- **아바타 보존**: 기존 아바타 이미지, 페르소나 320종 설정값 100% 불변 보존.
- **목표 데이터 보존**: 기존 목표, 마일스톤 등반 내역 100% 불변 보존.

## 4. [원칙 ④] 1~3 재검토 및 보완 (Review & Edge Cases)
- **비판적 자기 검토 및 약점/한계 인정**:
  - CSS 셀렉터 확장 시 단순 치환만 수행할 경우, 화이트 테마에서 어두운 배경용 반투명 흰색(`rgba(255, 255, 255, 0.08)`) 보더나 글래스모피즘이 라이트 배경 위에서 보이지 않거나 어색할 수 있음.
  - 보완책: 화이트 테마 전용 룰셋에 마운틴 트레일, 캘린더 타임라인, 알약 칩, 서브탭, 레이더 카드의 라이트 전용 보더(`rgba(15, 23, 42, 0.12)`) 및 텍스트 대비 규칙을 명시적으로 추가 보강함.
- **기존 기능과의 충돌 가능성 검토**:
  - 레거시 뷰 슬롯(#calGrid 등)이 성소에서만 숨겨져 있었는데, 전 테마 공통으로 V3 슬롯이 표출되므로 충돌 없이 자연스럽게 모든 테마가 성소 수준으로 업그레이드됨.
- **엣지 케이스 (Edge Cases)**:
  - 테마 변경 중 빠른 탭 전환: `applyTheme` 시점에 현재 활성 탭을 안전하게 재렌더링하여 DOM 불일치 방지.
  - 고대비 모드(`data-high-contrast="true"`) 활성화 시: 테마별 고대비 색상 토큰 우선 적용 유지.

## 5. [원칙 ⑤] 해결 절차 정리 (Procedure & State Propagation)
- **구체적 실행 시퀀스**:
  1. [1단계]: `js/sanctuary-v3-engine.js` 수정 — `isFocusSanctuary()`를 4대 유효 테마 지원으로 확장하고, 테마 변경 시 실시간 테마 컬러를 반영할 수 있도록 보강.
  2. [2단계]: `index.html` 수정 — `applyTheme` 실행 시 `OurgoalSanctuaryV3.render(state.activeTab)`를 연계 호출하여 테마 변경 즉시 화면 조형이 일관되게 갱신되도록 배선.
  3. [3단계]: `ui.css` 수정 — 5386~7136행의 `[data-theme="focus-sanctuary"]` 조형 룰을 4대 테마 공통(`focus-sanctuary`, `black`, `white`, `urban-city`)으로 승격 확장하고, 테마별(블랙/화이트/도심) V3 세부 컴포넌트 컬러 팔레트 정밀 튜닝.
  4. [4단계]: `scripts/smoke-test.js`에 4대 테마 조형 및 동작 동기화 단언문 추가.
- **화면 간 상호연동 전파 규격**:
  - 테마 변경 시:
    1. 홈 화면 (`renderHome`): 상단바, 활동기록, 3초 체크인 일관 표출.
    2. 목표 탭: 마운틴 트레일 카드 및 목표 알약 칩 일관 표출.
    3. 캘린더 탭 (`renderCalendar`): 3대 캘린더 모드 일관 표출.
    4. 기록 탭 (`renderRecordsScreen`): 5대 기록 세그먼트 일관 표출.
    5. 소통 탭: 실시간 러닝메이트 레이더 일관 표출.

## 6. [원칙 ⑥] 절차 재검증 (Procedure Verification & Anti-SPOF)
- **단일 실패점 (SPOF) 점검**: CSS 셀렉터 합체 과정에서 문법 오류(쉼표 누락 등)가 발생하면 브라우저가 해당 룰 블록 전체를 무시할 수 있음. -> CSS 린트 및 각 테마별 실측 검증으로 방어.
- **가정의 타당성 검증**: 성소 룰셋을 4대 테마로 확장했을 때 화이트 테마의 명도 대비가 떨어지지 않는지 확인 필요 -> 화이트 테마 전용 오버라이드 룰셋에 V3 전용 컴포넌트(마운틴 트레일, 서브탭 등)를 명시적으로 보강함.
- **재검증 결과 도출된 절차 수정/보완사항**: 3단계 CSS 수정 시, 공통 조형 룰셋 확장과 테마별 컬러 오버라이드 룰셋을 명확히 분리하여 화이트/블랙/도심의 시인성을 100% 독립 보장하도록 절차를 세분화함.

## 8. [원칙 ⑧] 막히는 지점 예상 및 재검증 트리거 (Blockers & Re-verification Triggers)
- **잠재적 엔지니어링 블로커**: 화이트 테마에서 흰색 텍스트가 흰색 배경 위에 렌더링되는 시인성 결함 가능성.
- **사전 방어 및 우회 로직**: 화이트 테마 전용 룰셋에 `color: #0F172A !important`, `border-color: #CBD5E1 !important`를 명시적으로 적용.
- **롤백 계획 (Rollback Strategy)**: 문제 발생 시 `git checkout main`으로 즉시 무손실 복구.
- **재검증 트리거**: 테마 변경 후 마운틴 트레일이나 레이더가 보이지 않는 현상이 발견되면 [원칙 ② 중심 배선]과 [원칙 ⑤ CSS 셀렉터]로 되돌아가 셀렉터 명시도를 재검증함.
