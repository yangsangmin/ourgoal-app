"돌려보냄 무시하고 배포"라고 하셔도 AI는 아무것도 우회하지 않고 상민님이 직접 누르실 순서만 안내합니다. (제12조 제1항 5호, 제14조 제8항 2호)
15. **판정이 나올 때까지 기다림** — 무엇이: 심사를 청구한 뒤에는 court 검사가 끝날 때까지 기다렸다가 보고합니다. / 왜: 초안은 "심사를 청구한 뒤 멈춘다"여서 올리자마자 "심사 전"이라고 보고하고 끝낼 수 있었습니다. / 달라지는 점: 30분 넘게 안 끝날 때만 그 사실을 첫 줄에 적고 멈춥니다. (제12조 제1항 4호)
16. **둘째 줄 "상위 3건"의 기준** — 무엇이: 필요한 확인 수준이 높은 순(진짜 폰 > 진짜 계정끼리 > PC 화면)으로 법정이 고릅니다. / 왜: 초안에서는 AI가 적은 순서대로 앞의 셋이 나와, 가벼운 것만 앞에 보이게 짤 수 있었습니다. / 달라지는 점: 각 건에 지시 문장 앞 60자와 필요한 확인 수준의 이름이 함께 나옵니다. (제8조 제3항 6호)
17. **승인 근거** — 무엇이: 헌법 개정의 승인 근거를 PR #349 의 병합 기록으로 바꿨고, 효력도 병합된 때 생깁니다. / 왜: 초안은 AI가 버전 대장에 상민님 말씀을 옮겨 적으면 효력이 생겼습니다. / 달라지는 점: 상민님 말씀의 인용은 참고로만 붙습니다. (헌법 머리말, 제14조 제8항 3호, 버전 대장 원칙 4)
18. **법정이 고장 났을 때의 길** — 무엇이: 법정 자체가 고장 나 법정을 고치는 PR 까지 막히면, 보호 장치를 잠시 푸는 일은 상민님 결심으로만 하고 고친 직후 다시 겁니다. / 왜: 초안에는 이 경우의 길이 없었습니다. / 달라지는 점: 그때는 상민님이 GitHub 에서 직접 하실 순서를 `[손 필요]`로 안내받으십니다. (제7조 제10항 6호)
19. **"첫 네 줄" → "판정서 머리의 굵은 네 줄"** — 무엇이: 말을 바꾸고, PR 설명의 블록 3과 완료 보고의 첫 블록을 `node court/chat.js <PR번호>` 출력으로 통일했습니다. / 왜: 판정서 파일의 1~4행은 제목과 안내라서, 글자 그대로 따르면 엉뚱한 줄이 붙습니다. / 달라지는 점: 보고 맨 위에는 GitHub 기록에서 읽어 온 굵은 네 줄이 옵니다. (제6조 제1항, 제8조 제3항 2·3호)
20. **주장 칸·예비 점검·`[손 필요]`의 남은 오독 길** — 무엇이: "됐다"는 말을 주장 칸에만 쓰는 범위를 상민님께 가는 보고·PR 본문·dev_log 검증 결과 칸으로 좁혔고, 예비 점검에서는 "막힌 것"만 옮겨 적을 수 있게 했으며, `[손 필요]`는 작업마다 한 묶음으로 모으게 했습니다. / 왜: 범위가 너무 넓어 지킬 수 없었고, "예비 점검"이라는 말만 붙여 "이상 없음"을 옮겨 적을 수 있었습니다. / 달라지는 점: `[손 필요]` 요청은 작업당 한 번에 모아서 옵니다. (제7조 제10항 2·4·7호)
21. **기존 검사를 없애는 사유는 검사 제목마다** — 무엇이: 사유를 검사 제목마다 적게 했고, 글자만 보던 검사가 아닌 것은 모두 "실제로 돌리던 검사"로 봅니다. 제품 코드가 시험 결과를 흉내 내거나 시험을 중간에 끝내면 돌려보냅니다. / 왜: 한 줄 사유로 한 파일의 검사 여러 개를 덮을 수 있었습니다. / 달라지는 점: 실제로 돌리던 검사의 폐기는 상민님 결심 사항으로 올라옵니다. (제4조 제1항 1호 다목)
22. **필요한 확인 수준을 낮게 잡는 길** — 무엇이: 필요한 확인 수준은 AI가 적은 분야, 걸린 파일, 주장 문장의 낱말 가운데 가장 높은 것으로 정합니다. 글자 확인 주장이 들여다보는 파일은 걸린 파일 목록에 있어야 합니다. / 왜: 필요한 확인 수준을 정하는 값 가운데 AI가 자유로 적는 것이 있었습니다. / 달라지는 점: 저장소 맨 위의 화면 파일과 서버 경로 설정 파일도 하한 표에 들어갑니다([별표 2] — 표는 도구가 다시 만듭니다). (제7조 제10항 7호)
23. **주변 규칙 파일의 옛 정의** — 무엇이: `rules-control.json` 의 "4단계 = 이 PC main 병합 + 프리뷰" 세 곳을 "심사 청구"로, GEMINI.md·essence-gate.md 의 "금지 6"을 헌법의 "절대 금지 9대 행위"로(승인선은 헌법대로 필수 5 + 추가 3), essence-gate.md 의 "index.html +600줄 이내"를 헌법 제5조 제3항(줄 수 한도 폐지)에 맞췄습니다. / 왜: 주변 파일에 옛 정의가 남아 헌법과 어긋났습니다. / 달라지는 점: 없습니다. 다만 기계가 읽는 `rules.json` 의 줄 수 한도는 이번에 건드리지 않았습니다(아래 "아직 남은 한계" 4번).

### 나. 정상 작업을 잘못 돌려보내던 것 14건을 반영한 것

24. **검사 제목의 번호만 바뀐 것** — 무엇이: 검사를 하나 더하면서 제목의 "19/19"를 "19/20"으로 고친 것 같은 번호 변경은 "검사를 고쳤다"로 치지 않습니다. 검사가 글자만 보던 것인지 실제로 돌리던 것인지도 사라진 줄 하나가 아니라 그 검사 전체를 보고 정합니다. / 왜: 없앤 검사가 없는데 "제품을 돌리던 검사를 폐기하겠다는 신청 — 금고 변경 승인"이 상민님께 올라갔습니다(검수자 측정: 최근 제품 PR 58건 중 3건이 이 경우). / 달라지는 점: 이런 경우 승인 요청이 오지 않고 판정서에 "제목만 바뀜"으로만 나옵니다. (제4조 제1항 1호 다목)
25. **고친 코드가 기존 시험을 죽였을 때** — 무엇이: 고치기 전에는 끝까지 돌던 기존 시험이 고친 뒤에만 중간에 죽으면 "법정 도구 고장"이 아니라 "돌려보냄"입니다. 법정 도구 오류와 돌려보낼 사유가 함께 있어도 돌려보냄입니다. / 왜: 고장을 낸 쪽은 작업인데 상민님께는 "법정 도구 고장, 하실 일 없음"이 갔고, AI는 법정을 고칠 수 없어 아무도 움직일 수 없었습니다. / 달라지는 점: 판정이 돌려보냄으로 나오고, 판정서에 "작업 커밋의 제품 코드가 기존 시험 실행을 죽였다"와 그 오류의 첫 줄이 실립니다. AI가 고쳐서 다시 심사받습니다. (제7조 제10항 6호)
26. **법정 자신의 한계는 고장이 아님** — 무엇이: 표준 점검이 누를 버튼이 화면에 하나 더 생겨 헷갈리게 된 것, 법정이 인터넷을 막아서 새 외부 자료를 못 받아 생긴 오류는 "되던 기능이 고장 남"이 아니라 "확인 부족"으로 나옵니다. / 왜: 고장 난 기능이 없는데 "되던 기능이 고장 났습니다"가 상민님께 갔습니다. / 달라지는 점: 판정서에 "표준 점검 갱신 필요" 또는 "법정 환경 한계(외부 차단: 주소)"와 그 까닭이 나옵니다. 표준 점검을 고치는 일은 "금고 변경 승인"으로 따로 여쭙니다. (제7조 제10항 12호)
27. **심사 시간** — 무엇이: 법정이 주장을 심사하는 데 시간 예산(기본 25분)을 두고, 넘기면 화면에서 돌려 봐야 하는 남은 주장은 돌리지 않고 "확인 못 함(시간 부족)"으로 내립니다. GitHub 쪽 제한 시간도 45분으로 늘렸습니다. / 왜: 시험을 성실하게 많이 낸 작업일수록 제한 시간에 걸려 판정서 없이 "심사 못 함"이 될 수 있었습니다. / 달라지는 점: 판정서는 반드시 나오고, 시간 때문에 못 본 항목은 둘째 줄의 "확인 못 한 채 나가는 것"에 실립니다. (제7조 제10항 13호)
28. **올리기 전 예비 점검은 권고** — 무엇이: AI가 GitHub 에 올리기 직전에 자기 PC 에서 도는 예비 점검은 "주장 파일이 아직 없다"는 것 하나로는 막지 않고 경고만 합니다. 채점 기준을 함께 고친 것·고장 난 부품·깨진 기존 시험은 막습니다. 예비 점검이 도중에 죽으면 "막을 이유 없음"이 아니라 "끝내지 못했습니다"라고 찍습니다. / 왜: 중간 저장·초안 올리기까지 막히면 AI가 점검을 통째로 건너뛰는 버릇이 듭니다. / 달라지는 점: 없습니다. 판정은 여전히 GitHub 법정만 합니다. (제7조 제10항 14호)
29. **주장 파일은 하나** — 무엇이: 한 변경에 주장 파일은 하나만 낼 수 있습니다(둘 이상이면 돌려보냄). / 왜: 법정은 주장 파일 하나만 심사하므로, 나머지 파일에 든 주장은 심사받지 않은 채 묻힙니다. / 달라지는 점: 없습니다(막힌 길). (제7조 제10항 1호)
30. **처음부터 못 재는 것은 화면 동작 주장으로 내지 않음** — 무엇이: 법정이 처음부터 잴 수 없는 것(로그인 뒤 화면 등)은 "눌러서 확인해 달라"고 청구하지 않고 처음부터 "확인 못 함 + 정해진 사유"로 냅니다. / 왜: 한 번 시험으로 청구한 주장은 그 PR 안에서는 그 시험을 통과해야만 풀립니다(철회·종류 변경으로는 풀리지 않음 — 위 2번). / 달라지는 점: 잘못 청구한 PR 은 계속 돌려보내지므로 새 PR 로 다시 내야 합니다(아래 31번). (제8조 제3항 5호)
31. **돌려보냄 횟수를 세는 법과 새 PR** — 무엇이: 같은 커밋을 다시 심사한 것은 횟수에 넣지 않습니다. 3회가 된 뒤의 돌려보냄은 둘째 줄이 "[결심 필요] 대상"으로 바뀝니다. 앞선 심사에서 "안 됨"이던 지시는 법정이 다시 확인해 주어야만 목록에서 빠집니다. 돌려보내진 작업을 새 PR 로 다시 낼 때에는 PR 설명 첫 블록에 앞선 PR 번호를 적습니다. / 왜: 횟수는 PR 마다 따로 세어져 새 PR 에서는 0부터 다시 세어집니다. / 달라지는 점: 새 PR 의 "누적 0회"만 보지 마시고, 첫 블록에 앞선 PR 번호가 있으면 그쪽 횟수도 함께 봐 주십시오. (제12조 제1항 4호, 제6조 제1항, 제8조 제3항 2호)
32. **판정번호** — 무엇이: 판정번호를 만들 때 실행 장소, 빠른 점검인지 여부, GitHub 실행 번호를 함께 넣습니다(같은 조건으로 이 PC 에서 다시 돌리면 같은 번호가 나옵니다). / 왜: AI PC 의 예비 점검과 GitHub 의 판정이 같은 번호로 나와, 번호만으로는 어디서 나온 판정인지 구분할 수 없었습니다. / 달라지는 점: 채팅에 적힌 판정번호가 PR 화면의 판정번호와 같은지 보시면 됩니다. 헌법 조문은 바뀌지 않았습니다(도구만 고침).
33. **그 밖에 도구만 고친 것** — 무엇이: 오류 문구 속의 법정 주소 차이를 새 오류로 세던 것, 기능을 다른 파일로 옮긴 것과 주석에만 남은 파일 이름을 부품 고장으로 세던 것, 한 번의 우연한 차이를 고장으로 세던 것(이제 양쪽을 두 번씩 더 띄워 전부 같을 때만 고장), 페이지가 멈추면 법정도 같이 멈추던 것(이제 30초 뒤 "페이지가 응답하지 않음"), 법정이 도중에 죽으면 판정서가 남지 않던 것(이제 시작할 때 "심사 못 함: 실행 중 종료"를 먼저 써 둠), GitHub 쪽 글꼴 설치 실패와 재실행 충돌을 고쳤습니다. / 왜: 모두 "고장 난 것이 없는데 돌려보냄·심사 못 함이 나오는" 길이었습니다. / 달라지는 점: "되던 기능이 고장 났습니다"라는 보고가 실제 고장일 때에만 오게 하려는 것입니다. 헌법 조문은 바뀌지 않았습니다(도구만 고침).

## 아직 남은 한계

고쳤다고 해서 없어지지 않은 것을 그대로 적습니다.

1. **시험이 지시와 같은 것을 재는지는 기계가 대조하지 못합니다.** 법정은 "이 시험이 고치기 전엔 안 되고 고친 뒤엔 된다"까지만 보증합니다. 그 시험이 상민님 지시 문장과 같은 것을 재는지는 판정서의 "법정이 한 일" 문장을 사람이 읽어야 알 수 있습니다.
