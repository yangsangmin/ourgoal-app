> **제정자**: 상민님 직접 지시 및 제정

> **성격**: 아워골의 기능 추가·변경·삭제, UI·UX, 프론트엔드, 백엔드, DB, 세팅값 일체의 작업 시 최우선으로 준수해야 하는 **저장소 불변 절대 헌법**

## 제1장 총칙 및 제정 배경

### 제1조 (목적)
본 헌법은 아워골의 기능 추가, 수정, 삭제, UI/UX 개편, 백엔드 및 데이터베이스 변경 등 모든 개발 작업 시 발생해 온 고질적인 결함(되던 버튼 먹통, 껍데기 버튼 방치, 연계 기능 상호연동 불발, 유저 데이터 유실, 뷰 간 상태 불일치, AI 코드 축약)을 원천 방지하고, 사용자가 어떠한 업데이트 이후에도 신뢰와 안정성을 체감할 수 있도록 무결성 작업 표준을 확립함을 목적으로 한다.

### 제2조 (적용 범위)
아워골 코드베이스(`C:\dev\ourgoal-app`) 내 `index.html`, `ui.css`, `ui.js`, `js/`, `api/`, `docs/`, `scripts/`, `sim/`, `package.json` 및 데이터베이스 스키마와 관련된 모든 작업에 예외 없이 적용된다.

### 제3조 (5대 핵심 고질병 및 원천 근절 선언)
1. **되던 기능/버튼의 먹통 현상 (Regression)**: 기존에 정상 동작하던 요소가 새로운 코드 변경의 사이드이펙트로 파괴되는 현상을 원천 금지한다.
2. **껍데기 버튼 방치 (Shell UI / Dead Click)**: 마크업(HTML)만 만들고 실제 동작 핸들러, 비즈니스 로직, 데이터 연계가 누락된 껍데기 요소를 생성하는 행위를 엄격히 금지한다.
3. **상호연계 기능의 고립 (Disconnected Features)**: 다른 기능이나 화면과 연동되어야 하는 기능이 단독으로만 존재하여 상호작용하지 못하는 설계를 금지한다.
4. **유저 데이터의 증발/초기화 (Data Loss)**: 업데이트나 마이그레이션 후 사용자의 **아바타 설정/생성값, 목표 목록/마일스톤, 체크인/회고 기록, 화면 구성 세팅값(테마, 접힘, 필터 등)**이 단 1바이트라도 초기화되거나 유실되는 것을 절대 용납하지 않는다.
5. **화면 간 상태 불일치 (State Desynchronization)**: 한 화면에서 데이터가 변경되었음에도 연관된 다른 화면(홈, 기록, 통계, 캘린더, 프로필)에 즉시 반영되지 않아 유저에게 혼란을 주는 불일치를 금지한다.

## 제2장 작업 착수 및 2중 8원칙 프로세스

모든 작업은 반드시 **상민님의 지시 의도**를 받들어 **[문제해결 8원칙 2회 연속 적용]** 프로세스를 단계별로 거쳐야 한다.

```
[상민님 명령/지시]
       │
       ▼ (문제해결 8원칙 1회차 적용)
[1단계: 요구사항 정의서 수립 (docs/specs/REQ-*.md)]
       │
       ▼ (문제해결 8원칙 2회차 적용)
[2단계: 엔지니어링 작업계획서 수립 (docs/specs/PLAN-*.md & .Codex/작업계획서/)]
       │
       ▼ (무누락·무축약 정밀 구현)
[3단계: 배선 완결형 코드 구현 (HTML + Event + Logic + Error + Feedback)]
       │
       ▼ (5대 무결성 전수 검증 게이트)
[4단계: 전수 클릭 + 전 UX + 데이터 보존 + 상호연동 + 자동화 테스트 통과]
       │
       ▼ (직관적 6단계 상태 보고)
[5단계: 로컬 메인 병합 → 실서버 배포 → 실운영 최종 확인]
```

### 제4조 (1단계: 문제해결 8원칙 1회차 적용 → 요구사항 정의서 제작)
상민님의 지시가 접수되면 코드를 작성하기 전, 반드시 문제해결 8원칙을 적용하여 `docs/specs/REQ-<기능명>.md`를 작성해야 한다.
- **① 문제 정확히 파악**: 상민님 지시의 원문과 의도, 현재 사용자가 겪는 문제나 마찰을 기술.
- **② 본질·원인·핵심 파악**: 지시의 근본 목적, 본질 축(E1 체크인 루프, E2 기록 회고, E3 동류 소통, INFRA, FIX), 체감 가설 정의.
- **③ 해결방식 결정**: 요구사항 목록(FR-01, FR-02...), 전수 인터랙션(버튼, 클릭, 입력) 목록, 유저 데이터 스키마 보존 명세.
- **④ 1~3 재검토·보완**: 기존 기능(계정/로그인, 캘린더, 알림 등)과의 충돌 여부 및 엣지 케이스 점검.
- **⑤ 절차 정리**: 화면 간 상호연동 요구사항, 권한/세션 처리 요구사항 명세.
- **⑥ 절차 재검증**: 요구사항이 누락 없이 본질을 충족하는지 대조 검증.
- **⑦ 단계별 실행 기준**: 성공/완료 판정 기준을 측정 가능한 지표로 정의.
- **⑧ 막히는 지점 예상**: 예상되는 기술적 제약, 호환성 문제, 브라우저 환경 차이 사전 도출.

### 제5조 (2단계: 문제해결 8원칙 2회차 적용 → 작업계획서 수립)
요구사항 정의서(REQ)가 완료되면, 이를 토대로 다시 문제해결 8원칙을 적용하여 `docs/specs/PLAN-<기능명>.md` 및 `.Codex/작업계획서/<세션id 8자>.md`를 수립한다.
- **① 파악**: REQ에서 도출된 세부 요구사항 및 변경 영향 범위 전수 파악.
- **② 본질·원인·핵심**: 데이터 흐름의 중심 배선(Wire) 식별 및 전역 상태(`state`) 영향 분석.
- **③ 해결방식**: 파일별 수정 명세(Before/After), 변경 예산(Diff 줄 수 한도), 껍데기 방지 4위 1체 설계.
- **④ 재검토**: 기존 UI 레이아웃/CSS 파괴 여부, 스크립트 순서 의존성, 300줄 순증가 한도 점검.
- **⑤ 절차 정리**: 구현 상세 순서(DB 스키마/마이그레이션 → 비즈니스 로직 → DOM 렌더러 → 이벤트 리스너 → 피드백).
- **⑥ 절차 재검증**: 5대 무결성 검증 시나리오(클릭 전수 검증, 데이터 무손실 검증, UX 회귀 검증, 화면 연동 검증, npm test) 설계.
- **⑦ 단계별 실행**: 체크리스트 구성 (항목 · 소요시간 · 완료 측정 기준).
- **⑧ 막히는 지점 예상**: 전역 변수 충돌, 비동기 레이스 컨디션, 로컬 스토리지 한도 등 기술적 블로커 대책.

## 제3장 무누락·무축약 작업 이행 규범

### 제6조 (AI 코드 축약 및 생략 전면 금지)
1. AI 에이전트는 코드 작성 시 `// ... rest of code unchanged ...`, `/* 기존 코드 동일 */`, `// TODO: 나중에 구현`, `// FIXME` 등의 축약 주석을 남길 수 없다.
2. 모든 함수와 로직은 생략 없이 100% 완전한 실행 가능한 코드로 작성되어야 한다.

### 제7조 (껍데기 UI 원천 금지: 4위 1체 배선 원칙)
새로운 버튼, 링크, 입력창 등 인터랙티브 UI 요소를 추가할 때는 반드시 아래 4가지 요소가 한 세트로 완결되어야 한다:
1. **마크업(HTML)**: 고유 ID, 접근성 라벨, 올바른 시맨틱 태그.
2. **이벤트 리스너(Event Listener)**: 클릭/터치/키보드 이벤트 바인딩 (인라인 `onclick`보다 안전한 이벤트 바인딩 권장).
3. **실제 비즈니스 로직(Logic & Handler)**: 빈 함수나 `console.log`가 아닌, 실제 데이터 읽기/쓰기/변환을 수행하는 함수.
4. **사용자 피드백 및 예외 처리(Feedback & Error Handling)**: 로딩 인디케이터, 성공 토스트/UI 갱신, 실패 시 친절한 오류 안내 및 롤백.

## 제4장 5대 무결성 전수 검증 의무 (Zero-Defect Verification Suite)

모든 작업은 코드 작성을 마친 후, 아래 5대 무결성 검증을 **전수 수행**하고 모든 항목을 통과해야만 완료로 인정된다.

### 제8조 (제1검증: 전수 클릭/터치 검증 - Zero Dead-Click)
1. 신규 추가/수정된 버튼뿐만 아니라, 해당 화면 및 앱 전체의 모든 인터랙티브 요소(네비게이션 탭, 모달 열기/닫기, 액션 버튼 등)를 전수 검증한다.
2. 버튼 클릭 시 미정의 함수 호출(`is not defined`), 널 참조 에러(`Cannot read properties of null/undefined`) 등 일체의 JS 런타임 에러가 발생해서는 안 된다.
3. 클릭 시 사용자가 기대하는 상태 변화(화면 이동, 데이터 변경, 모달 표출 등)가 즉각 일어나야 한다.

### 제9조 (제2검증: 전 기능 & 전 UX 무결성 검증 - Zero UX Regression)
1. 변경된 특정 기능뿐 아니라, 아워골의 **전체 핵심 사용자 여정(Full User Journey)**이 온전히 동작해야 한다:
   - **계정 및 세션 관리**: 게스트 모드 진입, 소셜 로그인(카카오/구글), 이메일 로그인, 세션 유지, 로그아웃, 비밀번호 변경, 탈퇴 유예.
   - **온보딩 및 첫 경험**: 첫 진입 랜딩, 목표 선택, 첫 체크인.
   - **3대 본질 루프**:
     * E1 (체크인 루프): 오늘의 질문 → 답하기 → AI 피드백 → 내 위치 확인 → 잔디/스트릭 기록.
     * E2 (기록 회고): 일/주/월/년 회고, 타임라인, 통계 콕핏, 캘린더 잔디.
     * E3 (동류 소통): 공개 피드, 도움돼요 반응, 모임장 찌르기, 템플릿 복제.

### 제10조 (제3검증: 유저 데이터 100% 무손실 보존 검증 - Zero Data Loss)
업데이트 후 기존 사용자의 모든 데이터는 단 1바이트도 유실되거나 손상되지 않고 온전히 유지되어야 한다:
1. **아바타 데이터**: 사용자가 커스텀 제작한 아바타 이미지, 특징 분석값, 잔여 제작 횟수, 착용 상태.
2. **목표 데이터**: 유저가 생성한 목표 목록, 진행률, 마일스톤, 세부 할 일, D-Day.
3. **기록 데이터**: 과거 모든 날짜의 체크인 내용, AI 피드백, 스트릭 유지 일수, 태그.
4. **화면 구성 세팅값**: 유저가 설정한 테마(다크/라이트/색상), 홈 화면 카드 접힘/펼침 상태, 필터/정렬 옵션.
- **집행 방법**: `scripts/verify-integrity-gate.js` 내의 [데이터 무손실 시뮬레이터]에 실제 운영 수준의 가상 페르소나 데이터 10종을 통과시켜, 스키마 변조나 필드 누락이 발생하는지 딥 이퀄(Deep Equal)로 대조한다.

### 제11조 (제4검증: 화면 간 상호연동 및 전파 검증 - Full State Propagation)
1. 특정 화면이나 기능에서 데이터가 추가/수정/삭제되면, 그 데이터와 연관된 다른 모든 화면에 실시간으로 일관되게 반영되어야 한다.
   - 예: 체크인을 작성하면 → 홈 화면의 스트릭 및 오늘의 기록 갱신 + 기록 탭의 타임라인 즉시 추가 + 통계 탭의 주간 달성률 즉시 상승 + 캘린더 탭의 잔디 즉시 점등.
   - 예: 목표를 수정하면 → 홈 화면 목표 카드 + 목표 탭 상세 아코디언 + 통계 탭 목표 목록 동시 갱신.
2. 연계되지 않고 특정 화면에만 고립된 데이터 표시는 즉각 결함으로 판정한다.

### 제12조 (제5검증: 기술 규격 및 자동화 테스트 100% 통과)
1. `npm test`를 실행하여 기존 236개 이상의 스모크 테스트와 신규 `verify-integrity-gate.js`를 100% 통과(0개 실패)해야 한다.
2. 브라우저 콘솔 에러 0건, 네트워크 에러(Mixed Content, 404 등) 0건이어야 한다.
3. Vercel 서버리스 함수 한도(Hobby 12개) 및 인라인 스크립트 문법 유효성을 준수해야 한다.

## 제5장 직관적 6단계 상태 보고 헌법 및 배포·병합 프로세스

### 제13조 (직관적 6단계 보고 헌법 절대 준수)
모든 작업 진행 및 완료 보고 시에는 "시스템 반영", "검증 완결" 같은 모호한 개발자식 추상 언어를 전면 금지하며, 반드시 상민님이 제정한 **직관적 6단계 명칭과 물리적 구동 의미**를 명시해야 한다:
1. **[1단계: 기획·설계 상태]**: 코드는 아직 작성하지 않았고, 작업계획서와 규격(REQ/PLAN) 문서만 작성된 상태.
2. **[2단계: 내부 시뮬레이션 상태]**: 작업 브랜치에서 코드를 작성하고 단위/스모크/무결성 테스트(`npm test`) 등 내부 자동 검증만 통과한 상태 (앱 실제 구동 전).
3. **[3단계: 로컬 수동 확인 상태]**: 개발자의 로컬 환경(`localhost:8000` 또는 브라우저)에서 화면을 직접 띄워 눈으로 보고 눌러본 상태.
4. **[4단계: 로컬 메인 병합 상태]**: 작업 브랜치가 로컬 `main`(정본)에 합쳐져 로컬 앱에서 실제로 동작하는 상태 (원격 push/배포 전).
5. **[5단계: 실서버 배포 상태]**: GitHub로 `git push`되어 Vercel 실서버 배포가 완료되어 실제 웹사이트에서 유저에게 서비스되는 상태.
6. **[6단계: 실운영 최종 확인 상태]**: 실제 운영 인터넷 주소(`ourgoal-app.vercel.app`)에 직접 접속해 라이브 환경에서 실동작까지 최종 확인한 상태.

### 제14조 (배포 및 병합의 완결)
1. 작업은 단순히 브랜치에서 코드를 짜고 끝나는 것이 아니라, 상민님의 승인 또는 자동 지시에 따라 **PR 생성 → 메인 병합 → Vercel 배포 → 실운영 라이브 최종 확인(6단계)**까지 책임지고 완결해야 한다.
2. 병합 직후 반드시 충돌 마커 잔존 검사(`git grep "^<<<<<<<"`)와 `npm test`를 재실행하여 메인 브랜치의 무결성을 검증한다.

## 제6장 기계적 강제 집행 시스템 (Automated Enforcement)

### 제15조 (게이트키퍼 스크립트 강제 배선)
1. `scripts/verify-integrity-gate.js`는 본 헌법의 물리적 집행관이다.
2. 커밋 전(`pre-commit`), 푸시 전(`pre-push`), PR 오픈 시 essence-gate 및 CI 파이프라인에서 자동으로 구동되며, 5대 검증 중 단 하나라도 실패하면 커밋/푸시/병합을 물리적으로 차단한다.
3. AI 에이전트는 이 게이트 스크립트를 임의로 비활성화하거나 통과 조건을 완화할 수 없다.

### 제16조 (Tri-Sync 및 감사 기록 의무)
1. 모든 작업의 REQ, PLAN, 실행 결과는 옵시디언 볼트(`아워골_총괄 지식기반`), 노션 DB, 양비스 관제센터(`journal.jsonl`) 3곳에 Tri-Sync로 동기화되어 영구 보존된다.
2. 메타 감사자(Auditor)는 세션 종료 후 본 헌법의 준수 여부를 독립 감사하여 노션 감사 로그에 기록한다.
