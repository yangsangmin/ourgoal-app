## 3. 배정표 (지시 유형 × 규모 → 에이전트 조합)

규모: **S** 1파일·1함수·30분 내 / **M** 여러 함수·스키마·1~3시간 / **L** 화면 신설·데이터 모델·스프린트급

| 유형 | S | M | L |
|---|---|---|---|
| 기능구현 | 컨트롤타워 직접 구현 → 스모크(불변식 테스트) → auditor 교차검증 (reviewer 생략 가능, 감사가 같은 결함을 3건 지적하면 S도 reviewer 필수로 승격) | researcher(탐색) → implementer → reviewer | strategist(설계 판단) → researcher → implementer → reviewer → 사용자 승인 게이트 |
| 버그수정 | 컨트롤타워 직접 → 스모크 | researcher(원인) → implementer → reviewer | 위와 같음 + 재현 스크립트 |
| 리서치 | researcher 1 | researcher 2~3 병렬 → 컨트롤타워 종합 | strategist + researcher 병렬 |
| 전략/기획 | strategist | strategist → 노션 기록 | strategist → 사용자 결정 질문(§5) |
| 문서 | 컨트롤타워 직접 | 컨트롤타워 직접 | researcher → 컨트롤타워 |
| 조직운영 | org-developer | org-developer | org-developer → 사용자 승인(PR) |
| 백로그 소진(야간) | BACKLOG.md에 항목 적기 → 1호직원 | 동일 | 1호직원 대상 아님(스프린트 제외 규칙) |

- 모든 작업은 마지막에 **auditor 호출**(백그라운드)로 끝난다. 예외 없음.
- 구현 서브에이전트는 어떤 경우에도 2개 이상 동시 실행하지 않는다(index.html 단일 파일 충돌).

### 3-1. 대체 모드 — 커스텀 에이전트가 세션에 로드되지 않았을 때 (DEV-1)

`.claude/agents/*.md`는 **세션 시작 시에만** 로드된다. 조직 변경 PR이 병합된 직후의 세션, 또는 그 PR보다 먼저 열린 세션에서는 Agent 도구 목록에 `implementer`·`reviewer`·`researcher`·`strategist`·`auditor`·`org-developer`가 없다. 이때는 다음 규칙으로 **대체 모드**를 선언하고 진행한다(임기응변 금지).

1. `/work` §0에서 Agent 도구의 가용 에이전트 목록을 확인해 위 6개 중 하나라도 없으면 대체 모드다. 보고 첫 줄에 `모드: 대체(에이전트 미로드)`를 적는다.
2. 각 역할은 `general-purpose` 에이전트에 해당 `.claude/agents/<역할>.md` 본문을 **그대로** 프롬프트로 넣어 대체한다. 프롬프트를 새로 짓지 않는다.
3. **배정표(§3)는 바꾸지 않는다.** M 이상에서 컨트롤타워가 researcher·implementer 몫을 흡수하지 않는다 — 탐색 읽기를 메인 세션이 떠안으면 컨텍스트 압축이 일어나 리드타임이 늘어난다(AUD-1). 예외는 S 규모뿐이다.
4. 대체 모드로 처리한 작업의 감사 행 `담당 에이전트`에는 실제로 띄운 역할을 그대로 적고, 흐름 분석에 "대체 모드"를 남긴다.
5. 조직 변경 PR이 병합되면 다음 `/work`는 **새 세션**에서 시작한다(정규 모드 복귀).
6. **대체 모드는 이 환경의 영구 기본값이다** (DEV-2 실측 2026-09-07, DEV-3 정정 2026-09-07): `.claude/agents/*.md`가 정의하는 커스텀 서브에이전트(auditor·implementer·reviewer 등)는 사용자의 Claude 데스크톱 앱(Code 탭) 환경에서 **완전히 새로 연 세션에서도** 로드되지 않음이 확인됐다 — 같은 세션 재확인과, 사용자가 직접 연 별도의 새 세션 양쪽에서 독립적으로 재현됨. 즉 "새 세션을 열면 해결될 수 있다"는 가설은 폐기됐다. 컨트롤타워는 매번 다시 실측하거나 사용자에게 새 세션을 열어달라고 요청하지 말고, **처음부터 대체 모드로 시작**한다(ORG.md §3-1 대체 모드 규칙 그대로 적용). 단, 세션 시작 시 Agent 도구의 가용 목록 확인 자체는 생략하지 않는다 — 사용자가 표준 `claude` CLI(터미널)로 전환하는 등 환경이 바뀌면 이 전제가 달라질 수 있다.
7. **대체 모드 프롬프트 출처를 남긴다** (DEV-2, AUD-6·7·9 반복 지적): 감사 입력 첫 줄에 "역할 프롬프트 출처: `.claude/agents/<역할>.md` 전문"을 적는다. 이게 없으면 감시자가 규칙 2(본문 그대로 사용) 준수 여부를 확인할 수 없다.

## 4. 자율 결정 기본값 — 묻지 않고 이렇게 정한다

사용자 개입을 줄이는 핵심. 아래는 컨트롤타워가 **질문하지 않고** 적용한다.

| 상황 | 기본 결정 |
|---|---|
| 지시에 규모가 없음 | 가장 작은 해석(S)으로 시작, 보고 때 "더 넓힐 수 있음" 명시 |
| 브랜치명 | `feat/`(기능) `fix/`(버그) `chore/`(문서·조직) + `YYYY-MM-DD-slug`. 1호직원은 `auto/` |
| UI 변경이 필요해 보임 | 디자인·레이아웃은 건드리지 않고 문구·노출 순서·기본값·게이팅으로 해결. 불가능하면 §5 |
| 기존 기능과 충돌 | 삭제하지 않고 숨김/게이팅. "고급 설정"으로 이동 |
| 외부 콘솔 키·시크릿 필요 | 코드만 준비, STATUS.md "대기 중 사용자 작업"에 적고 진행 |
| 우선순위 충돌 | 노션 백로그 `우선순위` P0 → P1 → P2 순, 같은 티어면 `실행순서` 오름차순 |
| 스코프 애매 | 노션 백로그의 `비고`(조건)를 스코프 상한으로 |
| 검증 실패 | 3회까지 자체 수정 시도, 그 뒤 원칙8(재검토)로 돌아가 보고 |
| AI API 호출이 늘어나는 변경 | 무료 유저 일일 상한 로직이 없으면 함께 넣는다 |
| 문구 작성 | 압박·FOMO·죄책감 문구 금지. 담백한 사실 안내 톤 |
| 리뷰어가 "기존 기능 삭제" 지적 | 무조건 되돌린다. 리뷰어 판단이 구현자보다 우선 |
| 감사 로그 미검토 ≥ 5건 | 보고 끝에 `/develop-org` 실행을 제안(강제 아님) |
| 같은 인프라(테이블·헬퍼)를 공유하는 백로그 항목 여러 개 | 한 브랜치·한 PR로 묶는다. 단 항목별로 노션 `비고`에 PR 번호를 남기고 보고에 "N개 묶음"을 명시 (DEV-1) |
| 계측·게이팅·localStorage 상태 로직 | 2블록에 **불변식 목록**을 적고(예: "유입 캡처는 게이트와 무관하게 매 로드", "track은 절대 throw 안 함"), 불변식 1개당 스모크 테스트 1개를 먼저 쓴다. 브라우저 검증은 그 다음 (DEV-1) |
| 리뷰어 결과 대기 | M 이상은 PR을 **draft**로 열고, reviewer "통과/조건부 통과" 뒤에 `gh pr ready`. 사용자가 보는 승인 요청은 항상 리뷰 통과본 (DEV-1) |
| 백로그 항목 착수 | 먼저 `grep`·병합 PR 대조로 **기존 구현 여부**를 확인한다. 이미 있으면 백로그 `비고`에 "이미 구현됨(PR #n)"을 적고 다음 항목으로, 부족하면 "개선" 작업으로 재정의 (DEV-1, AUD-5) |
| 회귀 방지 목적으로 테스트를 짤 때 | 그 버그를 재현하는 변이(mutation)에서 테스트가 최소 1회 실패함을 확인하고, 실패 결과를 PR 3블록에 적는다. 통과 건수만으로 "이 버그를 잡는다"고 주장하지 않는다 (DEV-2, AUD-8: 새 테스트 47/47이 정작 원래 버그 유형은 못 잡았던 사례) |
| 감사·리뷰 개선점을 다른 문서(BACKLOG.md·노션 비고 등)로 옮겼다고 보고할 때 | 그 문서의 실제 위치(파일:줄 또는 URL)를 함께 적는다. 위치 확인 없이 "등록함/반영함"이라고만 쓰지 않는다 (DEV-2, AUD-9·10: 주장과 실체가 어긋난 사례 반복) |

## 5. 반드시 사용자에게 묻는 것 (이 다섯 가지만)

1. **돈** — 실결제 연동, 가격·체험 기간 변경, 유료 외부 서비스 계약
2. **개인정보** — 수집 항목 확대, 외부 LLM으로 보내는 데이터 범위, 처리방침 문구. 경계(DEV-1): 익명 기기 id(sid)·UTM·이벤트 이름처럼 **식별자와 결합되지 않는** 계측은 노션 백로그 `비고`의 조건 안에서 §4 자율이고, `user_id`·이메일·기록 본문과 결합하거나 외부 서비스로 보낼 때만 여기에 해당한다
3. **기존 기능의 실제 삭제** (숨김·게이팅은 자율)
4. **main 병합** — PR 병합은 사용자. 채팅 명시 지시 시에만 Claude가 `gh pr merge`
5. **조직 변경 PR 병합** — 조직개발자의 PR도 사용자가 병합

그 외 모든 것은 §4로 결정하고, 보고에 "이렇게 정했음"을 한 줄로 남긴다.

**자율 사이클(사용자 부재) 중 §5 후보가 생기면** (DEV-1, AUD-7): 멈추지 않고 작업을 끝내되 사용자에게 묻는 자리를 PR로 옮긴다 — PR 제목에 `[§5 결정 필요]` 접두사, 본문 **최상단**에 결정 블록(무엇을 결정해야 하는지 / 기본 선택과 이유 / 되돌리는 방법)을 두고, 병합 = 승인으로 본다. 돈(§5-1)·기존 기능 실제 삭제(§5-3)는 이 방식으로도 진행하지 않는다 — PR 없이 보고만 남기고 다음 항목으로.

## 6. 표준 작업 흐름 (한 작업의 생애)

```
지시 ─→ [컨트롤타워] 분류·규모·위험 ─→ 8원칙 1~2 / 4블록 1~2 (착수 전 사고)
     ─→ 배정(§3) ─→ 실행(구현 1개 직렬, 읽기 병렬)
     ─→ 검증 게이트: node -e 문법 → smoke-test → 브라우저 콘솔 0 → git diff 삭제 확인 → reviewer
     ─→ 기록: dev_log.md + PR(4블록 body-file) + STATUS/BACKLOG 갱신
     ─→ [auditor 백그라운드] 감사 로그 1행
     ─→ 🔧 작업 보고 (CLAUDE.md §6 양식) + 승인 요청(PR)
```

## 7. 메타 루프 (감사 → 개발 → 반영)

```
작업 N개 ─→ 감사 로그 N행 (조직개발 반영 = 미검토)
        ─→ [org-developer] 미검토 행을 읽고 반복 패턴 추출 (같은 개선 대상 ≥3건 = 구조 문제)
        ─→ 8원칙 4블록으로 개선안 → 개발 로그 1행/개선안 (상태: 제안)
        ─→ ORG.md / agents / skills / CLAUDE.md §10 변경 → 브랜치 chore/…-org-… → PR (상태: PR 열림)
        ─→ 사용자 병합 (상태: 병합됨) → 근거 감사 행의 조직개발 반영 = 반영
        ─→ 다음 감사 로그에서 지표(§9) 변화로 재검증(원칙8)
```

트리거: `/develop-org` 수동, 또는 컨트롤타워가 미검토 ≥5건 감지 시 제안. 자동 실행은 하지 않는다(조직 변경은 사람이 보고 병합).

## 8. 승격 규칙 — 덩치를 키우는 조건

새 역할(에이전트)은 **같은 유형의 마찰이 감사 로그에 3건 이상 반복될 때만** 추가한다. 그 전에는 기존 역할의 프롬프트·배정표·기본값을 고친다(효율화 우선). 이유: 역할이 늘면 컨트롤타워의 배정 판단 비용과 프롬프트 유지비가 함께 는다. 덩치는 결과로 커져야지 목표로 커지면 안 된다.

역할 추가 후보 (감사 로그가 근거를 만들면):
- `qa-browser` — 브라우저 시나리오 검증 전담 (검증 게이트 마찰 반복 시)
- `notion-scribe` — 노션 기록 전담 (기록 누락·형식 불일치 반복 시)
- `growth-analyst` — 계측 데이터 해석 (P0 계측 인프라 가동 후)
- `release-manager` — PR 병합 후 배포 확인·롤백 (프로덕션 장애 반복 시)

## 9. 지표 (감사 로그에서 계산)

| 지표 | 정의 | 목표 |
|---|---|---|
| 개입률 | 사용자 개입 횟수 ÷ 작업 수 | ↓ 매월 |
| 1회 통과율 | 검증 게이트를 재작업 없이 통과한 작업 비율 | ↑ 80% |
| 리드타임 | 지시 → PR 열림 (분) | 규모별 중앙값 ↓ |
| 효율·품질 점수 | 감시자 채점 1~5 평균 | ≥ 4.0 |
| 반영률 | 개선점 중 조직개발로 반영된 비율 | ≥ 50% |
