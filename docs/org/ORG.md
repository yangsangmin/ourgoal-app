## 3. 배정표 (지시 유형 × 규모 → 에이전트 조합)

규모: **S** 1파일·1함수·30분 내 / **M** 여러 함수·스키마·1~3시간 / **L** 화면 신설·데이터 모델·스프린트급

| 유형 | S | M | L |
|---|---|---|---|
| 기능구현 | 컨트롤타워 직접 구현 → 스모크(불변식 테스트) → auditor 교차검증 (reviewer 생략 가능, 감사가 같은 결함을 3건 지적하면 S도 reviewer 필수로 승격) | researcher(탐색) → implementer → reviewer | strategist(설계 판단) → researcher → implementer → reviewer → 사용자 승인 게이트 |
| 버그수정 | 컨트롤타워 직접 → 스모크 | researcher(원인) → implementer → reviewer | 위와 같음 + 재현 스크립트 |
| 리서치 | researcher 1 | researcher 2~3 병렬 → 컨트롤타워 종합 | strategist + researcher 병렬 |
| 전략/기획 | strategist | strategist → 노션 기록 | strategist → 사용자 결정 질문(§5) |
| 문서 | 컨트롤타워 직접 | 컨트롤타워 직접 | researcher → 컨트롤타워 |
| 조직운영 | org-developer | org-developer | org-developer → 사용자 승인(PR) |
| 백로그 소진(야간) | BACKLOG.md에 항목 적기 → 1호직원 | 동일 | 1호직원 대상 아님(스프린트 제외 규칙) |

- 모든 작업은 마지막에 **auditor 호출**(백그라운드)로 끝난다. 예외 없음.
- 구현 서브에이전트는 어떤 경우에도 2개 이상 동시 실행하지 않는다(index.html 단일 파일 충돌).

### 3-1. 대체 모드 — 커스텀 에이전트가 세션에 로드되지 않았을 때 (DEV-1)

`.claude/agents/*.md`는 **세션 시작 시에만** 로드된다. 조직 변경 PR이 병합된 직후의 세션, 또는 그 PR보다 먼저 열린 세션에서는 Agent 도구 목록에 `implementer`·`reviewer`·`researcher`·`strategist`·`auditor`·`org-developer`가 없다. 이때는 다음 규칙으로 **대체 모드**를 선언하고 진행한다(임기응변 금지).

1. `/work` §0에서 Agent 도구의 가용 에이전트 목록을 확인해 위 6개 중 하나라도 없으면 대체 모드다. 보고 첫 줄에 `모드: 대체(에이전트 미로드)`를 적는다.
2. 각 역할은 `general-purpose` 에이전트에 해당 `.claude/agents/<역할>.md` 본문을 **그대로** 프롬프트로 넣어 대체한다. 프롬프트를 새로 짓지 않는다.
3. **배정표(§3)는 바꾸지 않는다.** M 이상에서 컨트롤타워가 researcher·implementer 몫을 흡수하지 않는다 — 탐색 읽기를 메인 세션이 떠안으면 컨텍스트 압축이 일어나 리드타임이 늘어난다(AUD-1). 예외는 S 규모뿐이다.
4. 대체 모드로 처리한 작업의 감사 행 `담당 에이전트`에는 실제로 띄운 역할을 그대로 적고, 흐름 분석에 "대체 모드"를 남긴다.
5. 조직 변경 PR이 병합되면 다음 `/work`는 **새 세션**에서 시작한다(정규 모드 복귀).
6. **원인·해결책 확정** (DEV-2 실측 2026-09-07, DEV-3 정정, DEV-4 확정): 커스텀 서브에이전트는 **Claude 데스크톱 앱(Code 탭)에서는 로드되지 않지만, 터미널 표준 `claude` CLI에서는 6개(`implementer`·`reviewer`·`researcher`·`strategist`·`auditor`·`org-developer`) 전부 정상 로드됨**이 실측 확인됐다(2026-09-07, `claude -p`로 직접 조회). 즉 문제는 프로젝트 파일이 아니라 **하네스(데스크톱 앱 vs 터미널)** 차이였다. 실제 서브에이전트 격리·병렬이 필요한 무거운 작업(2시간 자율 사이클, 무거운 `/work`, org-dev 사이클)은 **터미널에서 `claude` 실행을 우선 권장**한다. 데스크톱 앱에서 계속할 경우엔 대체 모드(위 1~5)를 그대로 쓴다 — 대체 모드도 이미 실제 PR·감사를 만들어낸 검증된 경로다. 세션 시작 시 Agent 가용 목록 확인은 하네스가 다를 수 있으므로 매번 계속한다.
7. **대체 모드 프롬프트 출처를 남긴다** (DEV-2, AUD-6·7·9 반복 지적): 감사 입력 첫 줄에 "역할 프롬프트 출처: `.claude/agents/<역할>.md` 전문"을 적는다. 이게 없으면 감시자가 규칙 2(본문 그대로 사용) 준수 여부를 확인할 수 없다.

## 4. 자율 결정 기본값 — 묻지 않고 이렇게 정한다

사용자 개입을 줄이는 핵심. 아래는 컨트롤타워가 **질문하지 않고** 적용한다.

| 상황 | 기본 결정 |
|---|---|
| 지시에 규모가 없음 | 가장 작은 해석(S)으로 시작, 보고 때 "더 넓힐 수 있음" 명시 |
| 브랜치명 | `feat/`(기능) `fix/`(버그) `chore/`(문서·조직) + `YYYY-MM-DD-slug`. 1호직원은 `auto/` |
| UI 변경이 필요해 보임 | 디자인·레이아웃은 건드리지 않고 문구·노출 순서·기본값·게이팅으로 해결. 불가능하면 §5 |
| 기존 기능과 충돌 | 삭제하지 않고 숨김/게이팅. "고급 설정"으로 이동 |
| 외부 콘솔 키·시크릿 필요 | 코드만 준비, STATUS.md "대기 중 사용자 작업"에 적고 진행 |
| 우선순위 충돌 | 노션 백로그 `우선순위` P0 → P1 → P2 순, 같은 티어면 `실행순서` 오름차순 |
| 스코프 애매 | 노션 백로그의 `비고`(조건)를 스코프 상한으로 |
| 검증 실패 | 3회까지 자체 수정 시도, 그 뒤 원칙8(재검토)로 돌아가 보고 |
| AI API 호출이 늘어나는 변경 | 무료 유저 일일 상한 로직이 없으면 함께 넣는다 |
| 문구 작성 | 압박·FOMO·죄책감 문구 금지. 담백한 사실 안내 톤 |
| 리뷰어가 "기존 기능 삭제" 지적 | 무조건 되돌린다. 리뷰어 판단이 구현자보다 우선 |
| 감사 로그 미검토 ≥ 5건 | 보고 끝에 `/develop-org` 실행을 제안(강제 아님) |
| 같은 인프라(테이블·헬퍼)를 공유하는 백로그 항목 여러 개 | 한 브랜치·한 PR로 묶는다. 단 항목별로 노션 `비고`에 PR 번호를 남기고 보고에 "N개 묶음"을 명시 (DEV-1) |
| 계측·게이팅·localStorage 상태 로직 | 2블록에 **불변식 목록**을 적고(예: "유입 캡처는 게이트와 무관하게 매 로드", "track은 절대 throw 안 함"), 불변식 1개당 스모크 테스트 1개를 먼저 쓴다. 브라우저 검증은 그 다음 (DEV-1) |
| 리뷰어 결과 대기 | M 이상은 PR을 **draft**로 열고, reviewer "통과/조건부 통과" 뒤에 `gh pr ready`. 사용자가 보는 승인 요청은 항상 리뷰 통과본 (DEV-1) |
| 백로그 항목 착수 | 먼저 `grep`·병합 PR 대조로 **기존 구현 여부**를 확인한다. 이미 있으면 백로그 `비고`에 "이미 구현됨(PR #n)"을 적고 다음 항목으로, 부족하면 "개선" 작업으로 재정의 (DEV-1, AUD-5) |
| 회귀 방지 목적으로 테스트를 짤 때 | 그 버그를 재현하는 변이(mutation)에서 테스트가 최소 1회 실패함을 확인하고, 실패 결과를 PR 3블록에 적는다. 통과 건수만으로 "이 버그를 잡는다"고 주장하지 않는다 (DEV-2, AUD-8: 새 테스트 47/47이 정작 원래 버그 유형은 못 잡았던 사례) |
| 감사·리뷰 개선점을 다른 문서(BACKLOG.md·노션 비고 등)로 옮겼다고 보고할 때 | 그 문서의 실제 위치(파일:줄 또는 URL)를 함께 적는다. 위치 확인 없이 "등록함/반영함"이라고만 쓰지 않는다 (DEV-2, AUD-9·10: 주장과 실체가 어긋난 사례 반복) |
| 잴 수단이 없는 항목의 상태 | `미검증`으로 둔다. **`진행중`으로 매핑하지 않는다** — 미검증은 "일이 진행 중"이 아니라 "잴 수단이 없다"는 뜻이고, 진행중으로 칠하면 아무도 안 움직이는 항목이 움직이는 것처럼 보인다 (DEV-9) |
| 임계값·기준을 정할 때 | 표본 수와 잠정 여부를 값과 **함께** 적는다(예: "인접 평균 28 이하(잠정, 표본 2)"). 표본이 부족하면 게이트로 승격하지 않는다 (DEV-9) |
| 집계에 안 잡히는 행이 생겼을 때 | 상태를 비우지 말고 `분류불가`로 세워 화면에 노출한다. 빈 값은 0으로 세어져 유령 옵션과 결과가 같다 — 조용한 손실을 눈에 보이는 미결로 바꾼다 (DEV-9) |
| 노션·파일에 한글이나 경로를 쓸 때 | **§10 문자열 무결성**을 적용한다 — 옮겨 적지 말고 있는 자리에서 읽는다. 옮겨 적어야 하면 리터럴로 쓰고, 쓴 직후 왕복 대조하고, select·status 값은 쓰기 전 허용 목록과 대조한다 (DEV-6) |

## 5. 승인선 — 반드시 사용자에게 묻는 것 (DEV-7, 2026-09-08 사용자 확정)

> **원리: 되돌릴 수 있으면 하고, 되돌릴 수 없거나 새 행위자를 만들면 묻는다.**

이 원리가 아래 목록의 근거다. 목록에 없는 상황을 만나면 목록을 유추하지 말고 **원리로 판정**한다 — "되돌리는 방법을 한 문장으로 댈 수 있는가", "이 행위가 나 말고 다른 행위자를 만들어내는가" 두 가지를 묻는다.

### 자율 (묻지 않는다)
- **읽기·조사·기록** — 코드·노션·로그 읽기, 리서치, 감사·개발 로그 쓰기.
- **코드 수정 · PR 생성** — 브랜치 위에서 하는 일은 전부 되돌릴 수 있다.
- **main 병합** — 2026-09-08 사용자 확정("니가 병합"). Claude가 `gh pr merge`로 직접 병합하고, 직후 충돌 마커 `grep -rn "^<<<<<<<" .`과 스모크 테스트로 main 상태를 검증해 보고한다(CLAUDE.md 8-B). 되돌리는 방법: revert PR.

### 묻는다

4. **조직 변경 PR 병합** — 조직개발자의 PR은 병합 자율의 **예외로 남긴다.** 이유: 조직 변경은 승인선 자체를 포함해 "무엇을 물어야 하는가"를 바꾸는 자기수정이다. 자기수정을 자기가 승인하면 되돌릴 수 있는지 판단하는 기준 자체가 흔들린다. git으로 되돌릴 수 있다는 사실은 이 예외를 무효화하지 않는다 — 되돌릴 대상이 되돌림을 판정하는 규칙이기 때문이다.
5. **세션 소환** — 새 세션·에이전트를 띄우는 것은 사용자가 말로 승인한다. 원리의 "새 행위자를 만들면 묻는다"에 해당한다. 소환된 세션은 이 대화를 보지 못한 채 독립적으로 움직이므로, 띄우는 순간 되돌리기가 더 이상 내 손에 없다. 서브에이전트(§2 실행층)는 컨트롤타워가 회수·중단할 수 있으므로 여기 해당하지 않는다.
6. **무언가를 바꾸는 세션을 띄울 때** — 5에 더해, **무엇을 바꿀지 먼저 보여준 뒤** 승인을 받는다. "세션을 띄워도 되나"와 "그 세션이 무엇을 바꿀 것인가"는 다른 질문이고, 후자가 실제 위험이다.
7. **되돌릴 수 없는 것** — 외부 발행(공개 배포·발송·게시), 데이터·페이지·브랜치의 영구 삭제. 되돌리는 방법을 한 문장으로 댈 수 없으면 여기에 해당한다.

그 외 모든 것은 §4로 결정하고, 보고에 "이렇게 정했음"을 한 줄로 남긴다.

**자율 사이클(사용자 부재) 중 §5 후보가 생기면** (DEV-1, AUD-7): 멈추지 않고 작업을 끝내되 사용자에게 묻는 자리를 PR로 옮긴다 — PR 제목에 `[§5 결정 필요]` 접두사, 본문 **최상단**에 결정 블록(무엇을 결정해야 하는지 / 기본 선택과 이유 / 되돌리는 방법)을 두고, 병합 = 승인으로 본다. 돈(§5-1)·기존 기능 실제 삭제(§5-3)는 이 방식으로도 진행하지 않는다 — PR 없이 보고만 남기고 다음 항목으로.

## 7. 메타 루프 (감사 → 개발 → 반영) — 두 층으로 분리 (DEV-5)

개선점은 성격에 따라 반영 층이 다르다. **역할·권한·검증 게이트 등 "구조"를 바꾸는 것**과 **절차·체크리스트 등 "작업 방식"을 바꾸는 것**을 같은 승인 절차로 묶으면, 절차 개선까지 매번 PR·병합을 거쳐야 해서 학습 속도가 사용자 가용성에 묶인다(이 문제 자체가 DEV-2~4에서 조직 PR 5개가 쌓이며 실측됨).

## 10. 문자열 무결성 (DEV-6) — 모든 기록 쓰기에 적용

> **상위 규칙: 문자열을 옮겨 적지 않는다. 있는 자리에서 읽는다.**

아래 3원칙은 전부 이 한 줄에서 나온다 — **옮겨 적는 순간이 틀릴 자리다.** 그러니 가장 확실한 방어는 옮겨 적는 일 자체를 없애는 것이고, 옮겨 적어야만 할 때 3원칙이 적용된다.

실증(2026-09-08):
- **지킨 사례** — hp-04의 i2v 드라이버는 장문의 중국어 네거티브 프롬프트를 코드에 옮겨 적지 않고 워크플로 JSON에서 매번 읽는다. 커맨드센터 `lib/reqanchor.js`는 요구사항 정의서의 `REQ-STATUS-JSON` 앵커를 파싱만 하고 어떤 문자열도 재조립하지 않는다.
- **어긴 사례(가장 위험)** — `lib/dispatch.js`가 값을 파일로 옮겨 적으면서 인코딩을 주지 않아 cp949로 저장했고, **깨진 프롬프트가 소환되는 세션에 그대로 전달됐다.** 화면은 노션에서 값을 받아 멀쩡해 보여 눈으로는 안 잡혔다.

마지막 사례의 성질을 기억한다 — **실패가 실패처럼 보이지 않고, 다른 행위자에게 전파된다.** 손상된 문자열은 예외를 던지지 않고 조용히 하류로 흘러가며, 그 하류에서는 원본과 대조할 방법이 이미 없다. 그래서 대조는 **쓴 그 자리에서** 해야 한다.

노션·파일에 한글이나 경로를 쓸 때 값이 **조용히** 손상된다. 화면에는 멀쩡해 보이므로 눈으로는 잡히지 않는다. 2026-09-08 하루에만 네 세션에서 확인됐다: 한글 코드포인트 변형(도넛→도넘, 컨트롤타워→컴트롤타워, 조끼→조낄), 백슬래시 소실(`C:\dev\command-center` → `C:devcommand-center`), Windows에서 인코딩 미지정 파일 쓰기가 cp949로 저장돼 깨진 프롬프트가 다른 세션에 그대로 전달된 사고(`lib/dispatch.js`).

**원인은 전송이 아니라 조립이다.** 같은 페이지·같은 세션·같은 MCP 도구로 A/B 실험한 결과, 한글 리터럴로 쓴 줄은 겹받침 포함 한 글자도 틀리지 않았고 `\uXXXX` 이스케이프로 조립한 줄만 깨졌다. 모델이 코드포인트를 조립할 때 틀린다. 한 호출의 코드포인트 수가 손상률을 올리는 증폭기 역할을 한다(단건 0건 / 18건 배치 8건 / 20건 배치 2건).

**규칙 기반 탐지로는 끝나지 않는다.** 교정 자체가 또 깨진다(곱선→공선→곡선, 세 번째에야 성공). 새 손상형이 나올 때마다 금지 목록이 뒤따라갈 뿐이다. 그래서 아래 2번(왕복 대조)이 핵심이고, 1·3번은 발생을 줄이는 보조다.

1. **리터럴로 쓴다** — 한글·경로를 `\uXXXX` 이스케이프로 조립하지 않는다. 파일 쓰기는 인코딩을 반드시 명시한다(`fs.writeFileSync(path, str, 'utf8')`). Windows에서 인코딩을 생략하면 cp949로 저장된다.
2. **쓴 직후 왕복 대조한다(필수)** — 쓰기 응답 또는 재조회 결과를 보낸 문자열과 대조한다. 원인 종류를 가리지 않고 100% 잡히는 유일한 방법이다. 불일치가 있으면 그 자리에서 고치고, **고친 결과를 다시 대조한다**(교정이 새 손상을 만든 사례가 있다). 대조하지 않았으면 "기록함"이라고 보고하지 않는다.
3. **select·status 값은 쓰기 전 허용 목록과 대조한다** — 노션은 없는 옵션명을 받으면 에러 없이 새 옵션을 만든다. `완료`가 `완로`가 되면 그 행은 어느 집계에도 안 잡히고 진행률만 조용히 낮아진다. 마찬가지로 옵션이 막혔다고 값을 비워 두면 유령 옵션과 결과가 같다 — 안 보이는 것이 0으로 세어진다. 값을 비우지 말고 실패를 보고한다.
