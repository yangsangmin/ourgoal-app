# 이 폴더의 옛 작업계획서를 본뜨지 말 것

이 폴더에는 세션별 작업계획서가 쌓여 있다. **2026-09-21 이전에 쓴 계획서는 기록으로만 남긴 것이며, 새 계획서의 본보기가 아니다.**

## 폐지된 것 (2026-09-21, 헌법 v2026.09.21 판정 분리)

| 옛 계획서에 적힌 것 | 지금 |
| :-- | :-- |
| `[4단계: 로컬 메인 병합 및 5A 프리뷰 배포]` — 작업을 이 PC 의 main 에 병합하고 프리뷰를 올리는 것이 마감선 | **폐지.** 이 PC 의 main 에 작업을 병합하지 않는다(헌법 제9조 제1항). |
| 완료 기준 `ALL PASS`·`N/N 통과`·"스모크 테스트 전부 통과" | **폐지.** 작업자가 돌린 검사의 출력은 증거가 아니다. "됐다"는 판정은 법정만 낸다(헌법 제7조 제10항). |
| 작업자가 찍은 화면 캡처를 완료 증거로 첨부 | **폐지.** 화면은 법정이 직접 찍은 것만 증거다. |

## 지금의 4단계 = 심사 청구

**4단계는 "심사 청구"다: 작업 브랜치를 올려 초안 PR 을 만들고, GitHub 에서 도는 법정(`court` 검사)의 판정을 받는다.**

1. 작업 브랜치를 GitHub 에 올리고 초안 PR 을 만든다. 주장 파일(`reports/<작업번호>/claims.json`)을 같은 PR 에 넣는다.
2. GitHub 의 `court` 검사가 끝날 때까지 기다린다.
3. `node court/chat.js <PR번호>` 의 출력을 보고의 첫 블록으로 그대로 붙인다(종료코드 0 = 판정을 옮겼다, 3 = 아직 판정이 없다).
4. 돌려보냄이면 고쳐서 다시 심사받는다. 한 PR 에서 돌려보냄이 3회 쌓이면 멈추고 상민님께 보고한다(법정 댓글의 넷째 줄에 "이 PR 돌려보냄 누적 N회"가 찍힌다).
5. 돌려보내진 작업을 새 PR 로 다시 낼 때는 PR 본문(블록 1)에 앞선 PR 번호를 적는다(누적 횟수는 PR 단위로 세어진다).

프리뷰(5A)는 PR 을 올리면 Vercel 이 자동으로 만든다. 작업자가 따로 배포하지 않는다.

알아 둘 것:

- 푸시 전 예비 점검은 주장 파일이 없어도 경고만 하고 올려 준다(중간 저장용). 그래도 심사를 청구하기 전에는 주장 파일을 넣는다 — GitHub 의 법정은 주장 없는 제품 변경을 돌려보낸다.
- 한 변경에 주장 파일은 하나다. 법정이 잴 수 없는 것(로그인 뒤 화면·파일 첨부 등)은 처음부터 화면 동작 주장으로 내지 않는다 — 한번 낸 화면 동작 주장은 철회해도, 낮춰도 법정이 옛 시험을 다시 돌린다.
- PR 의 법정 댓글은 법정만 고친다. 법정이 아닌 계정이 고친 흔적이 있으면 그 PR 은 `[결심 필요]` 대상이 되고 그 PR 에서는 통과가 나오지 않는다.

## 새 계획서의 완료 기준은 이렇게 쓴다

- 쓰지 않는다: "ALL PASS", "로컬 main 병합 완료", "스크린샷 확보".
- 쓴다: "초안 PR 을 올리고 법정 판정을 받았다(판정번호 기재)", "확인 못 함으로 남은 지시는 목록과 `[손 필요]` 안내를 붙였다".
- 내 PC 에서 돌린 `npm run court`·푸시 전 예비 점검의 "막을 이유 없음"은 판정이 아니다. 완료 기준에도 보고에도 옮겨 적지 않는다.

자세한 것: `court/README.md`(법정 한 장 설명서), `docs/rules/OURGOAL_ABSOLUTE_INTEGRITY_RULES.md` 제7조 제10항·제8조 제3항·제9조·제12조.
