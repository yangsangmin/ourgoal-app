## 5. 대기줄(OfflineSyncManager)의 실제 범위
파일은 `js/core/virtual-user-helpers.js` 136~211행이다.

- **넣는 곳은 한 군데다**: 홈 오늘 기록 저장에서 `navigator.onLine` 이 false 일 때만 넣는다(`checkin-capture.js` 129~131행). 기록 창 · 전문 템플릿 · 타이머 · 목표 · 일정은 넣지 않는다.
- **온라인인데 500 · 401 · 응답 없음일 때는 쓰이지 않는다**(함수 재현 A · F: 대기줄 없음).
- **비우는 때는 `online` 사건뿐이다**(`js/core/app-enter.js` 148~153행). 앱을 켤 때는 처리하지 않는다. 오프라인에서 저장하고 끈 뒤 온라인에서 켜면 다음 오프라인→온라인 전환까지 남는다(코드로 읽음).
- **실패해도 비운다**: `syncOnline` 은 `saveProfile` 이 끝나면 비우는데, `saveProfile` 이 실패를 던지지 않는다. 서버가 500 이어도 `{"synced":1,"failed":0}` 을 돌려주고, 대기줄이 비고, 「동기화했어요 ✅」가 뜬다(함수 재현 E). 152행과 190행 주석의 「저장 성공 뒤에만 비움」은 실제와 다르다.
- **계정이 바뀌면**: 로그아웃 때 통째로 지운다(`js/account-isolation.js` 15행, 64~74행). 대기줄 항목에는 주인 표시가 없다.

## 6. 함수 수준 재현 13조건
원시 출력의 약자 — `threw`: 예외를 던졌는가 · `warn`: 콘솔 경고 수 · `bk`: 기록 백업에 새 기록이 있는가 · `full`: 전체 사본에 있는가 · `q`: 대기줄이 있는가 · `srv`: 서버에 새 기록이 있는가 · `shown`: 재실행 뒤 화면 데이터에 있는가 · `up[]`: 재실행 때 나간 기록 올리기 요청.

| 조건 | 원시 출력 | 뜻 |
|---|---|---|
| A. 기록 쓰기 500, 서버에 옛 기록 2건 | `save: threw0 warn0 bk1 full1 q0 srv0 \| restart: shown0 n2 bk0 up[] srv0` | 조용히 실패하고 기기에는 남는다. 재실행하면 화면과 백업에서 사라지고 다시 올리지 않는다 |
| B. 500, 서버 기록 0건 | `… \| restart: shown1 n1 bk1 up[checkins.upsert:1] srv1` | 재실행 때 남고 다시 올라간다 |
| F. 401, 서버 2건 | A 와 같음 | 401 도 조용하고, 재실행하면 사라진다 |
| G. 500, 서버 2건, 재실행 때 조회도 실패 | `… \| restart: shown1 n3 bk1 up[checkins.upsert:3] srv1` | 조회가 실패하면 기기 것을 쓰고 다시 올린다 |
| C1. `users` 응답 없음 | `ret0 bk0 full0 keys[]` | 함수가 안 끝나고 기기에 아무것도 없다 |
| C2. `goals` 응답 없음 | `ret0 bk0 full1 keys[goals,guest_profile]` | 기록 백업 전에서 멈춘다 |
| C3. `checkins` 응답 없음 | `ret0 bk1 full1 keys[goals,guest_profile,records]` | 기기에는 있고 함수는 안 끝난다 |
| D. 서버 클라이언트 없음 | `threw0 warn1(Supabase sync failed:) bk0 full0 keys[settings]` | 경고 1건, 기기에는 설정만 |
| D2. 게스트, 서버가 전부 거절 | `warn0 full1 keys[goals,guest_profile,records,profile,settings]` | 게스트는 기기에 남는다 |
| E. 대기줄 1건, 서버 500, `syncOnline` | `res{"synced":1,"failed":0} queueLeft0 srv0 toasts1` | 올리지 못했는데 비우고 성공 알림 |
| H. 목표 쓰기 500, 서버 목표 1건, 재실행 | `warn0 \| restart shown0 n1 bk0` | 새 목표가 사라진다 |
| I. 500 뒤 같은 실행에서 다시 저장 | `srvAfterFail0 srvAfter2nd1` | 다음 저장 때 같이 올라간다 |
| K. 저장 성공 뒤 재실행 | `bkBefore photo1 fb1 \| shown photo0 fb0 energy- goalIdg9 \| bkAfter photo0 fb0` | 사진과 피드백이 화면과 백업에서 사라진다 |

## 7. 중복 반영 가능성(전부 코드로 읽음)
- **홈 오늘 기록**: 첫 기다림 전에 단추를 잠근다(39행, 44행). 두 번 눌러도 1건이다. id 는 누를 때 한 번 만들고(66행) upsert 라서 늦게 성공해도 서버 중복이 없다.
- **기록 탭 기록 창**: 잠금이 없다. 저장이 늦을 때 한 번 더 누르면 같은 객체를 다시 넣어(485행) 같은 id 가 2건이 된다. 경험치는 없다.
- **기록 도우미 창**: 잠금이 없다. 한 번 더 누르면 같은 id 2건에 경험치도 두 번이다(133~134행).
- **전문 템플릿**: 잠금이 없지만 저장 전에 창을 닫는다(141행). 두 번째 누름이 닿기 어렵다(추측). 닿으면 id 가 새로 생겨 2건에 경험치 두 번이다.
- **목표 만들기**: 잠금이 없고 누를 때마다 id 가 새로 생긴다(218행, 308행). 저장이 늦을 때 두 번 누르면 목표가 2개다.
- **같은 id 2건이 서버 묶음에 들어갈 때**: 매 저장이 기록 전체를 한 묶음으로 보내므로, DB 가 묶음을 통째로 거절하면 그 뒤 모든 기록 저장이 조용히 실패한다. DB 가 실제로 거절하는지는 추측이다(못 잼).
- **경험치는 따로 간다**: 별도 서버 원장이 5초마다 돌고 실패하면 30초 뒤 다시 시도한다(`js/avatar/xp.js` 317~388행). 기록이 사라져도 경험치는 남는다.

## 8. 출시 전 판단 재료
**고쳐야 한다고 볼 근거가 있는 것**
1. 서버가 500 이나 401 로 답해도 성공 알림이 뜨고, 로그인 사용자의 그 기록·목표가 재실행 때 사라진다(함수 재현 A · F · H). 조건은 서버에 이미 1건 이상 있고, 실패 뒤 같은 실행에서 성공한 저장이 없을 때다. 기존 사용자 대부분이 이 조건에 든다.
2. 서버가 답하지 않으면 기기에도 저장되지 않고 화면이 「기록 중…」에 멈춘다(함수 재현 C). 그때 앱을 끄면 기록이 어디에도 없다. 게스트도 같다.
3. 저장 실패를 알리는 경로가 사실상 0개다(코드로 읽음, 함수 재현 E).
4. 오프라인 대기줄이 서버 실패에도 비워지고 성공 알림을 낸다(함수 재현 E). 앱을 켤 때는 처리하지 않는다(코드로 읽음).
5. 사진 · AI 피드백 · 에너지 · 집중이 로그인 재실행 때 기기에서 지워진다(함수 재현 K). 저장 실패와 무관하게 매번 일어난다. 영향이 커서 화면 확인이 필요하다.

**근거가 약한 것(코드로만 읽음)**
- 기록 창과 기록 도우미 창의 두 번 누름으로 같은 id 2건, 경험치 두 번. 느린 망에서만 생긴다.
- 그 중복 id 때문에 이후 기록 저장이 전부 실패하는 연쇄(DB 동작 추측).
- 목표 만들기 두 번 누름으로 목표 2개.
- 수동 동기화 단추가 기기에만 있는 기록을 버림.
- 서버 클라이언트가 없을 때 기기 무저장(함수 재현 D 는 됐으나 발생 빈도 모름).
- 일정과 설정은 기기 전용이라 기기를 잃으면 같이 잃는다.
- 저장할 때마다 목표와 기록 전체를 다시 보낸다. 기록이 많을 때의 시간과 실패율은 못 쟀다.

**모르는 것**
- 실제 서버 라이브러리가 500 · 401 · 망 끊김을 가짜와 같은 모양으로 돌려주는지. 가짜는 「예외 없이 error 를 돌려준다」로 만들었다. `js/tabs/comm/dm-ledger.js` 65행 주석이 같은 말을 하지만 실제 라이브러리는 돌리지 않았다. `index.html` 2145행은 버전을 고정하지 않고 `@2` 로 불러온다.
- 브라우저가 답 없는 요청을 얼마 뒤에 끊는지.
- 운영 DB 의 `checkins.id` 형식.
- 세션 없이 전체 사본으로 들어가는 부팅 길의 실제 결과.
- 이 실패들이 실사용에서 얼마나 자주 나는지.
