## 4. 지시(DIR-006)에 옮긴 자리
- 「왜」 ⑦ — 위 1 · 3 · 4 · 5 를 표시와 함께.
- (나) — 읽기 조사를 이미 한 사실과 범위를 넘긴 조회, 그리고 **실서버 쓰기 시험이 묶음 B 보다 먼저이고 상민님 승인 뒤에만 한다**는 것(아래 5절의 아홉 가지).
- (라) 묶음 B — 지움 처리는 운영 표의 사실이 확인된 뒤에 설계한다.
- (가) 묶음 P0 는 그대로다 — 서버에 더 묻거나 더 올리지 않는 묶음이라 이 사실들이 닿지 않는다.
- 「결심 대기」 표 — 운영에 실행되지 않은 것으로 보이는 SQL 을 실행할지(새 줄) · 「서버가 도와야 되는 보장」 줄에 위 6.

## 5. 쓰기 시험을 해야만 알 수 있는 것(조사 문서의 아홉 가지 — 그대로)
1. 없는 칸이 든 쓰기의 실제 응답(코드 · 글): `theme` 든 기록 묶음, `trash` 든 users, `deleted_at` 수정 — 앱의 재시도 조건(오류 글의 낱말)에 실제로 걸리는가, 지움 요청이 정말 0행 반영인가.
2. uuid 아닌 id 가 섞인 묶음: 전체 거절인가, 오류 코드, 그때 앱에 보이는 것.
3. 기본 키와 upsert 의 충돌 기준. 같은 id 재시도 · 한 묶음에 같은 id 둘 · 다른 계정이 같은 id 를 쓸 때(덮어씀 / 거절 / 새 행).
4. 「돌려받기」가 되는가, 돌려주는 칸과 꼴, 서버가 바꾸는 값(시각의 꼴 · `created_at` 기본값 · `due_date` 변환 · 빈값과 안 보냄의 차이).
5. `goals.updated_at` 이 새로 쓸 때 · 고칠 때 누가 채우고 바뀌는가(조건부 쓰기에 쓸 수 있는가).
6. 쓰기 접근 규칙: 자기 행 쓰기 · 상대 행 쓰기 거절 · 0행 결과 · 행 삭제(delete) 허용 여부(하네스 정리는 delete 를 쓴다).
7. `users` 행 없이 기록 · 목표를 쓰면(외래 키), users 저장이 5칸으로 줄어드는 것이 실제인가.
8. 한 묶음의 행 수 · 본문 크기 제한, 한 번 조회의 상한(1000건을 넘는 자료가 있어야 잰다 — 시험 계정에 그만큼 만들고 지우는 일이 따른다).
9. 지운 뒤 다시 열면 되살아나는가(화면 · 운영): 사실 2번의 확정.

(9번의 「사실 2번」은 조사 문서 「계약에 닿는 사실」의 2번 — 위 표의 1번 — 이다.)

## 6. 이 작업자가 다시 본 것과 못 본 것
- **다시 본 것**: 요청 기록 둘을 세었다 — 139건 · GET 133 · 표에 대한 GET 아닌 요청 0 · 응답 코드별 건수 · 오류 코드별 건수(42703 38 · 22P02 11 · 22007 8 · PGRST103 1)가 조사 문서와 같다. 위 표의 [확인] 가운데 칸의 유무(#11 #12 #13 #24 #26 #47 #49 #86)는 요청 기록의 응답 코드로 다시 보았다. 2절의 11건도 요청 기록에서 찾았다. 코드 줄(`trash-bin.js` 72 · 84행 · `record-ledger.js` 65~84행 · `home-cockpit.js` 197~202행 · `profile-load.js` 110~111행)은 origin/main 에서 다시 읽었다(`../measure.json` 의 `realServer`).
- **못 본 것**: 운영 서버에 접속하지 않았다 — 응답 자체는 조사 담당이 받은 것이고 이 작업자는 그 기록만 보았다. 요청 기록에는 본문이 없으므로 「돌아온 칸 9개」 「자기 행 5건」 같은 값은 조사 문서와 요약 파일(`result.json`)의 것이다.
- 요약 파일 `result.json` 에 운영 서버의 주소(프로젝트 이름이 든 호스트)가 한 줄 있다. 저장소의 `index.html` 에 이미 적혀 있는 공개 주소다. 토큰 · 공개 키 · 계정 id · 메일 주소 꼴은 넣은 파일에서 0건이다(글자 찾기).
