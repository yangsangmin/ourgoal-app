## 0. 함수 재현과 달라진 것

1. **응답 없음 뒤 「새로 고침」은 「앱 종료」와 결과가 다르다.**
   - 탭을 강제로 죽이면 기록은 어디에도 없다. 서버 기록이 0건이어도 사라진다(함수 재현과 같음).
   - 같은 탭에서 새로 고침하면, 멈춰 있던 저장이 그 순간 풀려 기기에 쓰고 서버로 다시 보낸다. 그때 서버가 정상이면 기록이 살아난다. 그때도 서버가 답하지 않으면 서버 옛 기록이 있는 사용자는 잃는다.
   - 이 「풀림」이 실제 브라우저의 새로 고침에서도 똑같은지는 확정하지 못했다(재현 도구가 요청을 붙잡는 방식의 영향일 수 있다).
2. **오프라인 대기줄은 기록을 되살린다.** 앞 보고서는 「넣기만 하고 실패해도 비운다」까지만 적었다. 화면에서는 온라인 사건이 오면 대기줄의 기록을 화면 데이터에 다시 넣고 올렸다. 앱을 껐다 켠 뒤에도 그랬다.
   - 다만 켤 때는 처리하지 않는다. 다시 켠 화면에 그 기록은 없고, 대기줄에만 남아 있다가 다음 오프라인→온라인 전환 때 돌아온다.
   - 온라인으로 돌아온 순간 서버가 500이면 「동기화했어요 ✅」가 뜨고 대기줄이 비며, 새로 고침 뒤 기록은 사라진다(함수 재현 E와 같음).
3. **서버가 답하지 않거나 통신이 거절될 때 다시 켜면, 로그인 사용자에게 랜딩 화면(「로그인 없이 둘러보기」)이 보인다.** 통신 거절은 21.6초 뒤 앱으로 들어갔고, 응답 없음은 45초까지 들어가지 못했다. 앞 보고서에 없던 내용이다.
4. **저장 실패는 켜 둔 채 기다려도 다시 올라가지 않는다.** 서버가 돌아온 뒤 45초 동안 올리기 요청은 0건이었다. 탭을 한 번 바꾸자 올라갔다. 앞 보고서의 「같은 실행 안에서 다음 저장이 일어나면 올라간다」는 맞지만, 그 저장은 사용자가 무언가를 해야 일어난다.

그 밖의 함수 재현 결과(A, B, D, D2, E, F, G, I, K)는 화면에서 같게 나왔다. 가짜 서버의 가정도 맞았다(1절). H(목표 저장 실패)는 화면에서 재지 않았다.

D 는 화면에서 보니 무게가 더 크다. 연결 라이브러리를 못 받은 상태(CDN 실패)에서 게스트가 사진 기록을 저장하면 성공 알림이 뜨고 기록 탭에도 보이지만, **새로 고침하면 기록이 없다.** 기기에 쓰이지 않기 때문이다(콘솔 경고 「Supabase sync failed」만 남는다). 이 상태가 실사용에서 얼마나 자주 생기는지는 모른다. 오프라인에서 앱을 처음 켤 때가 후보인데 재지 않았다.

## 1. 진짜 라이브러리가 답하는 모양

두 판을 쟀다: 운영 화면이 지금 받는 판(CDN `@2` = 2.117.3)과 저장소에 든 판(2.115.0). 결과는 같다.

| 서버 상태 | 쓰기(upsert) | 읽기(select) |
|---|---|---|
| 500 (JSON 본문) | 예외 없음. `{error:{message:"Internal Server Error"}, status:500}` | 같음. 요청 1번 |
| 500 (HTML 본문) | 예외 없음. `error.message` 에 HTML 글자가 그대로 들어감 | 같음 |
| 503 | 예외 없음. `{error}`, status 503. 요청 1번 | 예외 없음. **요청 4번, 7초 뒤** `{error}` |
| 401 | 예외 없음. `{error:{message:"JWT expired", code:"PGRST301"}, status:401}` | 같음. 요청 1번 |
| 통신 거절 | 예외 없음. `{error:{message:"TypeError: Failed to fetch"}, status:0}`. 요청 1번 | 예외 없음. **요청 4번, 7초 뒤** `{error}` |
| 응답 없음 | 8초 동안 끝나지 않음. 라이브러리에 시간 제한 없음 | 같음 |

**「예외 없이 error 를 돌려준다」는 가정은 맞다.** 새로 안 것은 읽기만 503과 통신 거절에서 3번 더 시도한다는 점이다(쓰기는 다시 시도하지 않는다).

## 4. K 판정 — 사실이다

**로그인 사용자가 사진 기록을 저장하고(서버 성공) 새로 고침하면 기록 카드에서 사진과 AI 피드백이 사라진다. 기기에서도 지워진다.**

| 시점 | 기록 카드 | 화면 데이터 | 기기 백업 · 전체 사본 |
|---|---|---|---|
| 저장 직후 | 사진 보임, AI 피드백 글 보임 | 사진 · 피드백 · 에너지 60 · 집중 40 | 사진 · 피드백 있음 |
| 새로 고침 뒤 | **사진 없음, 피드백 글 없음**(본문 · 시각 · 테마만) | 넷 다 없음 | **넷 다 지워짐** |

- 서버 기록이 2건일 때와 0건일 때 모두 같다. 사진이 든 다른 기기 열쇠도 없다(0개).
- 서버로 간 줄의 칸은 12개(`id, user_id, type, text, start_at, end_at, category, theme, sub_theme, theme_confidence, meta, created_at`)이고 사진 · 피드백 · 에너지 · 집중은 없다.
- **사진을 서버에서 따로 불러오는 길은 없다**(코드 다시 확인). Supabase 저장소 호출은 0곳이고(`storage` 검색에 걸린 것은 브라우저의 용량 측정이다), 사진 칸을 가진 표도 없다. 피드에 공유한 사진은 피드 글에만 붙고 기록으로 돌아오지 않는다. 새로 고침 때 나간 요청에도 사진을 찾는 것은 없었다.
- 지워지는 자리는 `js/core/profile-load.js` 177행이다. 서버에서 받은 기록(사진 없음)으로 기기 백업을 통째로 덮어쓴다.
- **게스트(둘러보기)는 해당하지 않는다.** 같은 순서로 재 보니 새로 고침 뒤에도 사진과 피드백이 남았다.
- 설계 문서(`docs/specs/LEDGER-DESIGN-2026-10-04.md` M03 줄)에는 이 손실이 적혀 있지 않다.
- 얼마나 많은 실사용자가 이미 겪었는지는 재지 못했다(실계정 금지).

## 5. 응답이 늦을 때 여러 번 누르기 (쓰기마다 3초 뒤 성공, 0초 · 0.4초 · 1.5초에 세 번)

| 화면 | 단추 상태 | 화면의 기록(목표) 수 | 경험치 | 알림 | 서버 |
|---|---|---|---|---|---|
| 홈 오늘 기록 | 2 · 3번째 때 잠김 | 1건 | +40 (한 번 누른 것과 같음) | 1번 | 1건 |
| 기록 창(새 기록) | 계속 열림, 창도 열림 | **3건, id 는 하나** | 0 (원래 없음) | 「기록을 추가했어요」 3번 | 아래 |
| 기록 도우미(빠른 기록) | 계속 열림 | **3건, id 는 하나** | **+60** (한 번은 +40) | 「기록을 저장했어요!」 3번 | 아래 |
| 목표 만들기(직접 설정) | 계속 열림 | **목표 3개, id 는 셋** | 0 | 1번 | 목표 3개 저장됨. 새로 고침 뒤에도 3개 |

같은 id 가 세 번 든 묶음을 서버가 어떻게 받는지는 **가정**이다(운영 DB 로 재지 않았다). 두 가정을 다 돌렸다.
- 거절한다고 보면(Postgres 의 알려진 규칙 21000): 그 뒤의 기록 저장이 모두 실패한다(12~13번 전부). 새로 고침 뒤 그 기록은 0건이다. 기록 도우미는 경험치 +60만 남는다.
- 받아 준다고 보면: 서버에 1건, 새로 고침 뒤 1건. 기록 도우미의 경험치는 +60 그대로다.

- 실서버 · 실계정 · 접근 제한 규칙. 서버 답의 모양은 가짜 서버가 정한 것이다.
- 운영 DB 가 같은 id 묶음을 거절하는지, `checkins.id` 의 형식.
- 「응답 없음」은 요청을 끝없이 붙잡는 방식이다. 실제 망에서는 언젠가 오류로 끝나는데 그 시간은 재지 않았다.
- 탭 강제 종료는 렌더러를 죽이는 방식(`Page.crash`)이다. 휴대폰에서 앱을 밀어 끄는 것과 같은지는 재지 않았다.
- 랜딩 화면이 보일 때 「로그인 없이 둘러보기」를 누르면 기존 데이터가 어떻게 되는지.
- 목표 저장 실패(H)의 화면 판, 전문 템플릿 창 · 시간 기록 · 타이머의 두 번 누르기.
- 연결 라이브러리를 못 받은 상태의 로그인 사용자, 그리고 그 상태가 생기는 빈도(오프라인에서 앱을 처음 켤 때 등).
- 서비스 워커 · 설치형 앱 · 휴대폰 실기기 · localStorage 용량 초과.
- 에너지 · 집중 슬라이더는 값을 바꾸고 입력 사건을 낸 것이다(손가락 끌기 아님).
